## 1. 结论

EP003 最终「20/20 帧 PASSED、四阶段推进到 PRODUCTION_PASSED」是成立的，但这个结果是被用户和人工挡回来的，不是闭环自动跑出来的。三条主线问题：

1. **出图通道有系统性质量缺陷**：47 个 provider receipt 里 26 个是 100x100 的退化图（55%），被通道当成「有效生成」收下并落盘成 raw，再由下游按宽高比不符打回。整集为此付出 52 次尝试（正常应为 20 次左右），Frame07 单帧烧掉 8 次。
2. **评审链看不见「图错了但看起来像对的」**：Frame15 的手臂畸形是用户肉眼看出来的，运行时侧 20/20 frame review 全部 pass、issue_codes 全空、全部是 `WORK_ISOLATED` 委派评审。修完之后再次 pass。也就是说当前自动评审对解剖/肢体/结构类畸变没有判别力。
3. **状态与证据层在收口前就已经不自洽**：性能账本没收到终态、图片尝试数为空、队列里还挂着 1 个 blocked 帧、派生缓存停在 STORYBOARD_LOCKED、评审证据能写未来时间戳、废弃没有官方出口。这些不影响出图，但会让「稳定生产闭环」的判定不可信。

## 2. A 组：出图通道

### W-25 Provider 100x100 退化图被当作有效生成收下（新，P0）

现象：`codex_subscription` 通道有相当比例返回一张 100x100 的图，通道侧仍写入 provider receipt、保留 raw，不做退化判定；下游再用 `ASPECT_RATIO_MISMATCH` 打回。

证据：

- `meta/provider-receipts/*.json` 共 47 个，`provider_raw_canvas` 分布：`1122x1402` 21 个、**`100x100` 26 个**。
- `media/raw/` 47 个文件，与 47 个 receipt 一一对应，说明退化图已经落盘。
- `production-queue.json` 中 26 条 `last_error` 全部为 `ASPECT_RATIO_MISMATCH: source=100x100, target=1080x1350, ratio_delta=0.250000`。
- `trace-events.jsonl` 中 `ASPECT_RATIO_MISMATCH` ×26，与 receipt 数完全吻合。

影响：26 次成功「生成」全部作废，占实际尝试付出的一半以上；配额、墙钟、日志全部被污染。

状态：❌ 未解决。建议在 receipt 落盘前加退化画布判定（极端小尺寸 / 长宽比严重偏离请求值直接判技术失败，不入 receipt、不落 raw、不消耗内容额度）。

### W-26 出图入口 prompt 预算阈值与真实 prompt 规模不一致（新，P1）

现象：Frame01 的第一个 attempt 在 `BEGIN_REJECTED` 阶段被拒，原因是 prompt 预算超限。但 EP003 的真实生产 prompt 是 30KB 级的 `meta/runtime/prompt-packages/*.json`，说明这个 260 字符/900 字节的阈值和实际生产 prompt 规模不在一个量级上。

证据：

- `production-queue.json` Frame01 条目：`prompt budget exceeded: 317 chars/923 bytes; limit=260 chars/900 bytes`
- `execution.phase = BEGIN_REJECTED`，`prepared_at = 2026-09-11T13:41:58+08:00`
- 对照 `meta/runtime/prompt-packages/01.json` 实际体积 29851 bytes

影响：首帧直接拒单，浪费一次事务准备；阈值语义（校验的是哪段文本）不清晰，容易在别集变成随机阻塞。

状态：❌ 未解决。

### W-27 技术失败不留 provider receipt，收据链有缺口（新，P1）

现象：attempt 数与 receipt 数不一致。

证据：

## 3. B 组：像素质量与评审

### W-28 自动/委派评审对肢体解剖畸变无判别力（新，P0）

现象：Frame15 女生的手臂比例失真、手臂与衣袖融合，是由**用户肉眼**发现并提出的；运行时侧对同一张图给出的结论是 pass。

证据：

- 20 个 `meta/frame-reviews/*.json`：`decision` 全部 `pass`。
- `issue_codes` 全部为空（0 条）。
- `critic_provenance.runtime` 全部 `WORK_ISOLATED`（委派评审，非人工亲审）。

状态：❌ 未解决。这不是「再加一条规则」能补的，需要在评审维度里显式加入人体结构检查项（手/臂/关节/衣物-皮肤过渡），并承认它是当前评审的能力边界。

### W-29 已 PASSED 帧的用户点名返修被 ledger 拒绝（新，P1）

现象：用户点名要求修 Frame15 时，有一次返修尝试被账本直接拒绝。

证据：

- `production-queue.json` Frame15 条目 `status=blocked`，`last_error = ledger begin failed: cannot begin original from PASSED`，`phase=BEGIN_REJECTED`，`prepared_at=2026-09-11T18:03:10+08:00`。

影响：「PASSED 帧不可再 begin original」这个保护是对的，但它与「用户明确要求返修」这条合法路径冲突，最终表现为一次静默 blocked + 队列终态污染（见 W-30）。缺少显式的 repair 入口（以 kind=repair 而非 original 开启事务）。

状态：❌ 未解决。

## 11. 附：5 小时 18 分的时间去哪了

整集 12:56:43 → 18:14:49 = **318 分钟**，20 帧，平均 16 分钟/帧。从账本上看不出来（见 W-09），下面是按 worker 日志重建的时间线。

### 11.1 三个宿主步骤占了 82% 的墙钟

| 步骤 | 区间 | 时长 |
| --- | --- | --- |
| `CREATIVE_STORY`（host-184a9a3e…） | 12:57:50 → 13:13:51 | 16 min |
| `PREIMAGE_COMPILE`（host-385a7b5a…） | 13:13:52 → 14:22:57 | 69 min |
| `VISUAL_LOCK`（host-a962125a…） | 14:23:00 → 17:19:17 | **176 min** |
| 尾部评审/字幕/门禁/阶段推进 | 17:19:17 → 18:14:49 | 56 min |

合计宿主步骤 261 min / 318 min。**出图不是一个后台 worker 池在跑，而是被一个 176 分钟不关闭的 host request 驱动**；这期间任何宿主侧等待（评审、往返、等用户）都直接落在关键路径上。

出图窗口本身是 13:42:35 → 17:50:24 = **248 分钟**（Frame01 baseline 在 `PREIMAGE_COMPILE` 步骤期间就已经开始生成）。

### 11.2 并发实际是 0.83，配置是 3

按分钟采样 51 个 worker 日志的在途数：

```
0 个 worker 在跑：106 min  (43%)
1 个 worker 在跑：102 min  (41%)
2 个 worker 在跑： 16 min  ( 6%)
```

worker-minutes 合计 206 min，与 attempt 时长合计 12095s（202 min）吻合。**有效并发 0.83**，只有 16% 的时间真正用上了 2~3 个 worker。

`meta/batch-runtime-performance.json` 的 23 个 batch：`max_workers=1` 有 17 个、`=3` 有 6 个；planned 合计 42、returned 合计 16（38%）。计划 5 帧的 6 个 batch 只收回 9/26 帧。**20 帧的集从头到尾没有真正成批跑过。**

### 11.3 根因一：3 并发直接撞限流，系统把自己降级成串行

14:38:51 第一次发起 3 帧并行（03 / 06 / 19）：

三个 worker 同 pid、同秒失败。此后 scheduler 的 `max_workers` 再没稳定回到 3。这一条与 V2.4.2 的设计约束叠加：`meta/batch-provider-capability.json` 里 `openai_images_api.credential_available = false`，**没有 API Key 时全局只允许 1 个 Logical Batch 在途**——也就是说本机的串行是设计内的，3 并发是设计外的。

### 11.4 根因二：78% 的后端时间烧在没有产出的尝试上

`trace-events.jsonl` 的 51 个 `image_generation` span：

```
FAILED 30 个 → 9486s (158 min)

```

**有效产出的生成只占 54 分钟**。失败里最大一块就是 W-25 的 100x100 退化图（26 个 receipt），每次照样跑满 240–380 秒才打回重试。

| 帧 | attempts | 首末跨度 |
| --- | --- | --- |
| F07 | 8 | 15:16:20 → 16:17:13 = **61 min** |

F07 + F15 两帧就吃掉出图窗口的一半以上。F10 那种「2 次尝试 39 分钟」的形态说明它不是生成慢，而是在 F07 后面排队。

### 11.5 根因三：三段宿主机空档，共约 108 分钟没有 worker 在跑

```
13:49:18 -> 14:38:51   49.5 min   (Frame01 baseline 之后 → 三帧并行之前)
14:47:30 -> 15:03:17   15.8 min
17:16:59 -> 17:42:40   25.7 min   (用户指出 Frame15 手臂畸形之后的返修空档)

```

这 108 分钟里没有任何图片 worker 在跑。同期账本里对应的 `VISUAL_LOCK_BASELINE_REVIEW` 只有 342.5s、`PRODUCT_REVIEW_VISUAL-LOCK-BASELINE` 只有 56.3s，两个评审 span 加起来 7 分钟——**其余 40 多分钟是宿主/评审/用户往返，不是后端在算**。

### 11.6 根因四：单次生成本身偏慢，且每次都重起一个 Codex 会话

51 次尝试时长分布：min 59s / p25 103s / **median 296s** / p75 344s / max 364s / mean 237s。28 次落在 240–380s，13 次在 120s 以下（快速失败）。

每次尝试都是一个完整的 Codex 会话：隔离 `CODEX_HOME` → 加载 plugin/MCP/skill → websocket prewarm（失败）→ `legacy_notify` hook 报 `os error 206` → 单轮 `input_tokens≈88484`。固定开销按日志里的启动段估计在 60~90 秒量级，占成功尝试时间的 20%~30%。

### 11.7 小结：如果三件事修掉，本集应该是多长时间

20 帧 × 中位 296s ÷ 3 并发 ≈ **33 分钟**后端时间，加上前期 17 分钟、评审与门禁 60 分钟，整集在 **1.5~2 小时**内可收口。实际用了 5 小时 18 分，多出来的 3 个多小时基本对应：

- 26 次 100x100 废图（≈2 小时，W-25）
- 并发被 429 压回 1（≈1 小时，W-06/W-14）
- 三段宿主空档（≈1.8 小时，含用户反馈往返，属流程而非引擎）

**注意**：这三项都不是「模型太慢」，而是通道质量、并发策略和宿主驱动方式的问题。
