## W-45 Authority Refresh 与 Incremental / PREIMAGE Recovery 状态不兼容（P0）

### 暴露

M04 天界普通居民生活档案及人物/Frame Contract 等上游权威重新派生后，Visual Lock 的 `01 / 05 / 16 / 17` 被正确标记为 `AUTHORITY_REFRESH_AUTHORIZED`，要求按新权威重新生成且不消耗普通内容返修额度。但恢复链存在四层不兼容：

1. `incremental_frame_review.py` 只接受 `PASSED / LOCKED`，把合法的 `AUTHORITY_REFRESH_AUTHORIZED` 当成坏数据，直接抛 `ValueError`。
2. `PREIMAGE_VERIFY` 这类纯确定性校验/重建仍被 Runtime DAG 发成 WORK Host Action，造成无意义 `HOST_WAIT`。
3. `product_runtime_adapter.next_host_step()` 只检查 Frame Contract index 文件是否存在，没有验证合同是否仍与当前权威 SHA 一致，因此 stale index 被误判为可直接 VERIFY。
4. 更深一层，旧 `PREIMAGE_COMMITTED_SNAPSHOT` 也可能已 stale；此时直接重编 Frame Contract 会被正确拒绝，恢复顺序必须先回到 fresh PREIMAGE task set，而不能硬刷新 derived cache。
5. Runtime DAG 已正确要求 fresh PREIMAGE 后，`next_action` 仍可能因 Ledger 中存在 `AUTHORITY_REFRESH_AUTHORIZED` 而优先返回 `REFRESH_AUTHORITY_IMAGES`；连续 Host Loop 会因此绕过 fresh PREIMAGE，形成旧权威图片刷新与新权威重建的竞态。

### 修复

- `incremental_frame_review.py`
  - 新增 unfinished ledger 识别；最终语义 Review 不再消费中间生产态。
  - `AUTHORITY_REFRESH_AUTHORIZED` 明确派生为 `AWAITING_AUTHORITY_REFRESH`，并保留 `authority_refresh_frames`、全部 pending 状态与原因。
  - `AWAITING_AUTHORITY_REFRESH / AWAITING_PRODUCTION` 不启动 Final Critic。
- `product_runtime_adapter.py`
  - `next_host_step()` 同时检查 PREIMAGE committed snapshot 新鲜度与 `frame_contract.verify_all()`。
  - stale committed snapshot → `PREIMAGE_TASK_SET`。
  - committed snapshot 有效但 Frame Contract stale/missing → `PREIMAGE_FRAME_CONTRACT_COMPILE`。
  - Frame Contract 有效但 handoff stale → `PREIMAGE_VERIFY`。
  - `PREIMAGE_VERIFY / PREIMAGE_FRAME_CONTRACT_COMPILE` 的历史 Host Request 可在 canonical evidence 已有效时 reconcile，不永久占用 current pointer。
- `runtime_dag.py`
  - 仅把 `PREIMAGE_FRAME_CONTRACT_COMPILE / PREIMAGE_VERIFY` 两类无模型确定性动作留在本地执行。
  - 真正需要模型生成候选的 `PREIMAGE_TASK_SET` 继续保持 WORK + DevSpace Host 边界，不静默交给 Codex，也不伪造候选。
- `next_action.py`
  - `STORYBOARD_LOCKED` 且 PREIMAGE authority/handoff stale 时，canonical PREIMAGE freshness barrier 优先于 Production Queue。
  - 此时统一返回 `PREIMAGE_COMPILE` 并携带真实 `preimage_step`，禁止 `AUTHORITY_REFRESH_AUTHORIZED`、技术重试或其他图片动作抢跑。
  - 只有 handoff 已重新验证后，Queue/Authority Refresh 图片路径才恢复正常优先级。

## W-48 Visual Lock 单帧 PASS 不固化，四图复审可让未变化像素反转并被旧 Candidate Pool 判耗尽（P0）

### 暴露现象

Frame17 fresh authority-refresh 重生后，`next_action` 最终返回：

```text
action = USER_DECISION_REQUIRED
frames = [5, 16, 17]
reason = Visual Lock bounded admission candidate pool exhausted after real Codex Vision failures
```

但进入本轮前的真实视觉审核结论曾是 Frame01 / Frame05 / Frame16 单帧 PASS，只剩 Frame17 FAIL。

### 硬证据

`meta/visual-lock-critic-attempt-5.jsonl`（2026-09-14 09:42 +08:00）中：

- V-B / Frame01：全部 checks=true，issues=[]；
- V-W / Frame16：全部 checks=true，issues=[]；
- V-A / Frame05：全部 checks=true，issues=[]；
- V-H / Frame17：FAIL。

当前像素未变化：

```text
Frame05 sha256 = f397389a28536012af4965e30116994ac36f9cfc71d877c80e849659a81e23dd
Frame16 sha256 = 193e5f4745d1437ce64773f904c24e6e5f402a37134e4be94ea9721d86e129ec
```

Frame05 该像素生成于 2026-09-14 09:41:53；Frame16 该像素生成于 2026-09-13 23:12:03。后续只 fresh 重生了 Frame17。

但 2026-09-14 11:16 的 fresh four-admission Critic 又把同一 Frame05/16 像素重新判 FAIL；当前 `visual-profile-review.json` 因此包含 Frame05/16/17 的失败行。

### 根因 1：Gate 决策是全有或全无

`visual_lock_v21._mark_decisions(ep, passed)` 只接收一个全局 `passed`：只要四张里任何一张失败，四个 calibration item 全部写成 `failed`。因此 Frame17 单张失败会覆盖 Frame01/05/16 已取得的单帧 PASS 语义。

### 根因 2：Ledger 只落失败，不固化单帧 PASS

`visual_lock_v21._record_failed_calibration_frames()` 只遍历失败 row，并执行 `production_ledger review --decision repair`；没有与之对称的 SHA-bound per-frame PASS/admission 固化路径。

所以即使某一轮 Critic 明确判定 Frame05/16 PASS，只要四图总体仍 FAIL，它们不会被 Ledger 固化成“当前 SHA + 当前 Frame Contract 已通过”；此前的 `NEEDS_USER` 状态仍可能保留。

### 根因 3：Frame17 改图会重新审全部四张未变化像素

Visual Lock 当前 review scope 固定为 `VISUAL_LOCK_FOUR_ADMISSION`。Frame17 换像素后，01/05/16 也重新交给新的 isolated Vision 会话自由判断。

因此同一像素可以出现：

```text
09:42 PASS
11:16 FAIL
```

对于 SHA、Frame Contract、Profile、review schema/check-set 均未改变且已有有效单帧 PASS 的 admission，不应因为别的 admission 换图而失去已验证证据。

### 根因 4：Candidate Pool 不识别已通过 SHA

`visual_lock_candidate_pool.failed_rows()` 直接读取最新 `visual-profile-review.json`；`exhausted_frames()` 只判断 latest review row failed + Ledger `NEEDS_USER` + no active candidate + `successful_slots >= maximum`。

`successful_slots()` 又统计所有历史 `visual-lock-candidate-*` 成功输出，没有“该 SHA 已通过 admission”的排除条件，也没有 per-review / per-authority PASS epoch。

于是 Frame05/16 一旦被 fresh Critic 反转成 FAIL，立即因为旧候选 slot 已耗尽而进入 `USER_DECISION_REQUIRED`。

### 结论

**Frame05/16 不是被 fresh Frame17 的内容依赖拖坏，也不是像素或 Frame Contract 发生变化。真正原因是 Visual Lock 缺少“单帧 SHA-bound admission PASS 固化与复用”语义，四图总体 FAIL 会覆盖局部 PASS，fresh review 又会重新审未变化像素，candidate pool 最后把这种判定反转误解释成候选池耗尽。**

### 建议修复方向

1. 新增 per-frame Visual Lock admission evidence，绑定 `frame + asset_sha256 + frame_contract_sha256 + profile_sha256 + review schema/check-set`。
2. 四图总体 gate 仍要求四项全部 PASS，但每个 admission 的 PASS 必须独立固化；其他帧变化不能自动使其失效。
3. fresh review 只审 dirty admission；已有且 provenance 有效的 PASS admission 直接 reuse。
4. `_mark_decisions` 改为逐 row 写 `passed/failed`，不能用全局 boolean 一刀切四帧。
5. Candidate Pool 在 `prepareable_frames/exhausted_frames` 前排除“当前 SHA + 当前 Contract 已有有效 PASS admission”的帧。
6. 只有 asset SHA、Frame Contract、Visual Profile 或 review contract/check-set 变化时，才 invalidate 对应单帧 PASS。

已完成框架修复：

4. Visual Lock fresh review 对单帧 PASS/FAIL 都同步 Ledger；PASS 会进入 `PASSED`，FAIL 才进入 repair/NEEDS_USER 路径。
5. `visual_lock_candidate_pool.failed_rows()` 在进入 prepare/exhausted 计算前排除仍有有效 SHA-bound admission PASS 的帧。
