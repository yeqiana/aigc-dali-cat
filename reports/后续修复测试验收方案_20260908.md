## 5. S2：B1 行为基线

先阅读 image_scheduler、batch_scheduler、scheduler_core、async_scheduler_adapter、上层调用方及恢复测试，建立调用链与返回状态表。

复用 tests/system/test_runtime_recovery.py、test_scheduler_core.py 和已有批次回归；只补缺口，不重复实现已有测试。

记录两类行为：

- 共同行为：对账、依赖检查、attempt 准备、worker 生命周期、输出验证、账本提交、队列回写、失败传播。
- 合法差异：选帧规模、Provider 分派、原生批次共享请求、能力探针、批次完成屏障、Scout、并发调整和入口返回码。

特别核实：当前单帧入口截取 ready[:max_workers] 后按完成事件消费。本层返回后上层是否补位、何时补位，必须沿调用链测试。“按完成顺序收到事件”不等于“完成一帧立即补入下一帧”。尚未核实的行为不得直接记为故障或已满足。

基线结论（2026-09-08）：单次入口调用先 admit 一批任务（单帧 lane 截取 ready[:max_workers]；batch lane 受 images_per_batch 与验证 lane 限制），随后按完成顺序消费事件；已提交批次内的后续任务在 worker 空出时自动补位，峰值在途不超 workers。队列中超过当批的就绪任务由 episode_runner 周期循环重新进入 scheduler 继续 admit，直到无进展或有界退出。

基线测试记录队列/账本终态、后端调用次数与 frame/attempt 关联、事件先后、峰值在途数和返回码。时间戳、随机 ID 等非语义字段归一化后比较；使用事件同步控制顺序，避免依赖脆弱的固定 sleep。

对照应比较应当相同的行为，并显式断言合法差异。若基线发现缺陷，先单列缺陷与预期行为，不把旧错误固化为必须保持的结果。

## 6. S3：共享循环实施

优先在既有 scheduler_core 及相关模块内抽取最小共享执行骨架，不预设大型类体系。

建议拆分：

1. 规划策略：确定本轮可执行任务、依赖和并发名额。
2. 执行策略：单帧调用或原生批次共享调用，统一交付可消费的逐帧结果。
3. 共享循环：准备生命周期、调度任务、处理结果、校验产物、提交账本和队列。
4. 收尾策略：批次能力与性能记录、并发调整、批后 Scout；单帧只执行适用操作。
5. 入口适配：保留原外部函数、CLI 与返回状态语义。

分小步提交：先提取公共生命周期/结果处理，再接入单帧与批次，最后清除重复循环。每步保留可回滚边界，禁止同时修改正式剧集权威文件。

若确实遇到不能统一的语义，必须给出最小反例、失败测试、被违反的契约和可选设计，再记录保留范围。不能仅凭“实现不同”结束合并。

### 调度测试与验收矩阵

| ID | 场景 | 必须观察到的结果 |
|---|---|---|
| T01 | 一帧超时、其他帧成功 | 成功帧提交且不重生；仅失败帧有界重试 |
| T02 | 一帧阻塞或返修，兄弟帧依赖满足 | 独立帧继续；必要依赖仍被正确阻止 |
| T03 | baseline 尚未通过 | 依赖 baseline 的任务不启动 |
| T04 | 有空闲名额和就绪任务 | 在允许的 lane/batch 范围内补位；测试覆盖上层驱动 |
| T05 | 原生五帧请求 | 同批只发一次原生请求，逐帧映射与提交，不重复启动共享任务 |
| T06 | 原生请求失败回落 | 回落行为可追溯，不能把回落成功冒充 native_multi_image |
| T07 | 逻辑批次与技术失败 | 在途不超配置上限；按策略 3→2→1；成功帧不随重试重生 |
| T08 | 同批部分生成完成 | 全部已提交原始任务终结前，不启动受屏障约束的批后 Scout |
| T09 | Scout 技术失败 | 记录待最终审查，不伪造 PASS，不让独立生成任务全部停下 |
| T10 | 图片成功、Ledger 提交失败 | 保留候选与终态证据；恢复补提交，不再请求生图 |
| T11 | Ledger 成功、Queue 回写失败 | 对账回放成功记录且保持幂等 |
| T12 | 请求已发出、终态未知 | interrupted_unknown，不自动重生；独立任务继续 |
| T13 | begin 前中断、损坏 journal/lifecycle、双 stale | 按各自证据分类恢复，不伪造成功或无界崩溃 |
| T14 | 并发直接写队列、进程退出 | 单写锁有效；退出后可恢复；不覆盖运行中结果 |
| T15 | WORK/WEB 宿主等待、能力缺失 | 保留可执行请求/等待原因，不忙循环、不消耗假 attempt |
| T16 | 无进度、无就绪任务及各类终态 | 有界退出；不能把未完成的空队列选择结果当最终完成 |
| T17 | 连续恢复两次 | 第二次幂等，调用次数、账本和成功候选不重复增长 |

T01–T17 可由已有用例和新增用例共同覆盖，验收记录逐项映射实际测试名称。

## 8. S5：真实生产与交付

选择满足当前门禁的新篇或可恢复在制篇；执行前确认实际授权范围与图片执行配置。墨脱已发布线不作为随意改写状态的测试对象。

通过正式流程验证适用的前期合同、Visual Lock 1+3、Production、逐帧审核、字幕、Release preflight、Final Candidate Snapshot build/verify 和交付消费。已有且 SHA 有效的步骤按正式恢复规则复用，不为测试无条件重跑。

隔离故障注入与真实生产证据分别记录。真实通道正常运行不等于真实故障恢复已经观察到；若未发生故障，明确恢复行为由隔离测试证明，真实运行只证明正常闭环。

验收要求：

- 实际图片与帧映射、合同绑定、输出尺寸、产物 SHA 和可取得的 Provider receipt 可追溯；不可取得的模型独立回执不得推测补齐。
- 无成功帧无故重生，无伪造用户批准，无未授权模型切换。
- 所有适用正式门禁通过，阶段由正式工具推进，交付内容与 verified Snapshot 一致。
- 本阶段以有效交付/PUBLISH_READY 为范围；平台发布和发布后数据复盘按另有的实际授权执行，不作为本方案默认副作用。

## 9. S6：Golden 回归

先取得一个符合当前准入规则的真实样本，再逐步增加。recommended_minimum=10 是覆盖目标，不能为凑数量降低标准。

注册前按当前工具验证全部要求，缺输入不计零错误。既有样本不适用当前规则时保留缺口记录，不补造审核证据。

完成注册后运行实际 Golden 回归与 performance replay，并触发包含 golden-replay 的远端 workflow_dispatch；记录提交 SHA、run/job、样本数量、逐样本结果和跳过原因。需要本地媒体的检查与 Git-only 检出能力分别报告，不能用 metadata-only 代替像素验收。

验收：至少一个真实合格样本实际被执行；registered=0 或 job skipped 均不满足本项完成标准。一个样本通过仅证明该样本覆盖范围，不声明十集目标已达成。
