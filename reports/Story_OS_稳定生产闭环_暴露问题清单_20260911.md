## 1. 结论（先看这里）

**一句话：现在还不能算“稳定生产闭环”。**

- 本次修掉了三个具体断点：①自动出图链没接进主入口；②图片保存冲突被当成静默技术失败；③并发 worker 共享 `CODEX_HOME` 触发保存冲突（改为每 worker 独立目录，第 8 节）。
- 但“生产 → 发布 → 数据复盘”的最后一公里没有任何一集走通：4 集停在 `PUBLISH_READY`，`PUBLISHED` 与 `DATA_REVIEWED` 均为 0 集。
- 平台侧 V3 Runtime 归属已经切换、常驻 Worker 正在跑，但系统服务/计划任务没注册，“重启后能不能自愈”没有验收。
- 所以当前真实状态是：**单篇可以从选题一路走到 `PUBLISH_READY`（需要人盯宿主动作）；发布之后全部未验证。**

分层判定见第 4 节；暴露问题清单见第 3 节。

## 2. 本次修复的两个问题（A/B；本轮用户修复版本见第 8 节）

### 2.1 问题 A：自动出图链没有接进主入口

“停在人工触发图片生成这一步”这个判断**基本属实，但要说准确**：不是没有出图能力，而是没有代码自动调用出图调度器，出图要靠人手工执行 `image_scheduler.py run`。

证据（今天在本 checkout 逐条复核）：

- `config/storyos.yaml:157` 写着 `runtime.continuous_host_loop: true`，但修复前全仓库没有任何代码读取它（`rg continuous_host_loop` 只命中配置文件本身）→ 死开关。
- `episodes/_system/runtime_dag.py`：WORK/WEB 且未显式 `--codex` 时，`scoped_model` / `scoped_codex` 步骤直接返回 `HOST_ACTION_REQUIRED_RC = 20`（HOST_WAIT），把执行权交回宿主。
- `episodes/_system/episode_runner.py` 本来就有出图分发逻辑（`GENERATE_IMAGES` / `RETRY_TECHNICAL_FAILURES` / `REPAIR_FAILED_IMAGES`），但 `story_os.py` 没有 `runner` 入口，只能按脚本路径手工调用；且全仓库不存在 `meta/runtime-runner-state.json`，说明 runner 从未真正跑过。
- 现实现场证据：`episodes/10_彼此的天上/03_雾中的另一座生活区/meta/image-workers/` 里帧 01 的两次 attempt（13:45 / 13:49）都来自手工启动的进程。

修复：

| 文件 | 改动 |
| --- | --- |
| `episodes/_system/episode_runner.py` | 抽出纯决策函数 `local_image_action(action)` 与执行函数 `run_local_image_action()`，`execute_cycle()` 复用它们，行为不变 |
| `episodes/_system/workflow_runner.py` | 新增 `continuous_host_loop_enabled()` / `host_loop_step()` / `advance_host_loop()`；DAG 返回 HOST_WAIT 且开关为真时，先执行本机可执行的图片动作，再恢复 DAG，结果写入 performance 与 checkpoint（步骤名 `HOST_LOOP`） |
| `episodes/_system/story_os.py` | 新增 `story_os.py runner <episode_dir> [--interval N] [--resume]`，转发到 `episode_runner.py`（仍走 `persistent_runner_daemon` 的单所有权锁与心跳） |

修复后的链路：

```
story_os.py run <episode> --full-auto
  → workflow_runner.execute
  → runtime_dag.execute  →  rc=20 HOST_WAIT
  → (continuous_host_loop=true) advance_host_loop
       本地可执行动作 → episode_runner.run_local_image_action → image_scheduler / batch_scheduler
       → 重新 runtime_dag.execute
  → 遇到宿主动作（CREATIVE_STORY / PREIMAGE_COMPILE / VISUAL_LOCK / RELEASE / 评审）立刻交回，rc 原样返回
```

边界（必须知道）：

- 只自动执行“本机图片执行层”的动作；Story、Preimage、Critic、Gate、Release 仍交回宿主，符合 AGENTS 的 runtime 路由规则。
- 循环上限 `HOST_LOOP_MAX_CYCLES = 12`；到顶就返回 HOST_WAIT，不会无限空转，也不会把宿主动作伪造成 PASS。
- 已做一次真实数据干跑：把 `episodes/10_彼此的天上/03_雾中的另一座生活区` 的 `meta`/`docs`/`prompts` 复制到 `.storyos/_verify_hostloop/`（跑完删除，不碰原目录）：`next_action.write()` → `VISUAL_LOCK / WORK`，`host_loop_step()` → `(False, 'VISUAL_LOCK')`，即遇到宿主动作立即交回，没有触发任何出图；该临时目录已清理。
- 仍未在真实新篇上从 `IDEA_LOCKED` 跑到 `PUBLISH_READY` 做整篇端到端验收（见第 6 节第 1 条）。
- 14:23 复核：`episodes/10_彼此的天上/03_雾中的另一座生活区/meta/runtime-runner-state.json` 已存在（status=HOST_WAIT、return_code=20、pid 3320、heartbeat 14:23:00），`meta/runtime/next-action.json` 也已重算为 `VISUAL_LOCK / WORK` → 修复 A 的链路已真实跑过一轮，不再只有离线干跑。

修复：

| 文件 | 改动 |
| --- | --- |
| `episodes/_system/image_model_policy.py` | 新增 `ARTIFACT_SAVE_COLLISION="PROVIDER_ARTIFACT_SAVE_COLLISION"` 与匹配模式（`failed to save generated image` / `os error 183` / `error_already_exists` / `当文件已存在时`），分类顺序放在 RATE_LIMIT 之后、BACKEND_5XX 之前 |
| `episodes/_system/image_artifact_collector.py` | 恢复根目录改为 `CODEX_HOME` 感知（`codex_home()` / `generated_images_root()`）；新增按 `call_id=` 的二级恢复；兼容路径补 `root / name` 探测 |
| `episodes/_system/image_scheduler.py`（无需改） | 该 code 不在 `NON_REGENERATING_FAILURE_CODES` 集合里，因此仍按“技术失败可重试”处理，不消耗每帧一次的内容返修额度 |

补充实测证据（EP003）：

P01 + P02

实际:
P01

结果:
身份锁定虚假通过

1. required_anchors 必须与执行引用集合对账；
2. 缺少任一 required anchor 时 Visual Lock fail closed；
3. 多人物场景优先保障角色身份引用。

- **"pid 存在"不再等于"Driver 活着"**。本轮实测到一个会被误读的真实状态：Driver 写完退出码后，解释器还要约 2 秒才真正离开进程表，这 2 秒里 `pid ` 与 `rc` 同时存在，任何"有 pid 就算在跑"的读法都会把它读成活的。修法是两条：**收尾时用一个原子写同时落 `rc` 并把 `pid` 清零**（`_finish`），以及**常驻进程另起守护线程每 15 s 写 `meta/runtime/driver-beacon.json`**，只有"该 pid 正在跳动"才判 `RUNNING`。
- 状态机与它各自的授权：`NEVER_STARTED` / `RUNNING`（pid 存活**且**有该 pid 的心跳）/ `ALIVE_NOT_BEATING`（pid 存活但没有心跳——可能是卡死的 Driver，也可能是 Windows 复用了这个 pid）/ `EXITED` / `ABNORMAL_DISAPPEARANCE`（没留下退出码就没了）/ `UNKNOWN`（进程表读不到）。心跳容忍窗 90 s，远大于 15 s 间隔，且心跳在独立线程上，因此 69 分钟的 PREIMAGE 步骤阻塞不了它。
- **`launch` 只在 `RUNNING` 时拒绝重启**，不再"只要 pid 活着就拒绝"。否则一个被复用的 pid 会把 Episode 永久钉死——这属于方案 §13 明令禁止的"绕过 fail-closed 检查"的反面：不能为了防双开而制造一个不可恢复的状态。**真正的双开防线仍是 owner lock**（`runner_state_store`，内核在进程被终止时释放），双开返回 rc=25，`interpret_rc` 有对应人话。
- **`recover` 只报告，绝不杀任何东西**：不杀 Driver、不杀 Codex，更不 `taskkill /IM codex.exe`（那会连带打死用户自己的 Codex 桌面后端）。恢复动作就是"再 start 一次"；孤儿 Codex 任务的结果由 P0-D 的 in-flight 领取，不销毁。该约束由 AST 扫描测试守住（`runtime_driver` 不得出现 `kill` / `terminate` / `TerminateProcess` / `taskkill` 名字）。
- **修掉一个会误导操作者的启动判定**：Episode 已在终点态时，Driver 会在 settle 窗口（3 s）内跑完并退出，旧写法把它报成 `NOT STARTED reason=EXITED_DURING_STARTUP`——即"启动失败"。真实含义是"启动成功且活已经干完了"。现在只要落了退出码就算 `started=True` 并附上 rc；只有"没留下退出码就没了"才是启动失败。

**P0-D Codex in-flight 领取（Gate D）**

新增 `episodes/_system/inflight_codex_task.py`：在**提交之前**把 `request_id` / fingerprint / stdin SHA / 截止时间落盘到 `meta/runtime/in-flight-codex.json`，重启后的 Driver 只问一个问题——"有没有一个我已经付过钱的任务，正好回答当前这个问题？"三个答案，没有一个是"默认再提交一次"：`ADOPT` / `WAIT` / `RESUBMIT`，全部 fail-closed 向 `RESUBMIT`。

- 领取校验按序拒绝：无结果 / 无 evidence / `request_id` 不符 / 非 `scoped_step`（**别的类型的产出不能给 scoped 步骤收尾**）/ `timed_out`（即便 rc 写成 0）/ rc 缺失 / **rc 非 0** / stdin SHA 漂移 / 输出缺失 / 不可解码 / 字节数不符（半截文件）/ 自身摘要不符。任何一项不成立都退化为 RESUBMIT，**永不 ADOPT**。
- **`WAIT` 不重新提交**：runner 的 `/v1/health` 新增 `inflight_request_ids`，只认正面报告；没有正面报告时用任务自己的截止时间兜底（宽限期内"没结果"可能是 runner 重启丢了在跑表，不等于任务死了）。只有"确认过期且没产出"才允许重跑。
- 接缝实测（`scoped_codex_worker.run_step`，把真实 Codex 调用接成会抛异常）：重启后的 Driver 走 `_attach` 领到旧结果并写回该步日志，返回 rc=0，**且没有任何第二次提交**。这条才是"Driver 重启不会把同一个 Codex 任务再发一次"的正面证据，而不是去看一个决策对象。
- 提交前的 in-flight 记录只在**收到结果**后才清除（`collected and request_id`）；本进程死在任务中途时记录保留，供下一次领取。

#### 12.6.2 W-103 修复设计：Candidate-aware Final Semantic Patch

**目标**：当 20 帧里只有少数 fresh candidate 需要重新确认时，只审 dirty roots + 必要 context，复用其他已验证的 SHA-bound review，不再默认重审 20 帧。

准备改动面：

1. `incremental_frame_review.py`
   - 把当前“只消费全体 accepted/locked”的 planner 扩展出 **candidate-aware plan**；
   - dirty roots = 当前 `REPAIR_READY` 且存在 fresh `current_candidate` 的帧；
   - context 使用现有邻帧算法：普通帧 ±1；结尾关键帧保留更宽 context；
   - LOCKED/PASSED context 继续使用 approved SHA，只作审查背景，**不得改变 Ledger 状态**；
   - 保持 `PATCH_LIMIT_RATIO=0.25`：20 帧最多 5 个 dirty root 才允许 patch；超过阈值自动 FULL。
2. `frame_semantic_review.py`
   - 抽取/复用现有 exception / continuation target-only apply 语义，形成普通 candidate patch apply；
   - target PASS 才 `review → promote → lock`；target FAIL 才走现有 repair/NEEDS_USER 语义；
   - context FAIL 只能让 patch 本轮 FAIL/升级 FULL，**不得直接解锁 context**，除非后续 FULL authority 明确重新判定；
   - 所有 source fingerprint、Frame Contract、candidate SHA 在 critic 前后必须一致。
3. `next_action.py`
   - 在 `complete_candidates && !all_locked → REVIEW_FINAL_PRODUCTION` 之前插入 candidate-aware plan；
   - `PATCH` → 新 `REVIEW_FINAL_PATCH`；
   - `FULL` → 保持现有 `REVIEW_FINAL_PRODUCTION`；
   - `NOOP` → 复用现有 review，不产生 Critic 调用。
4. `machine_action_executor / episode_runner`（如 action dispatch 需要）
   - 只增加 canonical action 接线，不复制 review 业务逻辑。

**必须 FULL 的安全回退条件**：

- Story / Storyboard / Visual Contract 全局 SHA 变化；
- 任一 dirty root 的 Frame Contract / source binding 无法证明 fresh；
- 无可复用 baseline review；
- dirty roots 比例 `> 25%`；
- deterministic near-duplicate / global source drift；
- patch context 自身出现无法在局部范围判断的跨段连续性冲突。

**W-103 验收**：

- 构造 `18 LOCKED + 17/18 REPAIR_READY` 时，`next_action` 不得返回 frames 1～20 的 FULL review；
- 只审 17/18 + 必要 context，18 个 clean frame review SHA 不变；
- context frame 永不被 patch apply 改 Ledger；
- 2/20 dirty 必须 PATCH，6/20 dirty 必须 FULL；
- Story/Storyboard/Visual/Frame Contract 漂移必须 FULL/fail-close；
- patch critic 中途 source drift 必须拒绝 apply；
- 目标性能：2 个 dirty roots 的真实 review wall **优先压到 3～8 分钟级**；该性能值先作为验收观测目标，不作为 Gate 造假 PASS。

#### 12.6.3 W-104 修复设计：FULL Review bounded fan-out + single-writer merge

**目标**：W-103 无法安全 PATCH、确实需要重审 20 帧时，避免一个 Critic 串行吃完整 20 帧；但不能因为并发破坏全局连续性和 W-71 的原子收口。

设计约束：

- 最大并发由唯一配置 `runtime.review.vision.max_inflight_final` 控制，当前为 **4**；按帧数自动 1/2/3/4 降档，标准 20 帧固定四路，不开放无限 review worker；
- shard 只产生**非权威 candidate**，任何 shard 完成时都不得写 Ledger；
- 每个 target frame 只属于一个 shard，context/anchor 可以重复附带但无写权限；
- 每个 shard 绑定同一份 frozen Story/Storyboard/Visual/Frame Contract fingerprint；
- 所有 shard 完成后，父线程执行：coverage 校验 → source drift 校验 → conservative merge；若局部已 FAIL 直接进入既有失败流，不额外启动 Closure；若局部全 PASS，再执行轻量 Global Closure（只读跨 shard 边界/首尾锚）→ 再次 source drift 校验 → W-71 批量预检 → FAIL 先处理 → PASS promote/lock；
- 缺 shard、重复 target、source fingerprint 不一致、任一 worker outcome unknown 时全部 fail-close，不允许“4 个 shard 里 3 个 PASS 就先锁”。

推荐第一版 shard 策略：

- 20 帧按连续区间固定切成 4 个 target shard：`01-05 / 06-10 / 11-15 / 16-20`；更短帧集按 1/2/3 自适应；
- 每个 shard 可附带左右邻帧作为只读 continuity context；
- Frame01、climax、Frame20 等全局 anchor 可作为只读 context 重复出现；
- near-duplicate / exact frame coverage 仍由 parent 一次性全局执行；
- 轻量 Global Closure 已正式接入：只复核 shard 边界、Frame01/Frame20 与 shard summary，专门检查 `identity / wardrobe / spatial-temporal / visual memory / narrative progression / ending payoff`，不重新细审 20 张。

**W-104 验收**：

- FULL 20 帧 target coverage 精确 20/20、无重无漏；
- 标准 20 帧 `shard_count=4`，`max_inflight_review <= runtime.review.vision.max_inflight_final` 且真实峰值可观测；
- shard 完成前 Ledger 0 mutation；
- 任一 shard FAIL/timeout/outcome unknown → 不得提前 LOCK；
- source drift → 整轮作废；
- 与当前单 Critic 对比，真实 20 帧 FULL wall 目标先压到 **≤10～12 分钟级**；
- 质量回归：同一固定 Golden/fixture 上 issue-code 命中能力不得低于现有单 Critic 基线。

#### 12.6.4 W-105 修复设计：Performance Session + Wait Attribution

**目标**：以后回答“这一篇用了多久”时，能同时给出真实 E2E wall、active machine/model wall、Host/人工等待、各 Review/生图占比，而不是把几天前的历史生产和今天的 repair 混成一个数字。

准备改动：

1. `episode_performance.py`
   - 保留现有 Episode 级历史 ledger，不回写历史；
   - 增加 execution session/run 概念：`run_id / reason(create|resume|repair_revalidation) / started_at / ended_at`；
   - 每个 session 单独计算 interval union；
   - active 类：`MACHINE_ACTIVE / IMAGE_PROVIDER_ACTIVE / CODEX_VISION_ACTIVE / PRODUCT_REVIEW_ACTIVE`；
   - wait 类：`HOST_WAIT / USER_DECISION_WAIT / ORPHANED_IDLE`；
   - `active_wall_seconds` 只统计 active union；`wait_wall_seconds` 分类别；`end_to_end_wall_seconds` 保留用户真实挂钟。
2. Review / Image / Driver 现有 producer
   - 不复制计时器，只在进入/退出既有动作时记录 lane span；
   - 新增 `review_calls / reviewed_frame_count / review_mode(FULL|PATCH) / repair_rounds / max_review_inflight` 聚合指标。
3. SLO
   - 现有 `total_wall_seconds` 继续作为历史/用户挂钟参考；
   - 当前执行效率 SLO 改看当前 session 的 `active_wall_seconds`，同时单列 `wait_wall_seconds`，禁止把 USER/HOST wait 偷算成机器耗时，也禁止把 wait 从 E2E 抹掉。

**W-105 验收**：

- 同一 Episode 的原始生产与 7 天后 repair-revalidation 可输出两个独立 session；
- active interval 重叠只计一次；
- IMAGE + REVIEW 并发时 resource time 可大于 active wall，但 wall 不重复相加；
- HOST_WAIT / USER_DECISION_WAIT 不进入 active wall，但必须进入 end-to-end wall；
- dangling span finalize 只能标 `CLOSED_AT_FINALIZE`，不能伪造 PASS（保持 W-09 语义）；
- 当前 W-02 能独立打印“本次修复 session”的 Review / Image / Wait 分布，而不是继续只显示历史 `11.68h`。
