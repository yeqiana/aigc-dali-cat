## 1. 理解、计划与风险

### 理解

核心问题是：已经完成的治理收敛，尚不能约束后续现场修复。紧急修复能够解决局部生产问题，却可能重新分出执行循环、增加隐含控制入口，使恢复、排查和验收成本继续上涨。

不能把所有新增文件视为膨胀。历史 attempt、Provider Receipt、审核证据和快照需要保留；需要减少的是重复的有效实现、不明确的控制入口和不一致的当前语义。

### 计划

按“现场保护 → 调度收敛 → 预算入口 → 状态解释 → 审核恢复 → 发布对账 → 真实回归”执行。每步独立验收，不以增加新版本、新框架或新状态机作为解决方式。

### 风险

- 两条调度路径具有不同的 Batch barrier、依赖和后处理规则，不能为了共用代码强行统一业务策略。
- 预算是执行控制，迁移覆盖入口时可能误增额度或阻断既有授权任务。
- 审核恢复必须绑定候选与合同，复用失效结论会造成错误放行。
- 实际发布不等于通过系统验收，不能反向补造 PASS。
- 当前方案引用的是核查时的现场状态，实施前必须刷新工作区、进程和 Episode 证据。

## 3. 目标与非目标

### 目标

1. 同类执行机制只保留一套有效公共实现，产线差异通过既有调用参数或回调明确表达。
2. 每个控制字段有清晰来源、优先级、作用域和生命周期，运行证据不得暗中承担配置职责。
3. 相同候选与合同的有效审核结果可恢复，不靠长对话维持进度。
4. 用户可以直接区分生成、审核、门禁、实际发布四类进展。
5. 每个修复都有对应行为验收；共享机制调整必须覆盖两条产线。

### 非目标

- 不新增框架、Runtime、第二状态机或新的治理平台。
- 不修改冻结 Story、Storyboard、Character Contract来迎合既有错误图片。
- 不改变已锁图片控制模型、图片模型与质量。
- 不删除历史证据、忽略媒体或用户未提交内容。
- 不自动追加预算、二次内容返修授权或推送 Git。
- 不把目录改名、文件拆得更多或文档数量作为治理成功指标。

## 4. 实施顺序

### S0：现场保护与最小基线

**动作**

- 读取当前入口、配置、Git状态及本集队列、账本、阶段、发布记录。
- 确认 scheduler 与 worker 是否在途；有有效生成时先让结果落盘，不启动竞争调度器。
- 从当前提交建立本次变更基线，精确记录已有用户改动。只修改本步骤必要文件。
- 在已有实施记录中填写步骤结果，不再建立平行治理报告系列。

**验收**：运行任务、待审帧、待决策帧和当前提交可对账；没有中断有效生成，没有重生有效成功帧。

### S1：调度执行机制重新收敛（优先级P0）

**目标文件**：`scheduler_core.py`、`image_scheduler.py`、`batch_scheduler.py`及已有调度行为测试。

**实现约束**

- 在现有共享执行层补齐动态派发与完成通知所需能力，迁回image路径的公共执行职责。
- 公共层负责任务运行、完成事件串行消费、运行资源释放；两条产线保留各自准入、Batch barrier和后处理策略。
- 降并发若属于两条路径共有策略，应抽成一处实现；若策略确有不同，必须明确参数和对应测试，不复制隐含规则。
- 保持最多3个图片worker及现有Logical Batch全局限制；不得叠加两个池突破上限。
- 一次完成后补位；同帧不重复派发；Ledger单写；依赖失败不阻塞独立任务。
- 共享替代路径通过后移除被替代的执行循环，不能留下两套可运行实现长期并存。

**验收**

1. 实际scheduler入口下，6个独立模拟任务峰值3在途，慢任务未完成时空位可补入新任务。
2. 测试同时覆盖image和batch入口，不只测试底层stream adapter。
3. Batch后处理必须等待其原始生成barrier终结，不能提前执行。
4. 技术失败按既有3→2→1语义降并发，成功帧不重生。
5. 中断恢复、依赖隔离、单写与同帧互斥维持原行为。
6. 如有已授权真实任务，用该任务trace验收，不额外生成无关图片。

**回滚**：停止新派发、等待在途落盘后回退本步骤代码；保留新增的真实生成与审核证据，不回滚账本到旧快照。

### S2：明确预算配置与例外授权（优先级P0）

**目标文件**：`raw_candidate_budget.py`及现有授权入口、预算测试；配置/Schema只在确定现有结构无法表达时做最小修改。

**动作**

- 列出预算现有完整解析顺序：全局固定值、推导默认值、Episode覆盖、在途预留、已提交候选。
- 将预算例外明确归类为“有授权来源的执行决定”，不再称为仅审计证据。
- 优先复用既有授权机制。统一读取与校验入口，输出实际生效值及来源；不建立第二套预算状态机。
- 既有override文件先兼容读取并验证，不直接删除；迁移时仅迁移已有有效授权，不扩大额度。
- 固定配置是否允许被Episode例外覆盖，必须形成唯一、可测试的优先级，不能由调用路径偶然决定。
- 计划阶段展示“可用额度/在途预留/待生成数”。不足时准确报告可执行范围与需要的决定，不停止无关审核。
- 错版prompt造成的消耗如实保留，不修改历史计数来制造额度。

**验收**：并发claim不超额、技术失败按现有规则释放预留、重复提交不重复计数；缺授权或非法覆盖无法提高额度；重启后解析结果一致；既有已授权任务预算不被静默改变。

### S3：统一并发状态与进度解释（优先级P1）

**目标文件**：两scheduler及已有plan/next-action/observability输出。

**动作**

- 明确“配置上限”“本轮有效并发”“当前在途数”“历史降并发记录”的不同职责。
- 明确adaptive_parallel是持久控制字段还是历史记录，只保留一种含义；若需兼容，集中转换，消费方不得各自解释。
- plan和运行摘要展示相同语义。不得把历史值1展示为当前实际并发，同时运行3个worker。
- 复用现有队列与trace生成摘要，不新增独立状态文件。
- 固定进度输出为：生成完成数、内容审核通过数、待审/待决策数、正式门禁结果、实际发布事实。

**验收**：同一queue分别进入两条合法路径时解释一致；重启后不会因历史字段无说明地改变并发；队列派发、进程与摘要能对账。

### S4：审核恢复与prompt防漂移（优先级P0/P1）

**目标文件**：实际prompt编译/入队入口、现有审核记录与恢复入口；实施前定位真实调用链。

**动作**

- 入队和派发前核对实际发送prompt的来源及其绑定合同。仅有当前SHA字段，不足以证明prompt内容来自当前分镜。
- 来源漂移时重新编译派生缓存；不回写冻结权威，不把旧attempt重新标成当前合同产物。
- 审核中间记录优先扩展已有review机制：绑定候选SHA、合同SHA、检查项、判定与未决项；不得另造审批状态机。
- 完成一个可记录的审核单元就落盘；恢复时先校验已有记录，SHA不变且证据有效则复用。
- 默认全图加关键区域检查；只有具体新疑点才追加检查。无法判断记待审/UNCERTAIN，不为凑PASS无限放大。
- 明确初审、正式语义审核与最终发布验收的不同职责，重复项读取有效证据；需要独立评审的角色继续独立，不伪装成用户批准。

**验收**：旧prompt+新合同的错配在发送前被检出；任一绑定SHA改变会失效相关审核；相同SHA恢复不无条件重审；不确定项不能promote；局部失败不阻断独立任务。

### S5：本集发布事实与正式证据对账（优先级P0）

**动作**

- 刷新04帧和实际发布版本事实，确认用户发布的具体图片来源；无法取得实际文件映射时明确待补。
- 保留用户实际发布事实，继续区分其与正式验收状态。不得伪造相邻阶段转换或补签用户批准。
- 经用户明确决定处理剩余硬合同问题；本方案不自动授予例外返修或例外接受。
- 通过现有官方审核、Preflight、Snapshot及transition流程补齐可真实完成的证据。
- 后补验证针对哪个资产版本必须写清，不能用后补修复版的通过记录代表此前已发布版通过。
- release字段、快照和实际文件只有在映射已核实后才能绑定。没有完整证据时保留未闭环状态。

**验收**：实际发布事实可追溯；候选、approved、publish、snapshot来源明确；仍不满足条件时准确报告未闭环，不能用“已经发布”替代门禁。

### S6：把收敛成果纳入真实回归（优先级P1）

**动作**

- 复用现有tests/system、调度测试和Golden注册体系，不建立新测试框架。
- 保留Windows短路径与双平台行为用例，避免只在本机长路径验证。
- 合格真实Episode满足既有准入并获策展确认后再注册Golden；registered=0或skipped不能算完成。
- 真实回归优先重放已有合同与证据，验证恢复和门禁，不默认重新生成图片。
- 若需推送或远端workflow执行，按实际授权进行；本地通过与远端通过分别记录。

**验收**：有非空合格样本真正执行回归；旧成功资产SHA不变；失效证据被拒绝；跨路径共享行为及发布版本映射可验证。

## 5. 防止本方案本身增加负担

- 本文只是实施计划，不是新增创作权威、运行规范或机器状态源。
- 每一步先说明替换哪段现有实现；新增能力必须同时说明旧入口如何退出或兼容。
- 能使用现有字段和记录就不新建文件；必须新增时明确权威/控制/证据/派生分类、消费者与生命周期。
- 不把同一规则手工复制到AGENTS、SKILL、START_HERE等多个入口。入口保留路由与引用，详细规则由对应现有权威维护。
- 历史实施记录可以保留，但当前状态应由既有汇总入口指向有效结论，不让读者靠逐篇续版推断。
