## 实际行为与边界

| 情况 | 处理 |
|---|---|
| 限流、超时、临时服务故障 | 有界重试，失败帧单独处理；成功帧保留 |
| 某帧不可继续但其他帧依赖满足 | 优先继续独立帧 |
| WORK/WEB 宿主动作 | 记录 HOST_WAIT 与可执行请求，不改为假审批或忙循环 |
| 图片已生成但账本提交失败 | worker lifecycle 保存 transaction id、PID、输出、终态 result 与 provider receipt；恢复时重新走 Ledger 的正常验证后再补 Queue，不重复生成 |
| 账本已成功但队列未写入 | 从 Ledger 当前 candidate 回放 Queue 的 `generated` 状态；不改 Episode stage |
| 调用已发出但没有 worker 终态 receipt | 标为 `interrupted_unknown`，不自动重试、不伪造通过；无依赖的兄弟帧仍可继续 |
| 无进度的成功退出 | 有界检测后能力等待，不能无限空转 |
| 正式阶段推进 | 仍由 canonical stage + 实际证据验收；不能用 warning 豁免 |

远端 Ubuntu/Windows CI 与 Qodana 容器尚未运行；官方已确认 Python Qodana 镜像类型，配置切换不等于扫描通过：[JetBrains Python linter 文档](https://www.jetbrains.com/help/qodana/python.html)。

原生 API 批次的统计现在只会在全部计划帧由该原生请求成功并提交账本时标记 `native_multi_image=true`；只要回退到单帧，即使最终图片齐全也只记为部分原生批次。调度器、公共 CLI 队列写入、WORK/WEB 导入和批次评审现在共享同一 OS 队列锁；并发时直接写入会得到 `QUEUE_MUTATION_BUSY`，可稍后重试，不能覆盖运行中的调度结果。P0 已补齐：任意崩溃后的 `running` item 会依据事务 journal、worker lifecycle、Ledger 和候选文件对账，只有确定成功/失败才自动落盘；未知在途调用保留 `interrupted_unknown`。Ledger 热路径（调度 begin/success/tech-fail 与 repair review）已收敛为进程内直调，不再为每帧启动两次解释器；子进程冷启动项关闭。仍需后续处理：共同调度层共享代码收敛，以及冻结剧集重新进入生产时的 SHA 校验。现有正式剧集、旧候选和用户暂存内容未作为本轮测试输入批量重写。
