# Story OS 生产效率实测审计报告

更新时间：2026-09-18  
范围：当前仓库已有测试、Runtime/Performance Ledger、真实 Episode 生产记录与性能回放证据。  
口径原则：只把可复核的真实运行数据称为“实测”；目标预算、Mock、Fixture、Replay 中未调用真实图片后端的数据不得冒充真实生产耗时。

---

## 一、结论

当前 Story OS **已经存在能够证明生产效率改善的真实记录**，其中最强证据集中在图片生产并发、单图延迟、批次成功率、Review 耗时和 Performance Ledger 口径修复。

目前最明确的实测结论：

1. 图片三路并发真实批次由 **314s resource time 压缩到 115s wall time**，达到 **2.73× speedup，约 91% 三并发效率**。
2. 本轮图片 backend overlap-aware wall 为 **1235s（20.6 分钟）**，对应 resource time **2777s（46.3 分钟）**，并发直接节省约 **1542s（25.7 分钟）**。
3. 成功图片延迟已经稳定在约 100 秒级：**avg 101.7s / median 101.5s / P90 118s**。
4. 当前非 archive Episode 的 batch metrics 已出现 **20/24 ≈ 83.3%** 的新产出率记录；历史 archive 基线为 **42/16 = 38.1%**。二者样本与阶段不同，因此只能说明“新样本明显改善”，不能直接宣称总体成功率提升了固定百分点。
5. 当前最大可控效率瓶颈已经从“生图”转移到 **Review Amplification** 和 **FULL Review**。历史 FULL Final Semantic 真实样本约 **20 分钟出 candidate / 28 分钟 worker 活跃**。
6. W-103 已实现 Candidate-aware Final Review Patch；W-104 已实现标准 20 帧最多 4 shard 的 FULL Review fan-out；W-105 已把 ACTIVE / HOST_WAIT / USER_WAIT / IDLE 拆开。代码与测试层已闭环，但 W-104 的真实 20 帧外部 Codex 四路 wall-time 仍缺最终实产证据。

因此，当前已经可以证明“**局部生产链效率明显提升**”，但还不能严谨宣称“**现在一篇标准 20 图 Episode 全自动只需要 X 分钟**”。最后缺的是新的、无人干预的完整 Episode E2E Active Wall 验收。

## 三、图片生产效率

### 3.1 并发已经产生明确收益

当前最有说服力的数据是：

- 三路真实图片批次 resource time：314s；
- overlap-aware wall：115s；
- speedup：314 / 115 ≈ **2.73×**；
- 相对理想三并发效率：2.73 / 3 ≈ **91%**。

这说明 Image Scheduler / Batch Scheduler 的并发不是“架构上支持”，而是已经在真实生产记录中产生可测收益。

更大的本轮样本中：

- resource time = 2777s；
- overlap-aware wall = 1235s；
- 节省 = 1542s = 25.7 分钟；
- 相对于串行 resource time，wall 缩短约 **55.5%**。

注意：resource time 是多个 worker duration 的累加，可以重叠；它不能直接和 Episode E2E wall 相加。

### 3.2 单图性能

成功图：

- avg：101.7s；
- median：101.5s；
- P90：118s。

平均值和中位数非常接近，说明当前成功样本没有被少数极慢图片严重拉高；P90 仍在约 2 分钟以内。当前图片 provider 路径可以按“成功图约 1.5～2 分钟/张”理解。

### 3.3 产出率

历史 archive 记录曾出现 42 requested / 16 succeeded = 38.1% 的低产出基线。当前非 archive Episode 的 batch metrics 汇总为 20/24 ≈ 83.3%。

这是一项积极变化，但不能写成“成功率从 38.1% 提升到 83.3% 已正式验收”，原因是两组数据不是同一 Episode、同一时间窗和同一实验条件。正式结论应写：

> 新生产样本产出率明显高于历史 archive 基线，但仍需一整篇修复后新 Episode 证明总体产出率和空批次率稳定。

## 四、Review 已成为主要效率瓶颈

已有真实记录表明：

- FULL Final Semantic：约 20 分钟得到 candidate，worker 完整活跃约 28 分钟；
- Frame Semantic：已有约 4.2 分钟和 14 分钟样本；
- Release Semantic 最重单轮：约 13.9 分钟。

因此当前性能瓶颈排序已经发生变化：

**第一：Review Amplification → 第二：FULL Review → 第三：图片 Provider 单图延迟。**

尤其是“只返修 1～2 帧，却重新审 20 帧”，其浪费已经可能大于重新生成图片本身。

## 五、性能优化已经实施到什么程度

### W-103 Candidate-aware Final Review Patch

已实现 `REVIEW_FINAL_PATCH`：

- ordinary REPAIR_READY fresh candidate 才允许 PATCH；
- dirty ratio <=25%；
- 非目标 sibling 必须 LOCKED 且 review/source SHA fresh；
- context 只读，不允许 PATCH 顺手改 Ledger；
- freshness/coverage 不满足自动回 FULL；
- 专项 82 passed；
- 与 W-105/Runner 合跑 119 passed。

这项优化的目标不是“少检查”，而是**避免重复检查已经有 fresh SHA-bound PASS 的帧**。

目标观测值：2 个 dirty roots 的真实 Review wall 优先压到 **3～8 分钟级**。该值目前仍是验收目标，不是已经取得的真实成绩。

### W-104 FULL Review bounded fan-out

已经实现：

- 标准 20 帧固定最多 4 shard：01-05 / 06-10 / 11-15 / 16-20；
- shard 只产生非权威 candidate；
- parent 做 exact coverage、source drift、conservative merge；
- 局部全 PASS 后才执行轻量 Global Closure；
- 最终 Ledger 仍由 single writer apply；
- 配置/专项 41 passed；
- Runner/Product Runtime 114 passed + 6 subtests；
- 当前 System/Platform 回归也已通过更大规模验证。

性能目标：真实 20 帧 FULL wall **<=10～12 分钟级**。

**当前缺口：尚缺一轮真实外部 Codex 20 帧四路并发 + Global Closure + Ledger apply 的 wall-time 证据，因此该性能目标不能提前算作实测成绩。**

### W-105 Performance Session + Wait Attribution

已经解决过去性能数据最容易误判的问题：

- execution session 独立；
- ACTIVE；
- HOST_WAIT；
- USER_WAIT；
- IDLE；
- resource time 与 active wall 分开；
- interval overlap 只算一次；
- Host/User wait 不进入 active wall，但仍保留在 E2E wall；
- dangling span 只 CLOSED_AT_FINALIZE，不伪造 PASS。

因此未来已经具备回答三个不同问题的基础：

1. 用户从开始到结束等了多久？
2. Story OS 机器/模型真正干活多久？
3. 中间有多少时间是在等 Host / 用户 / 外部条件？

## 六、不能当成真实生产效率的数据

仓库存在 Performance Replay：

- historical baseline image continue：233 分钟；
- target budget：95 分钟；
- reduction target：59.23%。

但该记录明确声明：

- image_backend_invoked = false；
- target_budget_is_not_simulated_wall_clock = true；
- target_budget is not a measured real production duration。

所以 **95 分钟只能作为 Release Objective / 性能目标，不能写成“Story OS 当前一篇生产耗时 95 分钟”**。

同样，pytest 的 930/1206 等 passed 数量和测试执行秒数主要证明回归稳定性，不等于内容生产吞吐量。

## 七、当前可以对外/对内使用的严谨结论

推荐表述：

> Story OS 当前已经通过真实生产记录证明图片并发调度有效：三路真实批次取得 2.73× 加速、约 91% 并发效率；本轮图片 backend 并发累计节省约 25.7 分钟，成功图平均约 101.7 秒、P90 约 118 秒。随着图片链路并发化，当前主要效率瓶颈已经转移到 Final Semantic Review。系统已经实现局部 Review Patch、最多四路 FULL Review fan-out，以及 Active/Wait 分离的性能账本，为下一轮完整 Episode E2E 性能验收做好基础。

当前**不要**表述：

> Story OS 已经可以在 95 分钟内稳定完成一篇。

也不要把历史 11.68h 和当前 20.6m 图片 wall 直接相减后宣称整体提速百分比，两者口径不同。

## 八、正式生产效率验收还缺什么

下一轮建议用一个全新的标准 20 帧 Episode 做一次**零人工干预、不中途改代码**的完整生产验收，从 `create --full-auto` 到 `PUBLISH_READY`。

必须自动产出以下指标：

| 指标 | 验收意义 |
| --- | --- |
| E2E wall | 用户真实等了多久 |
| active wall | 系统真正工作多久 |
| HOST_WAIT / USER_WAIT / IDLE | 非机器执行时间去了哪里 |
| image wall / resource | 图片并发收益 |
| image requested/succeeded/failed | 图片生产成功率 |
| image P50/P90 | Provider 稳定性 |
| max image inflight | 实际图片并发峰值 |
| review wall | Review 占比 |
| review FULL/PATCH calls | 是否消除了重复全审 |
| reviewed frame count | 实际审了多少帧 |
| max review inflight | W-104 是否真实吃到四路 |
| repair rounds | 一篇需要返修几轮 |
| first-pass yield | 首轮直接通过比例 |
| PUBLISH_READY | 最终是否完整闭环 |

建议连续跑 **3 篇真实 Episode**。第一篇用于发现并修复最后的观测/生产缺口；后两篇不得中途改代码，才能开始形成稳定生产 SLO。

## 九、最终判断

当前生产效率证据成熟度可分为：

- **图片并发效率：已具备强实测证据。**
- **图片单图延迟：已具备实测证据。**
- **图片新产出率：已有积极样本，仍需整篇验证。**
- **Review 瓶颈：已被真实数据定位。**
- **局部 Review 优化：代码/测试闭环，真实 wall 收益待新 Episode。**
- **FULL Review 四路并发：代码/测试闭环，真实 20 帧 wall 收益待验。**
- **整篇 Episode 生产效率：观测基础已具备，但缺新的标准化无人值守 E2E 样本。**

所以现阶段最准确的评价不是“没有生产效率数据”，也不是“整篇效率已经验收完成”，而是：

> **Story OS 已经进入“局部效率有真实证据、整篇效率等待标准化 E2E 验收”的阶段。**

下一步不应继续堆更多性能 Mock，而应该直接把 W-103/W-104/W-105 带进新的真实 Episode，连续记录 3 篇，形成第一版 Story OS Production SLO Baseline。
