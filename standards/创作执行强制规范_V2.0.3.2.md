# Story OS V2.0.3.2｜创作执行强制规范

> 身份：`standards/制作规范_正式版.md` 的 active subordinate execution contract。
> 不建立第二状态机；只把既有 Story Lock / Visual Lock / Release 的创作要求变成可失败的证据门禁。

## 1. Story Lock：先可理解，再生产

V2.0.3.2 新篇在 Story Lock 前必须存在 `meta/story-semantic-review.json`，且由独立 Codex session 审查。

硬要求：

1. 主角、到场原因、个人代价必须明确。
2. 一篇只能有一套可统一解释主要现象的核心异常机制。
3. 因果链必须成立：现实目标 → 规则/铺垫 → 有意义的选择/违反 → 直接后果 → 被迫继续行动 → 高潮选择/代价 → 结果 → 余波。
4. “找到人 / 门打开 / 怪物出现 / 照片变化”只能是高潮前置，不得单独作为高潮。
5. 高潮至少兑现：选择、代价、关系变化、规则兑现、身份翻转、不可逆后果之一。
6. 终局必须重新解释至少 3 个前文具体事实；禁止靠结尾突然增加一套新机制伪装反转。
7. 任意连续 5 张至少有一次新证据、因果转折或认知升级。
8. 执行删图测试：删掉后不影响因果、理解、悬念、可信度或必要空间过渡的帧，应合并或删除。
9. 独立 Critic 必须完成五句盲复述；核心机制或高潮需要靠“可能/大概/不清楚”才能解释时，不得 PASS。
10. 传播评分不能替代语义门禁。

Full-auto 允许自动修故事一次；第二次独立 Critic 仍 FAIL 时停止，不得 delegated Story Lock。

## 2. Visual Lock：默认 M00 必须真的进入生成请求

用户未明确指定其他风格时，继续解析：

`M00｜MP4 × 网吧 × 流水席旧数码质感校准版`

但 V2.0.3.2 不再只锁 Profile 文件：

`resolve profile → compact visual contract → 每次正式 image request 注入 → 三张真实性校准实际视觉审查 → Visual Lock`

三张校准必须由独立视觉 Critic 对实际图片逐项确认：

- visual_profile_match
- reality_first
- ordinary_life_density
- available_light
- unposed_capture
- not_cinematic
- causal_imperfection

不能因为提示词写了 M00 就判图片通过。

`capture_style` 参考只能来自：
- 已通过的三张 calibration；
- 明确登记并通过的 capture-style reference。

普通刚生成、尚未批准的帧禁止反过来当 `capture_style`，避免错误风格自我放大。

## 3. 字幕最终排版硬规则

字幕仍遵守最终视觉规范。

新增不可违反规则：

> 字幕换行后，如果第二行不存在中文、英文或数字，只有标点符号，则整行直接舍弃。

例如：

```text
昨天我明明已经把它锁进柜子里了
。
```

最终必须渲染为：

```text
昨天我明明已经把它锁进柜子里了
```

不把标点搬回第一行，不保留孤立标点行。

V2.0.3.2 新篇正式字幕必须通过 `episodes/_system/subtitle_layout.py render-all` 生成 publish 图，并产生 `meta/subtitle-layout-audit.json`。PUBLISH_READY 会验证该审计及输出 SHA。

## 4. 状态机不变

仍只有：

`IDEA_LOCKED → STORYBOARD_LOCKED → VISUAL_CALIBRATED → PRODUCTION_PASSED → PUBLISH_READY → PUBLISHED → DATA_REVIEWED`

本规范新增的 review/audit 文件全部是 evidence，不是第二状态源。
