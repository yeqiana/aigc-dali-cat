- 日期：2026-09-14

## 0. 先明确一个正确的基线：并行的粒度是「步内」，不是「步间」

DAG 六个步骤（`INCREMENTAL_PLAN → CREATIVE_STORY → PREIMAGE_COMPILE → VISUAL_LOCK → PRODUCTION → RELEASE`）**步间严格串行，这是有意设计，不是缺陷**。证据：

| 证据 | 位置 |
|---|---|
| 纯 `depends_on` 依赖链 | `runtimes/runtime-dag.json` |
| 串行节点独占一个 wave | `runtime_scheduler.py:58-60` `candidates = [serial[0]] if serial else eligible` |
| DAG 以 `max_workers=1` 驱动调度器 | `runtime_dag.py:247` |
| 每轮只消费一个节点 | `runtime_dag.py:255` 只取 `wave["dispatch"][0]` |
| 实测峰值并发 | `node-execution.jsonl`：四个步级节点峰值均为 **1** |

**真正发生的并行在步内**：

| 机制 | 位置 | worker | 实测 |
|---|---|---|---|
| 帧合约并行编译 | `frame_contract.py:585-590` | `runtime.workers.derived` = 6 | 峰值 6 ✅ |
| 生图并行 | `image_scheduler.py` / `production.max_inflight_images` | 3 | trace 中 5 对重叠 ✅ |
| release 预备车道 | `runtime_dag.py:238` 后台线程池 | 1 | 本集 0 span |

> **取证注意**：帧合约的并行证据写在 `meta/runtime/node-execution.jsonl`（`runtime_node_execution.record`），**不是** `meta/runtime/trace-events.jsonl`。只扫后者会得出"没有任何重叠"的错误结论。**且该 ledger 的时间戳精度只有秒级**（`runtime_node_execution.py:11` `timespec="seconds"`），因此并发度测量是量化的，只能定性。

## A 类：配置声称的并行度 > 实际发生的

### A1 · `runtime.workers.authority: 4` 的并行路径在生产不可达

**配置**：`config/storyos.yaml` → `runtime.workers.authority: 4`
**机制**：`preimage_protocol.execute_local(ep, _worker, max_workers=workers)` —— 4 个 PREIMAGE authority 任务进 `ThreadPoolExecutor`

**取证**：
- 调用点 `runtime_dag.py:371` 位于 `elif s.step_id=="PREIMAGE_COMPILE":`（`runtime_dag.py:362`），该分支的前置条件是 `runtime_dag.py:339` 的 `if active_runtime in {"WORK","WEB"} and not codex:` **为假**
- `runtime_router.detect()` 返回 `config runtime.preferred_runtime`（`runtime_router.py:158`），实测输出 `('WORK', 'config runtime.preferred_runtime')`
- 生产入口 `episode_runner.py:155` 调用 `runtime_dag.execute(episode)` —— **不传 `codex` 参数**，故 `codex is None`
- 代入：`"WORK" in {"WORK","WEB"} and not None` → **True** → 恒走 host 动作分支，`elif` 永不进入

**结论**：该 4-worker 路径仅在 `STORY_OS_RUNTIME=CODEX` 环境变量覆盖时可达（`runtime_router.py:82-83`）。

**影响**：`runtime.workers.authority: 4` 与实际发生的并行度无关。任何基于该值推断"生图前有 4 路并行"的判断都是错的。

**补充（重要，勿误读为"这 4 个工作没做"）**：这 4 个任务是**做了的**，只是执行者换成了 host。走 `:339` 分支 → `product_runtime_adapter.build_preimage_requests`（调用点 `product_runtime_adapter.py:184`）。该函数 `:258-262` **一次遍历全部未完成任务，为每个任务发一个 request**，故一个 DAG pass 内 4 个请求同时发出；host 完成后回调 `complete_preimage_task`（`:283`）校验 candidate 并置 `COMPLETED`。

真实剧集 `meta/runtime/preimage-task-state.json` 证据：4 个任务全部 `COMPLETED`，各带 `request_id`，时间戳为 14:13:27 / 14:13:27 / 14:13:27 / 14:13:28。

**因此准确的结论是**：本地 4-worker 线程池从未启动；同样的 4 个工作被**委托给 host**，且从时间戳看 host 是并发完成的。最终结果形态相近（4 个 disjoint scope 并行产出 + 一次原子提交），但**控制它的是 host 侧调度，不是这个配置项**。

**诚实边界**：仓库内证据只能证明"4 个任务在 1 秒内全部 COMPLETED"，这与宿主并发执行一致，但 host 侧行为不在本仓库内，无法直接验证。设计本身是支持并行的 —— `product_runtime_adapter.py:299-300` 注释明确："The fourth independently finalized candidate releases only the serial authority commit."

**待定**：这是设计意图（并行改由 host 承担）还是配置漂移，需要产品判断，本文档不预设结论。无论哪种，`observed_preimage_parallelism_peak` 都只度量本地线程池那条路，**host 侧的并发无任何本地度量**（见 B1）。

### A2 · `runtime.parallel.authority_enabled` / `derived_enabled` 是死标志

**配置**：`config/storyos.yaml` → `runtime.parallel: {"authority_enabled": true, "derived_enabled": true}`

**取证**：全仓 `.py` 搜索这两个键，**唯一命中是 `storyos_config.py:155`**：

```python
for key in ("runtime.parallel.authority_enabled", "runtime.parallel.derived_enabled", "runtime.preimage_parallel_enabled"):
    if not isinstance(get_path(cfg,key), bool): errors.append(f"{key} must be a bool")
```

即：**只做 `isinstance(..., bool)` 类型检查，没有任何执行路径读它们的值。** 把它们改成 `false` 不会改变任何行为。

**对照**：同组的第三个键 `runtime.preimage_parallel_enabled` **有真消费者** —— `frame_contract.py:585`：

```python
if storyos_config.get_path(storyos_config.load_config(),"runtime.preimage_parallel_enabled",False):
    with cf.ThreadPoolExecutor(max_workers=workers,thread_name_prefix="storyos-frame") as pool:
```

**影响**：三个并列的开关里，两个无效、一个有效。这个不对称极具误导性 —— 看到 `parallel.authority_enabled: true` 会以为 authority 并行受它控制，实际上它什么都不控制。

### A3 · 图像 provider 配置里的 codex 并发声明与生效值不一致

**现象**：同一个概念（codex 订阅模式的并发上限与自适应阶梯）在**两个文件**里各写了一份，值不同，而只有一份被读取。

| 字段 | `config/agent_runtime/codex-subscription-batch.json`<br>（**实际被读取**） | `config/providers/image-provider-runtime.json`<br>`codex_subscription` 段 |
|---|---|---|
| `enabled` | true | true |
| `logical_batch_size` | 5 | 5 |
| 并发上限 | `max_inflight_codex_images` = **3** | `max_inflight_logical_images` = **5** |
| 自适应阶梯 | `adaptive_concurrency_steps` = **[3,2,1]** | `adaptive_concurrency_steps` = **[5,3,1]** |

**取证**：
- 生效方：`codex_subscription_batch_runtime.py:10-17` 的 `load()` 读的是 `agent_runtime.codex_subscription_batch.config`，实测解析为 `config/agent_runtime/codex-subscription-batch.json`；`adaptive_steps()` 在 L35 读 `adaptive_concurrency_steps`，`max_inflight()` 在 L29 读 `max_inflight_codex_images`
- 失效方：`max_inflight_logical_images` 全仓 `.py` 引用数 = **0**
- `image-provider-runtime.json` 确实被 `image_provider_runtime.py:34` 读取该段，但**只读 `.get("enabled")`**（L39、L91），不读并发数与阶梯
- **且键名不同**：`max_inflight_logical_images` ≠ `max_inflight_codex_images`。即使有代码去读 image-provider-runtime.json 的该段，键名也对不上

**影响**：`config/providers/image-provider-runtime.json` 的 `codex_subscription` 段是一个**过期的重复副本**。它读起来像"codex 可并发 5、阶梯 [5,3,1]"，而系统实际按"3、[3,2,1]"运行。

**修正说明**：本文档早前的口头表述曾把 `[5,3,1]` 称为"死字段"，该表述**不准确**。准确说法是：**键有活消费者，但消费者读的是另一个文件里的另一个值**。自适应阶梯机制本身是实现了的、有测试的，问题只在于这个副本文件没跟上。

## B 类：机制存在，但无生产观测

### B1 · `observed_preimage_parallelism_peak` 零生产证据

`preimage_protocol.execute_local` 会返回 `observed_preimage_parallelism_peak`（measurement_method: `active_worker_enter_exit`），并被 `runtime_dag.py:380` 写进 step note。

**取证**：
- 全仓该标识符只出现在 `preimage_protocol.py` 与 `tests/system/test_preimage_parallel_runtime.py`
- 真实剧集 `meta/runtime-dag-state.json` 的 `PREIMAGE_COMPILE` 行 note 中不含 `parallelism`
- 该并行路径（见 A1）在生产不可达，故无观测是**自洽的**

**附带**：这套机制的测试质量很高，含反向断言。`test_preimage_parallel_runtime.py` 有 5 条用例覆盖原子提交、STALE 拒绝、失败零写入，其中 `test_single_worker_never_counts_queued_work_as_parallel` 断言 `peak == 1` —— 专门防止"把排队当成并行"的假阳性。**测试覆盖不等于生产验证**，这是 A1 值得优先处理的理由。

### B2 · `production_plan` 的并发规划无生产消费者

### B3 · `runtime_resource_manager` 在生产只被喂 `max_workers=1`

`runtime_resource_manager` **已接线**（`runtime_scheduler.py:55,61`），但：

- DAG 调用形式为 `runtime_scheduler.schedule(node_contract, completed=..., max_workers=1)`（`runtime_dag.py:247`）—— **不传 `resource_snapshot`**
- 于是 `runtime_scheduler.py:55` 执行 `normalize(None, max_workers=1)`，配额模型看到的容量恒为 1
- 唯一传真实快照的调用方是 `production_plan.py:26`，而它无生产消费者（见 B2）

**影响**：`runtime_resource_manager` 的配额/容量模型在生产中不参与任何决策。`runtime.workers.review: 3` 的唯一消费者也是 `production_plan.py:21`，同样不在生产路径上。

## D 类：生图前重复请求 churn —— 7 次轮间失效，0 次由自身提交解释

本节回答一个具体问题：`天界普通女生的一天` 一共发了 9 轮 PREIMAGE 请求，**有几轮是真需要重做，有几轮是被无关变更误伤**。

### D0 · 结论先行

**0 轮能由 PREIMAGE 自己的产出解释。** 7 次轮间失效，每一次都是由 `meta/story-gates.json` 的**整份文件哈希变动**触发，而 4 个 PREIMAGE 任务只拥有这份文件 50 个 scope 中的 10 个。

### D2 · 三个判定（全部可复现）

**判定一：轮间唯一在动的输入是 `story-gates.json` 的整份哈希**

快照记录 6 个被哈希的输入（`preimage_authority_snapshot.hashes()`）。跨 8 个有效轮次：

| 输入 | 轮间变动次数 |
|---|---|
| `story_gates`（整份 `meta/story-gates.json`） | **7 / 7** |
| `story_lock`（`gates["story"]` 子集） | 0 / 7 |
| `character_contract` | 0 / 7 |
| `world_identity` | 0 / 7 |
| `runtime_request` | 0 / 7 |
| `visual_profile` | 0 / 7 |

→ 没有任何一轮是被 story lock、角色合约、世界身份或 runtime request 的变更触发的。

**判定二：每一次失效都不是"我们自己写脏的"**

`authority_commit.commit_transaction` 记录的 `input_sha = 提交时文件实际哈希`、`output_sha = 写入后文件哈希`（`authority_commit.py:46-47,67`）。两者都是整份 `meta/story-gates.json` 的 sha256。比对结果：

| 提交 | `input_sha` == 上一轮的 `story_gates`？ | `output_sha` == 下一轮看到的 `story_gates`？ |
|---|---|---|
| 22:56:27 | ✅ 全 64 位相等（对 #2） | ❌ 对 #3 不等 |
| 10:20:59 | ✅ 全 64 位相等（对 #3） | ❌ 对 #4 不等 |
| 10:55:38 | ✅ 全 64 位相等（对 #4） | ❌ 对 #5 不等 |
| 14:13:28 | ✅ 全 64 位相等（对 #9） | （末轮） |

**4/4 的 `input_sha` 精确匹配说明链路本身自洽；3/3 的 `output_sha` 不匹配说明：我们自己提交写完文件之后，文件又被别人写了一次，才有下一轮。**

加上 14:13:28 最后一次提交（写出 `85359db5605f`）之后，文件在 **14:40:05** 又被写了一次，当前值是 `8fa98a6c97f3`。这次写入发生在整个 `meta/` 最后一次活动（14:16:18）之后 24 分钟，是孤立的，**来源未能定位**。

**判定三：被哈希的粒度和被拥有的粒度不匹配**

- `preimage_authority_snapshot.hashes()` 对 `meta/story-gates.json` 取**整份文件**的 sha256
- `preimage_task_contract.TASK_SPECS` 里，4 个任务声明的 `authority_scope` 合计只有 **10 个** scope（`character.finalize`；`visual.environment_contract`、`visual.frame_directives`；`visual.world_identity`、`visual.world_state`、`visual.temporal_continuity`、`visual.wardrobe`；`visual.narrative_core`、`visual.shot_progression`、`visual.capture_grammar`）
- 该文件实测有 **50 个** scope

→ **任何一个非 owned scope 被写，都会让 4 个任务同时失效。** 这与 P2 修复属同一类缺陷（过宽哈希口径），只是 P2 的问题在 `meta/runtime-checkpoint.json`，这里在 `story-gates.json`。

### D3 · 因果链

```
pass k    PREIMAGE_COMPILE → next_host_step → PREIMAGE_TASK_SET → 发 4 条请求（HOST_WAIT）
          host 完成 4 个任务 → commit_transaction 写 10 个 owned scope → 重建 committed snapshot
pass k+1  PREIMAGE_COMPILE → PREIMAGE_VERIFY → rc=0
pass k+2  VISUAL_LOCK      → host 动作写 visual.calibration（非 owned scope）
                             → story-gates.json 整份哈希变化
pass k+3  PREIMAGE_COMPILE → committed snapshot 判定 STALE（stale() 比对整份文件哈希）
                           → 重新发 4 条请求，新 snapshot_id     ⟲ 回到 pass k
```

**代码上可指认的写入者（都在 VISUAL_LOCK 路径上，写的都是非 owned scope）：**

| 位置 | 写入的 scope | 是否必然改字节 |
|---|---|---|
| `visual_lock_baseline_gate.py:96-102` `_mark_baseline_pass()`，由 `approve()` `:225` 调用 | `visual.calibration.items[role=ordinary_baseline]` | **是** —— 把 `asset_path`/`sha256`/`decision` 从空值填成实值 |
| `visual_lock_v21.py:332-350` `prepare()` | `visual.calibration`（含 `items`） | 视当前状态而定 |

**时间戳吻合**：`VISUAL_LOCK_BASELINE_REVIEW` 的 3 次 PASS 中，`23:03:02` 与 `09:34:23` 两次**正好落在 #2→#3 窗口内**（#2 的 commit 在 22:56:27；此后 VISUAL_LOCK 于 23:03 写下标定项，紧接着 09-14 10:18:24 就出现了 #3 的新快照）。

### D4 · 诚实边界（哪些话不能说）

1. **"0 轮"指的是"0 轮能由 PREIMAGE 自己的产出解释"**，不是"0 轮被证明是无关 scope 误伤"。存活证据只能证明"文件的整份哈希变了，且不是我们写的"。要证明变更落在非 owned scope，需要逐 scope 的历史快照 —— 而快照文件每轮被覆盖，且该剧集**未被 git 跟踪**（`git ls-files` 未命中），因此**历史内容不可恢复**。
2. **未能现场复现写入**：`visual_lock_v21.prepare()` 在沙箱副本上**失败关闭**（`ValueError: Resolved Frame Contract must PASS first: frame 08..15 resolved contract stale`），没有写文件；沙箱里 host 不在，`runtime_dag.execute()` 连续 6 个 pass 全部停在 `rc=20`、零写入，无法驱动完整回路。因此 D3 的写入者指认是**代码可达性 + 时间戳吻合**，不是现场观测。
3. **#6–#9 窗口内的写入者未定位**：这几个窗口内没有任何命名 span 开启。
4. **`HOST_ACTION_VISUAL_LOCK` 是一个从未闭合的 span**（09-13T12:05:15 开启，状态 `RUNNING` 至今）。由于 `begin_named_span` 按名去重，此后每一次 VISUAL_LOCK host 动作都复用它、**不再产生新的命名 span**。所以"窗口内没有命名 span"不等于"窗口内什么都没发生"。
5. **可能还存在第二个独立的重新请求触发器**：`next_host_step`（`product_runtime_adapter.py:122-123`）在 `handoff_valid` 为假时也会返回 `PREIMAGE_TASK_SET`，**不要求快照 stale**。本次未能区分 9 轮各自由哪个分支触发。

### D5 · 连带发现

**当前剧集处于"帧合约索引与 story-gates.json 不一致"的状态** —— 沙箱上 `visual_lock_v21.prepare()` 报 `frame 08`–`frame 15` resolved contract stale。这是同一 churn 的直接后果：14:40:05 那次未定位的写入改动了帧合约依赖的输入，而索引没有重建。也就是说 **VISUAL_LOCK 现在无法推进**，除非先重建帧合约索引。

### D6 · 修复方向（三选一，需产品判断，本文档不代做）

| 方案 | 做法 | 代价 |
|---|---|---|
| **收窄哈希口径**（推荐） | `preimage_authority_snapshot.hashes()` 不再对 `story-gates.json` 取整份哈希，改为只哈希 4 个任务 owned 的 10 个 scope（与 `TASK_SPECS` 的 `authority_scope` 对齐） | 需保证 scope 集合与 `TASK_SPECS` 同源，否则会漏判真变更 |
| **加屏障** | 让写非 owned scope 的路径（`visual_lock_baseline_gate._mark_baseline_pass` 等）在 PREIMAGE 未提交时拒绝写入，或写后主动重建快照 | 挡住的是症状；且要枚举所有非 owned 写入者 |
| **接受 churn** | 不动，靠 host 侧幂等（candidate 可复用）吸收重复 | 每次仍要重新走一遍 host 往返；本次 17/33 条请求白发的成本是实付的 |

> 无论选哪个，`observed_preimage_parallelism_peak` 等本地度量都不受影响（该路径在生产不可达，见 A1）。
