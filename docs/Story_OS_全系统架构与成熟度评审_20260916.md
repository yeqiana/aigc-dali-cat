# Story OS 全系统架构与成熟度评审

> 审计日期：2026-09-16  
> 审计分支：`story-platform-v3`  
> 审计基线 HEAD：`3d4553c`（`fix: close visual lock retry and error isolation gaps`）  
> 性质：架构审计 / 生产闭环评审 / 后续治理路线图  
> 说明：运行中的 Episode 会持续产生 runtime / receipt / queue 等文件，因此本文将“系统架构事实”与“单次运行快照”分开描述。

## 一句话结论

**Story OS 的“造片生产线”已经基本形成，真正缺的不是继续堆新的 Phase 或重写生产内核，而是建立一个统一的 V3 Platform 控制面，让它能够稳定地观察、解释、调度和治理已经成熟的 Production Kernel。**

换句话说：

> **不要重写 `episodes/_system`。让 V3 Platform 去控制、观察、调度 Production Kernel，而不是把 Production Kernel 再写一遍。**

## 总览

| 区域 | 当前真实状态 | 成熟度判断 | 主要缺口 | 后续方向 |
|---|---|---|---|---|
| Production Kernel / 生产内核 | 已实际承担 Story → Visual Lock → Image → Review → Repair → Release 主生产流程 | ✅ 高 | 状态投影过多、部分依赖物化时序绕、Full Auto 遇候选池耗尽仍会停人工 | 收敛状态、补 `DEGRADED_PASS`、强化 Resident Driver |
| Runtime DAG / 调度 | 已具备分段执行、复用、恢复、SHA 校验、runtime ownership | ✅ 较高 | 复合 legacy step 仍串行；部分阶段先失败再补依赖 | 先物化依赖，再验证；逐步降低 legacy composite step |
| Image Scheduler / 图片调度 | 3 并发、continuous first-completed、单 Ledger Writer、技术失败隔离 | ✅ 较高 | Visual Lock 内容失败耗尽后策略仍偏“停下来问人” | 有界降级通过 + 更清晰故障分类 |
| Full Auto / 全自动 | 已能自动推进大部分生产链 | ⚠️ 中高 | 本质仍是“自动到需要人工为止”，不是稳定 Resident Driver | 收敛人为阻塞条件，补自动降级和统一 Driver |
| Evidence / 可追溯证据 | Episode state、Ledger、receipts、effective config、SHA、execution capsule 等较完整 | ✅ 高 | 文件过多，机器懂、人和 Console 难读 | 建立统一 `RuntimeStatusSnapshot` 读模型 |
| V3 Platform | Event/Trace/Artifact、Workflow、Agent、API、Repository、Redis/MySQL 等主体能力存在 | ⚠️ 中高 | 未真正成为生产 authority / control plane | 先只读接管，再控制调度，再做持久化权威 |
| Agent Platform | Registry / API / Runtime 等骨架和实现存在 | ⚠️ 中 | 部分 Execution 仍内存态，Production Kernel 未真正依赖 | Repository 化 + 与 Kernel 执行桥接 |
| Memory / Experience | Story DNA、Similarity、Advisor、Failure Memory、Experience 概念均已存在 | ⚠️ 中 | 还不是统一长期记忆，下一次生产决策依赖度低 | 统一 Experience Store，真正参与 pre-production 决策 |
| Console / 多任务监控 | 已具备足够底层事实 | ⚠️ 中 | 没有一个统一读模型，前端若直接解析各种 JSON 会越来越乱 | `RuntimeStatusSnapshot` → Platform API → Console |
| Git / 运行资产治理 | 源代码、Episode 资产、运行痕迹目前混在同一工作树 | ❌ 风险较高 | 跑批期间工作区持续 dirty，不利于提交、回滚、并行 Episode | 运行资产与源代码生命周期分层 |

# 一、当前 Story OS 的真实总体架构

当前系统不能简单理解为“V3 已经替换 V2”。实际更接近：

```text
┌──────────────────────────────────────────────┐
│                 V3 Platform                  │
│                                              │
│  API / Agent / Workflow / Event / Trace      │
│  Artifact / Memory / Repository / Console    │
│  MySQL / Redis / Governance                  │
└──────────────────────┬───────────────────────┘
                       │
             观察 / 投影 / 部分编排
                       │
                       ▼
┌──────────────────────────────────────────────┐
│          Production Kernel / 生产内核        │
│             episodes/_system                 │
│                                              │
│ Runtime Request                              │
│ Story / Character / Environment Contracts    │
│ Runtime DAG                                  │
│ Visual Lock                                  │
│ Image Scheduler                              │
│ Production Ledger                            │
│ Review / Repair / Release                    │
│ Episode State / Evidence / Resume             │
└──────────────────────┬───────────────────────┘
                       │
                       ▼
┌──────────────────────────────────────────────┐
│              Episode Assets                  │
│ story / storyboard / prompts / images        │
│ receipts / contracts / runtime evidence      │
└──────────────────────────────────────────────┘
```

最准确的描述是：

> **V2.x Production Kernel + V3 Platform Control Plane 正在包住它。**

V3 Platform 已经不是 PPT 或纯设计，它有大量真实实现；但真正掌握生产“方向盘”的，当前仍然是 `episodes/_system` 中的 Production Kernel。

---

# 二、谁才是当前生产事实权威

当前真正的生产 authority 仍然位于 Episode 生产内核，而不是 Platform 数据库。

核心权威包括：

- `meta/episode-state.json`：唯一机器阶段事实源；
- Production Ledger：图片与生产事实的单写权威；
- `meta/runtime-request.json`：绑定后的用户生产请求；
- Story / Character / Visual / Frame 等 Contract；
- machine gate / evidence gate；
- Runtime DAG；
- Image Scheduler；
- provider receipt / SHA / effective-config 等证据。

`runtime-dag-state.json`、checkpoint、runner state 等都属于**恢复证据或执行投影**，不应该成为第二状态机。

这点实际上是当前系统非常重要的优点：Production Kernel 的 authority 边界已经比较清楚。

问题不是 authority 不存在，而是**围绕 authority 的投影文件越来越多**。

# 三、一句话入口到成片的真实生产链

当前主入口：

```text
python episodes/_system/story_os.py create "<用户请求>" --full-auto
```

实际链路可以概括为：

```text
User Request
   ↓
Runtime Request
   ↓
Concept / Story Intent
   ↓
Episode Create
   ↓
Story Lock
   ↓
Character / World / Environment / Narrative Contracts
   ↓
Storyboard
   ↓
PREIMAGE
   ↓
Visual Lock
   ↓
Image Scheduler
   ↓
Batch Production
   ↓
Vision Review
   ↓
Repair / Canonical Repair Lane
   ↓
Production Passed
   ↓
Release Candidate
   ↓
Publish Ready
```

`production_orchestrator.run_full_auto()` 的定位是“组合现有模块”，而不是建立第二条生产链。它本身不应该重新实现生图、Ledger、Visual Lock 或状态机。

这一点设计方向正确。

# 四、Production Kernel 已经达到什么程度

## 4.1 已经具备生产级特征

当前 Production Kernel 已经具备以下能力：

1. **唯一阶段事实源**：`episode-state.json`；
2. **Runtime DAG**：支持阶段拆解、恢复和复用；
3. **SHA / 输入输出哈希**：用于判断证据是否漂移；
4. **Execution Capsule / Prompt Package**：派生缓存与作用域执行；
5. **Provider Receipt**：记录外部执行事实；
6. **Production Ledger 单写**：避免图片生产并发造成双权威；
7. **图片连续补位调度**：`continuous_first_completed=true`；
8. **图片并发 3**：并发属于 Image Scheduler，不属于 Runtime DAG 的复合 legacy step；
9. **技术失败与内容失败逐步分离**；
10. **技术重试不占内容返修预算**；
11. **Resume / Reuse**：有效证据不重复做；
12. **Runtime Ownership**：避免多个运行时争夺同一权威；
13. **Heartbeat / Runner / Host Loop**：已经具有 Resident Runtime 的雏形；
14. **fail-soft / incremental reuse**：适合真实长流程生产。

因此，Production Kernel 不再是“脚本集合”。

它已经是 Story OS 目前最有价值、最接近生产稳定态的一层。

# 五、当前最大的结构问题：状态文件太多

同一个 Episode 当前可能同时存在：

```text
episode-state.json
runtime-dag-state.json
runtime-checkpoint.json
runtime-runner-state.json
runtime-resume-token.json
next-action.json
production-queue.json
production-ledger
full-auto-status.json
effective-config.json
...
```

这些文件本身大多各有用途，但问题是：

> **机器知道谁是什么，人和 Console 不容易知道“现在到底是什么状态”。**

如果未来多 StoryOS 任务监控页面直接去解析这些底层文件，前端最终会变成另一套状态解释器。

这是必须避免的。

## 建议：统一 `RuntimeStatusSnapshot`

建立一个只读、可重复生成的状态投影：

```json
{
  "production_stage": "STORYBOARD_LOCKED",
  "execution_status": "WAITING_DECISION",
  "blocking_reason": "visual_lock_candidate_pool_exhausted",
  "current_action": "USER_DECISION_REQUIRED",
  "image_progress": {
    "generated": 4,
    "passed": 3,
    "blocked": 1,
    "total": 20
  },
  "review_progress": {},
  "auto_recoverable": false,
  "needs_user": true,
  "heartbeat_at": "...",
  "next_step": "..."
}
```

原则：

- Snapshot **不是新的 authority**；
- 它只读取 canonical state / ledger / runtime evidence；
- 可随时重建；
- Console 只读 Snapshot / Platform API；
- Console 不理解底层几十种 runtime JSON；
- 未来多 Episode 监控、报警、卡点定位统一走这个模型。

这是当前最值得做的 Platform read model。

# 六、Full Auto 目前还不是真正“无人值守到底”

当前 `run_full_auto()` 能够自动推进大部分链路，但退出语义仍然是：

1. 到 `PUBLISH_READY`：成功；
2. 遇真正需要用户决定：停止；
3. Repair Budget 耗尽：停止；
4. `RUNNING / REPAIRING`：仍可能返回未闭环状态。

所以当前 Full Auto 更准确的定义是：

> **自动执行到系统认为必须人工介入为止。**

这已经比普通流水线强很多，但还没完全达到用户期望的：

> “我说一句话，它自己跑，中间自己处理，最后告诉我结果。”

Full Auto 下一阶段不应继续增加新的大 Orchestrator，而是要减少“其实可以自动处理、却被定义为人工阻塞”的场景。

# 七、「尸解仙」暴露出的核心问题：Visual Lock 有界了，但仍会停人

审计时「尸解仙」的关键运行事实是：

- canonical Episode stage：`STORYBOARD_LOCKED`；
- 已产生部分 Visual Lock 图；
- 3 号帧成为阻塞帧；
- bounded admission candidate pool 已耗尽；
- `next-action` 最终进入 `USER_DECISION_REQUIRED`；
- Runner / Host 处于等待态；
- 用户实际观察到了 03 被反复出图的问题。

当前系统已经有：

- Visual Lock candidate pool 上限；
- 内容返修预算；
- 技术失败单独重试；
- `EXHAUSTED` 语义；
- Repair budget 耗尽后进入 `NEEDS_USER`。

但**没有形成一条通用生产策略**：

> “已经尝试足够次数，虽然不是理想分，但不属于致命错误 → 低分降级通过，继续全自动生产。”

也就是说：

> 当前是“有界失败”，还不是“有界降级”。

## 建议新增：`DEGRADED_PASS`

建议统一视觉审核结果：

```text
PASS
DEGRADED_PASS
FAIL
TECH_FAILED
```

`DEGRADED_PASS` 适用于：

- 达到规定内容尝试上限；
- 不是技术错误；
- 不是身份错人；
- 不是故事语义完全错误；
- 不是关键异常缺失；
- 只是构图、表演、局部真实性、审美分数未达到理想值；
- 继续重画的边际收益明显低于时间成本。

### 绝对不能 DEGRADED_PASS 的情况

- 人物身份错误；
- 强制参考锚点丢失；
- 核心剧情语义反了；
- 必须出现的异常没有出现；
- 图不可用 / 损坏 / 尺寸技术失败；
- 安全、合规或生产硬门禁失败。

这条策略的价值不是“降低质量”，而是：

> **把生产系统从追求单帧局部最优，改成追求整集在有限预算内稳定完成。**

# 八、PREIMAGE 当前存在“先验证失败，再补依赖”的绕路

「尸解仙」Runtime DAG 历史中，PREIMAGE 曾多次因为缺少以下派生合同而 BLOCK：

- capture-event-contract；
- world-state；
- temporal-continuity；
- wardrobe-contract。

之后系统又进行了 materialization，最终 PREIMAGE 通过。

这说明系统具备修复能力，但调用时序还可以更合理。

当前部分路径近似：

```text
execute
  ↓
verify
  ↓
发现缺依赖
  ↓
BLOCK
  ↓
materialize dependency
  ↓
retry
```

建议调整为：

```text
resolve dependencies
  ↓
materialize deterministic contracts
  ↓
execute model work
  ↓
verify once
```

即：**能确定性生成的依赖，必须在 verifier 前物化。**

这样能减少一次无意义的 DAG 周期，也能降低 Host Wait / BLOCK 状态噪音。

# 九、Runtime Request 正在承担过多职责

当前 Runtime Request 可以同时混入：

- 用户的创作要求；
- Story OS 的执行模式；
- 模型 / runtime 指定；
- 操作命令；
- 旧版本的人工执行说明；
- 历史 workaround；
- 强制约束。

「尸解仙」就是典型例子：真正重要的创作硬约束可以提炼得很清楚，但 raw request 同时保留了大量操作性文字，其中部分随着系统修复已经过时。

这会造成两个问题：

1. Creative Agent 看到过多执行噪音；
2. 旧操作说明有机会与新 Runtime 行为冲突。

## 建议三层拆分

```text
RuntimeRequest
├── creative_request
│   ├── story seed
│   ├── required constraints
│   └── creative preferences
│
├── execution_policy
│   ├── full_auto
│   ├── runtime ownership
│   ├── image model / quality
│   ├── retry / degradation policy
│   └── concurrency / budget
│
└── operator_instructions
    ├── one-off operational notes
    ├── migration compatibility
    └── debugging / manual commands
```

其中 Story / Concept Agent 默认只消费 `creative_request`，Runtime 只消费 `execution_policy`。

`operator_instructions` 不得污染 Story Input。

# 十、V3 Platform 已经做了很多，但还没有真正“接管”

当前 `platform/` 已经实际具备大量能力，包括但不限于：

- Event；
- Trace；
- Artifact；
- Workflow；
- Shadow Workflow；
- Agent Registry / Orchestration；
- Platform API；
- HTTP Server；
- MySQL Repository；
- Redis Runtime State；
- Memory / Experience API；
- Operations / Governance；
- Console 相关基础能力。

所以 V3 Platform 不是白做。

真正的问题是：

> **能力层做出来了，但生产接管层没有完全完成。**

在当前代码中，Production Kernel 仍没有真正依赖 Platform 的：

- AgentRuntime；
- ExperienceStore；
- MemoryRetrievalService；
- ShadowWorkflowEngine；
- RedisRuntimeStateStore；
- RuntimeRepositoryProvider。

因此，不能把“Platform 模块数量很多”理解成“生产已经 Platform-native”。

# 十一、Platform 内部还有部分内存态实现

当前部分 Platform 服务仍存在类似：

```text
self._agents = {}
_executions = {}
_experiences = []
```

这些实现用于 MVP / API 骨架是合理的，但如果它们要成为正式 Control Plane，就不能继续只依赖进程内存。

后续需要：

```text
Application Service
      ↓
Repository Contract
      ↓
MySQL / Redis / Durable Store
```

尤其是：

- Agent Execution；
- Workflow Execution；
- Experience；
- Runtime Status；
- Long-running Task；

这些都必须具备跨进程恢复能力。

# 十二、Memory / Experience 当前属于“有能力，但还没成为大脑”

Story OS 当前已经具备：

- Story DNA；
- Similarity；
- Advisor；
- Account Learning Index；
- Post Publish Review；
- Failure Memory；
- Experience Store 概念与 API；
- Shadow Observation / Feedback / Ledger。

这说明“学习系统”已经不是零。

但距离真正的长期 Memory 还有明显差距：

```text
过去做过什么
   ↓
抽取经验
   ↓
统一持久化
   ↓
下一篇创建时自动检索
   ↓
影响 Concept / Story / Visual / Production 策略
   ↓
生产结果再次回写经验
```

当前更接近：

> **已有多个学习部件，但它们尚未统一成“下一次生产一定会使用的长期记忆闭环”。**

因此 Memory 下一阶段不应继续增加新名词，而应解决“真的被生产决策使用”。

# 十三、Git 工作区与运行资产混用已经成为工程风险

本次审计期间，工作区持续处于 dirty 状态，而且随着跑批继续，修改 / 未跟踪运行文件数量仍在变化。

主要类型包括：

- Episode runtime state；
- provider receipts；
- production queue；
- effective config；
- runtime request；
- review evidence；
- 新 Episode；
- production prompts；
- 测试文件；
- 文档 / 图片。

这意味着当前一个 Git Worktree 同时承担：

```text
Source Code Workspace
+
Production Runtime Workspace
+
Episode Asset Workspace
+
Audit Evidence Workspace
```

短期还能工作，但多 Episode 并行后会越来越难治理。

## 建议长期分层

```text
storyOS repo
  → code / config / standards / schemas / tests

runtime workspace
  → queue / checkpoint / receipts / runner / temporary evidence

episode asset workspace
  → canonical episode assets / final evidence
```

不要求立刻搬仓库，但至少要先明确：

- 哪些运行文件应该 Git Ignore；
- 哪些是最终 Episode 权威资产；
- 哪些只属于 transient runtime；
- 哪些必须归档后才能提交。

# 十四、接下来不要继续“大扩建”，而要进入收敛期

当前规模已经相当大：

- `episodes/_system`：数百个 Python 模块；
- `platform`：大量 Platform 模块；
- `tests/system` + `tests/platform`：已经形成大规模测试集。

这时最危险的方向是继续不断新增 Phase、Engine、Manager、Service，而不处理已有边界重叠。

下一阶段应该从“建设期”切换到：

> **Authority 收敛 + Runtime 收敛 + Status 收敛 + Control Plane 接管。**

# 十五、建议路线图

## P0：直接提升当前生产闭环

| 优先级 | 项目 | 目标 | 是否影响现有生产权威 |
|---|---|---|---|
| P0-1 | Visual `DEGRADED_PASS` | 有界尝试耗尽后，非致命缺陷自动低分通过，不再无意义反复出图 | 否，只扩展审核结果语义 |
| P0-2 | `RuntimeStatusSnapshot` | 给 Console / 多 Episode 监控提供唯一统一读模型 | 否，只读投影 |
| P0-3 | Resident Driver 收敛 | Full Auto 真正做到无人值守持续推进 | 否，复用现有 Orchestrator / Runner / DAG |

### P0 完成后的目标体验

```text
用户一句话
   ↓
Story OS 自动跑
   ↓
技术失败自己重试
   ↓
一般内容缺陷有限返修
   ↓
低收益缺陷 DEGRADED_PASS
   ↓
严重语义 / 身份问题才真正阻塞
   ↓
Console 始终显示一个清晰状态
   ↓
完成 / 真正需要用户决定
```

## P1：减少内部绕路和架构噪音

| 优先级 | 项目 | 目标 |

## 本轮关键实现原则

1. **没有新增第二个 Episode 状态机。** `RuntimeStatusSnapshot` 只在读取时聚合事实。
2. **没有把低质量图片伪装成高质量 PASS。** `WEAK_PASS` 保留原始 Vision FAIL / review evidence，并明确记录为弱通过。
3. **没有让 Platform 反写 Production Kernel 权威文件。** 当前 Platform 先做只读控制面。
4. **没有迁移真实 Runtime Request。** 新旧请求继续可读，三域分层属于兼容式 derived view。
5. **没有执行真实 MySQL migration，也没有切换生产默认存储。** 本轮只把共享 `platform_latest_record` DDL 与 Adapter 落进代码，并使用 FakeConnection 验证；上线迁移仍是独立动作。
6. **没有移动、删除或重写历史 Episode 的正式证据。** Formal Evidence、Production Ledger、Provider Receipt、Episode Stage Authority 仍保留在 Episode；本轮只迁移已完成消费者双读的 operational / derived 数据。
7. **Runner 锁语义没有迁移。** `runtime-runner.lock` 继续留在 Episode 侧，避免状态路径外置时顺带改变进程互斥语义。
8. **执行迁移除了消费者收口，还必须满足资产自身的激活安全条件。** 普通 operational / derived 资产仍受 allowlist 管控；Production Queue 即使消费者已经全部收口，也因为缺少 scheduler 锁保护下的原子 copy + checksum verify + activation / stale-shadow rejection 协议而继续 fail-closed，不允许仅靠修改 Store 模式提前切换。
9. **Legacy 永不自动删除。** copy 成功后只通过 Workspace-first 读取自然切换；源文件继续保留，重复执行会校验并复用相同目标，冲突或源变化则 fail-closed。
10. **Checkpoint 已完成物理外置，但恢复语义没有改变。** 新写入进入 Runtime Workspace，所有恢复/授权/交付/观测关键消费者统一走 accessor；Legacy 仍可回退读取，并已进入迁移 allowlist。
11. **Frame Contract 只迁派生帧缓存，不迁发布证据索引。** `contracts/frames/*.json` 可 Workspace-first；`frame-contract-index.json` 继续保留 Episode，避免发布证据链被缓存治理顺带改变。
12. **Production Queue 消费者已全部收敛，但 writer 仍不切。** `production_queue_store.py` 继续 `legacy_pinned`；所有运行消费者只能经 Store 访问，兼容别名仅保留 API 形状，静态测试禁止用别名重新拼接 Queue 物理路径。当前唯一剩余阻塞是原子 cutover 协议，Workspace 中即使存在 stale queue shadow 也仍不能覆盖真实生产 Queue。
