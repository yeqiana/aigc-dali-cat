## 0. 一页速览

Story OS 不是普通代码仓库，而是**「创作规范 + 状态机 + 执行运行时」三合一的内容生产操作系统**，用于批量生产抖音第一人称怪谈/规则怪谈图文系列。

它的核心设计约束只有一条，但贯穿全仓：

> **规则可以很多，决策入口只能有一个。**

由此派生出的三条不变量：

1. 阶段状态唯一权威 = `meta/episode-state.json`，任何 trace / route / checkpoint 都不授予 PASS；
2. 推进阶段必须通过 `validate_episode → machine_gate → evidence_gate` 三层门禁，前向必须相邻；
3. 自动审核必须诚实标记为 `delegated_auto_review`，不得冒充用户亲审。

**当前健康度**：`story_os.py doctor` → `errors=0 warnings=0`。

**当前卡点**：`天界普通女生的一天` 停在 `STORYBOARD_LOCKED`，`USER_DECISION_REQUIRED`，帧 `[5, 16, 17]`。

**规模**：

| 维度 | 数量 |
|---|---|
| `episodes/_system/` 引擎模块 | 264 个 `.py` |
| `standards/` 规范文件 | 92 |

## 3. 核心架构：三层权威分离

```
┌─────────────────────────────────────────────┐
│ 规范权威  standards/制作规范_正式版.md        │  ← 创作规则
├─────────────────────────────────────────────┤
│ 状态权威  meta/episode-state.json            │  ← 七阶段，唯一
├─────────────────────────────────────────────┤
│ 执行权威  runs DAG / gates / evidence        │  ← 只记事实，不授 PASS
└─────────────────────────────────────────────┘
```

**关键设计**：执行层产生的所有东西（trace、route、checkpoint、next-action、node evidence）都是**派生证据**，明确声明 `stage_authority: meta/episode-state.json`。调度器 `runtime_scheduler.schedule()` 甚至显式声明 `authority.episode_state_mutated: false`。

## 4. 执行流程

### 4.1 三个入口（唯一的常驻驱动是 ③）

一个剧集同时只能有一个驱动者。这不是风格建议，是 2026-09-14 `尸解仙` 停摆的成因。

```bash
# ① 一句话全自动（一次性：建篇 → 交给 ②）
python episodes/_system/story_os.py create "<一句话>" --full-auto

# ② 指定剧集全自动（--full-auto 必须显式，缺省直接 SystemExit）
#    有界排空：遇 HOST_ACTION_REQUIRED 即退出交回，不常驻
python episodes/_system/story_os.py run <episode> --full-auto [--resume]

# ③ 常驻唯一驱动：唯一会写 meta/runtime-runner-state.json、持续心跳、
#    每循环落 HOST_LOOP 证据的进程。宿主 Agent 的职责是确保它在跑。
python episodes/_system/story_os.py runner <episode> [--interval N]
```

`story_os.py` 本体仅 248 行，是**纯转发器**——40+ 子命令绝大多数 `forward()` 到对应模块，自身不承载生产逻辑。

**不是入口**：`runtime_dag.py`（`story_os.py dag run`）是**步骤引擎**，执行被点名的节点后返回。它不启动宿主循环、不写心跳、不落 `HOST_LOOP` 证据；手工推进 DAG 会得到一个「看起来在推进、实际无人负责」的剧集。判活只读 `meta/runtime/next-action.json` 的 `host_loop`（只有 `RUNNING` 才算活着）与 `orphaned_pending_work`（`true` = 有活欠着却没人跑）。**引擎不提供看门狗**：没有任何模块会 start / stop / restart / wait runner，看到 `orphaned_pending_work: true` 的正确反应是人把驱动者重新拉起。

日常诊断命令：

```bash
python episodes/_system/story_os.py status  <episode>   # 只看状态
python episodes/_system/story_os.py next    <episode>   # 打印下一阶段与三条 precheck 命令
python episodes/_system/story_os.py doctor              # 仓库健康
python episodes/_system/story_os.py checklist <episode> # 最终验收清单
```

### 4.2 七阶段状态机

```
IDEA_LOCKED → STORYBOARD_LOCKED → VISUAL_CALIBRATED → PRODUCTION_PASSED
→ PUBLISH_READY → PUBLISHED → DATA_REVIEWED
```

- 常量定义：`episodes/_system/story_os_contract.py:17`（`canonical_stages()` 与 `story_os_manifest.json` 比对，漂移即 RuntimeError）
- **唯一写者**：`episodes/_system/episode_state.py:347-399` `transition_cmd()`
  - 前向必须**相邻**（`tgt_idx == cur_idx + 1`）
  - 必须依次通过三道闸，任一失败状态不动
  - 后退必须显式 `--rewind`
- 发布后阶段由 `runtimes/workflow-contract.json` 声明：`PUBLISH_RECORD`（→PUBLISHED）、`DATA_REVIEWED_GATE`（→DATA_REVIEWED，要求 48h checkpoint）

**重要**：stage 推进**不在** DAG 主循环里发生。真实分工是：

```
runtime_dag.execute()   只裁决：达到 target_state → REUSED；未达到 → 执行；后置校验失败 → rc=4
        ↓
真正 transition 发生在两处：
  ① scoped_codex_worker.py STEP_DIRECTIVES —— 写进 worker 的 prompt
     "TARGET: reach STORYBOARD_LOCKED and stop there."
     "... advance only to STORYBOARD_LOCKED."
     worker 在自身会话内执行 episode_state.py transition
  ② machine_action_executor.py —— 确定性机器收口
     _finalize_visual_lock()        → VISUAL_CALIBRATED
     _finalize_production_images()  → 写 story-gates.reviews.* = passed
```

即 **worker 自行声明推进目标，DAG 事后用 `validate_target()` 复核**。

### 4.3 Runtime DAG

拓扑定义：`runtimes/runtime-dag.json`

| 顺序 | step | executor | target_state |
|---|---|---|---|
| 1 | `INCREMENTAL_PLAN` | `machine_incremental_plan` | — |
| 2 | `CREATIVE_STORY` | `scoped_model` | `STORYBOARD_LOCKED` |
| 3 | `PREIMAGE_COMPILE` | `scoped_model` | — |
| 4 | `VISUAL_LOCK` | `scoped_model` | `VISUAL_CALIBRATED` |
| 5 | `PRODUCTION` | `scoped_model` | `PRODUCTION_PASSED` |
| 6 | `RELEASE` | `scoped_model` | `PUBLISH_READY` |

线性 `depends_on`，`PREIMAGE_COMPILE` 是执行节点**不是**第八个 stage。

**旁路**：`provisional_release_parallel: true` —— `CREATIVE_STORY` 之后后台线程起 `provisional_release.build`，与 `VISUAL_LOCK`/`PRODUCTION` 并行，但 `blocking: false, final_authority: false`。

**另一套细粒度拓扑**（`runtime_node_registry.first_batch_nodes()`，标签非执行器）：

```
story_lock
  ├─ character_finalize        ┐
  ├─ environment_prepare       ├─ 4 路并行 (max_concurrency=4)
  ├─ world_prepare             │
  └─ visual_narrative_prepare  ┘
```

### 4.4 单步执行循环

`episodes/_system/runtime_dag.py:196` `execute()`

```
1. reconcile_visual_profile_closure()   ← fail-closed，不可恢复 rc=9 直接返回
2. runtime_mode_router.guard()          ← 失败 rc=8
3. runtime_scheduler.schedule()         ← max_workers=1，按依赖取 ready node
4. 三种分支：
   ├─ REUSE     target_state 已达成且三门禁通过 → 跳过
   ├─ HOST_WAIT WORK runtime 且非 codex → 发 Host Action (rc=20)
   └─ 执行      scoped_codex_worker.run_step()
5. 后置校验（每步都做真校验，不是形式）：
   CREATIVE_STORY  → character contract / world identity / appearance anchor
   PREIMAGE_COMPILE→ directing quality + 构建 preproduction handoff
   所有步          → directing_quality.after_step + validate_target()
6. 落证据：checkpoint + node evidence + trace span + next_action.write()
7. rc!=0 → 若 VISUAL_LOCK 且 image_continue → speculative_production
           生成至多 6 个不可批准候选，然后返回
```

`validate_target()` 就是依次跑 `validate_episode.py` / `machine_gate.py` / `evidence_gate.py --target`，三者全 0 才算过。

### 4.5 Host Loop —— 整套系统的枢纽

`next_action.derive()`（`episodes/_system/next_action.py:191`）从**当前事实**派生「下一步该做什么」：

```
优先级（从高到低）：
  1. PREIMAGE authority 过期          → PREIMAGE_COMPILE
  2. 生产队列恢复
     ├─ 技术失败 / 外部阻塞 / 中断
     ├─ baseline 待审                  → REVIEW_ORDINARY_BASELINE
     ├─ 四张 Visual Lock 图齐备        → REVIEW_VISUAL_LOCK / FINALIZE_VISUAL_LOCK
     ├─ scheduler 依赖权威报可运行     → GENERATE_IMAGES
     └─ 全帧候选齐备                   → REVIEW_FINAL_PRODUCTION
  3. NEEDS_USER 硬停                  → USER_DECISION_REQUIRED
  4. 产品审核请求待办                 → PRODUCT_REVIEW
  5. 按 stage 兜底                    → CREATIVE_STORY / VISUAL_LOCK / PRODUCTION / RELEASE
```

**注意**：`meta/runtime/next-action.json` **没有任何代码读它**——所有消费方都调 `derive()` 现算。该文件是给 WORK 主机与人工看的持久化产物。

真正的行动消费者是 `episode_runner.local_host_action()`：

```
CODEX_IMAGE + {GENERATE_IMAGES, RETRY_TECHNICAL_FAILURES,
               REPAIR_FAILED_IMAGES, REFRESH_AUTHORITY_IMAGES}  → image_scheduler
CODEX_VISION                                                → vision_review_executor
MACHINE 动作                                                → machine_action_executor
其余                                                        → 交还 WORK host
```

**四态语义分离**（`next_action.py:497`）：

| 字段 | 含义 |
|---|---|
| `work_pending` | 是否有活 |
| `auto_recoverable` | 能否自动恢复 |
| `hard_stop` | 是否必须人工决策 |
| `blocking` | = `work_pending AND hard_stop`（遗留兼容） |

Host loop 两个形态：

| 形态 | 实现 | 特征 |
|---|---|---|
| 单次 run 内 | `workflow_runner.advance_host_loop()` | DAG ↔ 本地动作交替，上限 `host_loop_max_cycles=64`；非 0 rc → `host_action_technical_failure` rc=21 |
| 常驻 | `episode_runner.run_episode()` → `persistent_runner_daemon` | 单所有权锁 + 心跳，指数退避，无进展 3 次 → `CAPABILITY_WAIT` rc=24 |

### 4.6 图片生产链路

```
image_scheduler / batch_scheduler          队列与调度
  └─ scheduler_core.run_execution_loop()   唯一执行循环，硬上限 3 worker
       └─ image_worker_pool.execute()      预算 + 包装
            ├─ raw_candidate_budget.claim()          ← 额度不足 rc=98 硬停
            ├─ codex_subscription_image.generate_for_frame()
            │    ├─ read_canvas()                    正式画布
            │    ├─ prompt_package.compile_frame()   scene prompt + frame_contract SHA
            │    ├─ invoke_codex()                   隔离 CODEX_HOME 起子进程 → media/raw/
            │    ├─ provider_capability.inspect()    → meta/provider-receipts/
            │    └─ canvas_normalize.normalize()     LANCZOS，比例偏差超阈值抛 NormalizeError
            └─ raw_candidate_budget.commit()         ← rc=96 CANDIDATE_COMMIT_FAILED
       └─ ledger_call.success() → production_ledger.cmd_success()
            └─ 逐像素校验候选尺寸必须精确等于 ledger canvas
```

**Visual Lock 固定 1+3**（`visual_lock_v21.py:239 choose_plan()`）：

```
A. ordinary_baseline          → 单独过像素门，建立 Pixel Master
B. worst_capture_condition    ┐
C. first_major_anomaly        ├─ baseline PASS 后才放行，并行
D. high_impact_admission      ┘
```

选帧细节：**先选 high-impact 再选 worst**，防止 worst 吞掉唯一的 climax 帧。纯日常题材（`ordinary_life=True`）时 `first_major_anomaly` 退化为「首个强视觉/世界对比」帧，**不虚构异常**。

**Batch**：Logical Batch = 5 帧（`config/agent_runtime/batch.json`）。仅当队列全部为 `scope=batch, kind=original` 时走 batch 通道（`batch_scheduler.should_use()`）。Codex 订阅通道是把 5 帧 fan-out 成 5 个单图 worker，**不是** provider-native `n=5`。并发 3 起，失败轮降 `3→2→1`，只重试失败项。

**预算与返修**：

| 类型 | 额度 | 说明 |
|---|---|---|
| `original` | 2 | Raw Candidate Budget |
| `repair` | 2 | 内容返修 |
| `exception` | 2 | 有界候选池（不占内容返修额度） |
| `user_exception` | 1 | 用户显式授权的第三轮（**在途改动新增**） |

**技术失败 ≠ 内容返修**：

- 技术失败（网络 / 5xx / 超时 / artifact 冲突 / normalize 失败）：可自动重试 3 次，退避 15s / 45s，**不计入内容返修额度**，且不触发重新生图
- 内容失败（像素评审 FAIL）：走 `ledger CONTENT_FAILED → REPAIR_AUTHORIZED → auto_repair_enqueue`，每帧一次
- `NON_REGENERATING_FAILURE_CODES`（预算耗尽 / 契约不匹配 / 断路器 / prompt 漂移）直接 `blocked` 而非 `tech_failed`

### 4.7 门禁三层

推进阶段必须依次通过：

| 层 | 文件 | 管什么 |
|---|---|---|
| ① | `validate_episode.py`（705 行） | **传统结构**：manifest / gates / 发布图、approval SHA 漂移、DATA_REVIEWED 需 48h |
| ② | `machine_gate.py`（784 行） | **机器证据**：authenticity card / 四帧校准政策 / reference 执行回执 / identity continuity / 生产台账 / 帧评审。`machine_contract.strict != true` 时仅 WARN |
| ③ | `evidence_gate.py` | **审批溯源**：story_lock 审批、story_semantic_review、visual profile resolve、text-audit SHA 一致性、release_lock |

两个细节：

- `evidence_gate` 有**版本豁免**：`is_enforced` 只对 `tool_version >= 1.8` 的剧集强制，旧剧集跳过（防止历史剧集被追溯判死）
- 文本审计**两条独立路径**：`text_audit.py`（确定性、无模型）走 evidence_gate；WORK 语义评审走另一条，不可互相替代

### 4.8 评审路由

```python
runtime_router.text_review_runtime()    → 强制 WORK
runtime_router.vision_review_runtime()  → 默认 CODEX（STORY_OS_VISION_RUNTIME 可覆盖）
```

| 类型 | 实现 |
|---|---|
| WORK 文本/语义评审 | `product_review_adapter.prepare()` 冻结源文件 SHA256 写 review request，**Python 侧从不调模型**；`finalize_candidate()` 复查源哈希无漂移才采纳 |
| Codex Vision 像素评审 | `codex_critic_runner.launch()` → `codex exec --ephemeral -s sandbox -o candidate.json -i <附件> -`。被 fast_frame_scout / visual_lock_v21 / frame_semantic_review / incremental_frame_review 共用 |

**全量评审 vs 增量评审**：

- `frame_semantic_review.py`（1632 行）：全片逐帧语义像素评审，11 项基础检查
- `incremental_frame_review.py`（704 行）：在其之上的增量补丁层，只对 dirty/context 帧重评。**`machine_gate` 实际调用的是增量层**

**审批证据表达**：

| 锁 | 落盘 |
|---|---|
| Story Lock | `story-gates.json.approvals.story_lock`（artifacts 逐文件 SHA256） |
| Visual Lock | 同上 + 比对 resolved profile 四项字段 |
| Release Lock | `release-package.json.user_approved` 或委托路径 |
| 委托自动锁 | `delegated-approvals.json`，强制 `user_approved: false, delegated_auto_review: true` |

委托审批前提：`runtime-checkpoint.json` 中 `continuous_execution_authorized == true` 且 `approval_basis ∈ {delegated_continuous_execution, delegated_auto_review}`。**不冒充用户亲审**。

### 4.9 Runtime 职责边界

```
ChatGPT UI        = 用户交互界面，不参与 Runtime 判定（≠ WEB Runtime）

CODEX_VISION      = 独立、fresh、ephemeral 的真实像素审核 lane
WEB Runtime       = 历史兼容，不参与新生产路由
```

关键约束：`runtime_router.local_codex_image_allowed()` —— CODEX 图能力**不授予** Story / PREIMAGE / governance 权限。

## 6. 发现的问题

### P1 —— `MODULE_INDEX.json` 误伤现行模块

```jsonc
// episodes/_system/MODULE_INDEX.json:37-61
"formal_review": ["story_review.py", "visual_lock_v21.py", ...],
"legacy_or_migration_patterns": ["*_v20*.py", "*_v21*.py", "*_v22*.py", ...]
```

`visual_lock_v21.py` **同时命中两条**。而 `agent_read_policy` 要求「不泛读 legacy」——按索引办事的 Agent 会**跳过 V2.1 四帧 Visual Lock 的现行实现**（`choose_plan` / `run_critic` / `bind_from_queue` 全在其中）。

glob 匹配的是**文件名版本号**，不是废弃状态。

同类：`incremental_frame_review.py` **未列入 index**，但它是 `machine_gate` 实际调用的入口。

### P1 —— `START_HERE.md` 承诺的四个锁点，有一个不存在

`START_HERE.md` §2 列出「四个必须停下来的人工锁点：Story Lock / Visual Lock / **Repair Lock** / Release Lock」。

实际：**全库无 `repair_lock` 实现**。返修不叫「锁」，而是靠台账状态（`AUTHORITY_REFRESH_AUTHORIZED` / `NEEDS_USER` / `REPAIR_READY`）+ `content_repairs_used` 上限 + 有界候选池 + `final-acceptance` 受控例外约束。

约束确实存在，但文档把它描述成一个需要显式确认的动作，会让人/Agent 去找一个不存在的确认步骤。

### P2 —— provider 配置存在死字段且值与生效值冲突

| 文件 | 值 | 状态 |
|---|---|---|
| `config/providers/image-provider-runtime.json:43-46` | `[5, 3, 1]` | ❌ **无消费方** |
| `config/agent_runtime/codex-subscription-batch.json` | `[3, 2, 1]` | ✅ 实际读取 |

`codex_subscription_batch_runtime.py::self_test()` 硬断言 `== [3,2,1]`。按 `providers/` 那份理解系统行为会得到**错误结论**。注意：不要改代码去读它——那会把实际并发语义从 3→2→1 改成 5→3→1。

### P2 —— 治理文档规模已超过系统本身

`docs/` 61 + `reports/` 73 = **134 份治理文档**，对比 264 个引擎模块。文档标题形态高度相似（`*_分析与修复方案_*.md` / `*_漏洞治理_*.md` / `*_闭环缺口*.md`），存在：

- 同一问题在多个方案中被重复分析（例：Runtime 投影漂移出现在至少 3 份文档）

- 缺少索引，新人/Agent 无法判断哪份是当前有效口径

## 8. 值得肯定的设计

这份分析如果只列问题是不公平的。以下设计在同类系统中属于高水准：

1. **单写者纪律贯彻到底**：stage 单写者、ledger 单写者、PREIMAGE authority 单写者。并发只出现在像素生成与 derive 阶段，权威写入点全部串行。
2. **派生物自我声明**：所有派生证据显式标注 `derived_runtime_only` / `stage_authority`，不给「第二套状态机」留生长空间。
3. **技术失败与内容失败彻底分离**：技术失败不消耗内容返修额度、不触发重新生图、不改变请求指纹。这是很多生产系统做不到的。
4. **委托审批的诚实性**：强制 `user_approved: false, delegated_auto_review: true`，从数据格式上杜绝伪造用户亲审。
5. **fail-closed 默认**：Visual Profile closure 不可恢复时 rc=9 直接拒绝；required reference anchor 缺失直接抛异常；`machine_contract.strict` 之外一律 WARN 而非静默通过。
6. **确定性优先**：`text_audit.py` 这类检查坚持无模型实现；`PREIMAGE_FRAME_CONTRACT_COMPILE` / `PREIMAGE_VERIFY` 这类纯确定性动作留在本地执行，不发无意义的 Host Action。
