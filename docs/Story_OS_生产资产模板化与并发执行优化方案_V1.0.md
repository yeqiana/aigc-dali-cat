# Story OS 生产资产模板化与并发执行优化方案 V1.0

更新时间：2026-09-12

适用仓库：

```text
D:\workspace\YeQianWorkSpace\yeqian\storyOS
```

适用目标：

> 在不降低故事评审、人物一致性、视觉校准、真实像素评审和发布门禁的前提下，减少重复模型推理，提升一句话全自动生产效率。

---

# 一、问题背景

当前《天界普通人的一天》真实生产暴露出一个明显性能问题：

```text
一句话输入
↓
选题
↓
故事
↓
20 张分镜
↓
人物约束
↓
语言约束
↓
分镜密度检查
↓
开场检查
↓
人物视觉约束
↓
镜头推进检查
↓
最近作品重复度检查
↓
故事语义评审
```

流程本身是正确的，但当前执行方式仍存在大量：

```text
重新读取故事
↓
重新理解人物
↓
重新理解世界
↓
单独生成一个文件
↓
再重新读取
```

的问题。

## 当前真实耗时基线

扣除本次 DevSpace → Codex 用户态执行桥接故障时间后，《天界普通人的一天》截至故事阶段的实际制作耗时约：

```text
约 42 分钟
```

其中：

| 环节 | 实际耗时 | 当前判断 |
|---|---:|---|
| 分集创建、需求解析、候选准备 | 约 8 分钟 | 可继续压缩 |
| 独立选题评审 | 约 5 分钟 | 基本正常 |
| 故事、20 张分镜及故事配套资产 | 约 29 分钟 | 当前主要优化目标 |
| 图片生成 | 尚未开始 | 后续单独观察 |

结论：

> 当前性能瓶颈并不是“文件写入太慢”，而是“为了生成多个文件，重复调用模型、重复读取上下文、重复推理”。

因此，本方案不主张删除治理文件，而是：

```text
保留治理文件
+
减少模型调用次数
+
固定结构模板化
+
同源资产一次生成
+
无依赖检查并发执行
```

---

# 二、核心原则

## 2.1 文件可以分开，模型调用不要分得过碎

现有文件承担：

- 门禁证据
- 审计
- 断点恢复
- 哈希绑定
- 增量复用
- 失败定位
- 发布检查

这些价值必须保留。

因此：

```text
不要把几十个治理文件合成一个大文件
```

应该改为：

```text
一次读取故事上下文
↓
一次生成一整包生产资产
↓
程序拆分写入多个治理文件
↓
每个治理文件继续独立验证
```

也就是说：

> 合并的是“模型推理”，不是“治理资产”。

---

## 2.2 能模板化的结构不再让模型从零设计

以后模型只负责填“内容值”，不再重复决定：

- 文件有哪些字段
- 检查项有哪些
- 状态有哪些
- 固定规则是什么
- 默认结构是什么

---

## 2.3 并发必须建立在真实依赖关系上

允许并发：

```text
互不依赖
+
只读取同一个冻结故事快照
+
各自产出独立文件
```

禁止并发：

```text
后一步必须依赖前一步的最终结果
```

不能为了速度破坏：

- 故事锁定
- 人物身份锚点
- 视觉校准第一张基准图
- 时间连续性
- 服装连续性
- 真实像素门禁
- 最终发布门禁

---

# 三、资产模板化设计

建议将生产资产拆为三类。

---

# 四、第一类：完全固定结构模板

这类资产的“结构”高度固定，不应该每篇重新让模型设计。

建议抽成项目级模板。

包括：

```text
分集初始状态
发布清单
故事门禁
语言风格约束骨架
分镜密度检查骨架
开场检查骨架
人物视觉约束骨架
镜头推进检查骨架
字幕布局规则
字幕语言检查骨架
拍摄事件字段
世界状态字段
时间连续性字段
服装连续性字段
```

建议新增项目级模板目录：

```text
standards/production_templates/
```

建议结构：

```text
standards/production_templates/
├─ episode_state.json
├─ release_manifest.json
├─ story_gates.json
├─ voice_contract.json
├─ storyboard_density_review.json
├─ opening_social_anchor.json
├─ character_visual_contract.json
├─ shot_progression_review.json
├─ capture_event_contract.json
├─ world_state.json
├─ temporal_continuity.json
├─ wardrobe_contract.json
├─ subtitle_layout.json
└─ subtitle_voice_review.json
```

说明：

这些模板只定义：

```text
字段
默认状态
固定检查项
固定版本
固定约束
```

不包含具体故事内容。

# 五、第二类：题材生产预设

当前已有视觉档案，但下一步建议从“只控制画风”升级为：

```text
视觉档案
+
题材生产预设
```

生产预设不替代视觉档案，而是补充：

- 世界设定默认值
- 人物默认职业类型
- 拍摄设备
- 叙事语气
- 开场要求
- 禁止项
- 生活细节偏好
- 默认字幕口吻
- 默认镜头方向

例如《天界普通人的一天》对应：

```text
天界普通工作人员生产预设
```

建议固定：

```text
世界：虚构东方天界
主体：普通基层工作人员
拍摄设备：随身上岗记录牌
生活感：高
劳动细节：高
英雄叙事：禁止
神话宣传片感：禁止
华丽仙袍：默认禁止
普通岗位：优先
日常流程：优先
第一张：人物身份建立
字幕：普通工作人员碎碎念
```

未来可以逐步形成：

```text
现代现实生活纪实预设
古代普通人生活预设
天界普通人生活预设
县城异常预设
旅行纪实预设
感情故事预设
```

建议目录：

```text
standards/production_presets/
```

预设只提供默认生产约束。

显式用户要求始终优先。

# 六、第三类：每篇必须动态生成的内容

以下资产必须根据每篇故事生成，不能固化成固定内容：

```text
故事核心
具体人物经历
具体异常机制
具体高潮
具体结尾
20 张具体分镜
每张图具体动作
具体字幕
具体发布文案
```

但是这些内容不应该被拆成大量独立模型调用。

应该建立：

```text
故事生产资产包
```

一次模型推理至少生成：

```text
故事锁定候选稿
20 张正式分镜
人物最终设定
叙述者语言设定
开场锚点
人物视觉基础设定
20 张镜头基础设计
```

然后由程序拆分为：

```text
docs/故事锁定稿

docs/20张正式分镜

meta/character-contract.json
meta/voice-contract.json
meta/opening-social-anchor.json
meta/character-visual-contract.json
meta/shot-progression-review.json
```

注意：

```text
生成完成 ≠ 门禁通过
```

程序仍必须逐项执行验证。

# 七、推荐的一次性故事资产包

建议新增中间资产：

```text
meta/story-production-bundle.json
```

它不是新的状态机，也不是新的权威源。

它只是一次模型生成结果的临时中间产物。

建议结构包含：

```text

人物
世界

语言风格
人物视觉约束
开场信息
镜头尺度
机位
光线
人物动作
互动关系
每张图新增信息
```

随后确定性程序拆分：

```text
story-production-bundle
↓
故事文档
↓
20张分镜
↓
人物约束
↓
语言约束
↓
开场约束
↓
人物视觉约束
↓
镜头推进检查初稿
```

这样可以显著减少重复读取和重复推理。

# 八、第一组并发：故事阶段

## 当前问题

目前故事确定后，很多资产仍接近串行生产：

```text
故事
↓
语言约束
↓
分镜密度
↓
开场检查
↓
人物视觉
↓
镜头推进
↓
最近作品重复度
↓
故事语义评审
```

其中大量步骤实际上只依赖同一份故事与分镜。

---

## 推荐结构

先冻结一个故事候选快照：

```text
故事候选
+
20张分镜候选
↓
生成故事快照哈希
```

然后并发：

```text
                    ┌→ 故事语义独立评审
                    │
                    ├→ 最近作品重复度检查
                    │
故事候选快照 ────────┼→ 分镜密度检查
                    │
                    ├→ 人物视觉约束检查
                    │
                    ├→ 镜头推进检查
                    │
                    └→ 开场检查
```

全部结果绑定同一个故事候选快照哈希。

全部通过后统一收口：

```text
六路结果
↓
一致性汇总
↓
人物最终约束确认
↓
故事正式锁定
↓
分镜正式锁定
```

# 九、故事阶段哪些必须串行

以下依赖不可打散：

```text
一句话需求
↓
需求解析
↓
候选选题
↓
独立选题评审
↓
最终选题
↓
故事候选
```

原因：

后一步明确依赖前一步的最终结果。

另外：

```text
故事正式锁定
```

必须等待全部故事级门禁返回。

# 十、第二组并发：生图前准备

故事锁定后，当前很多生图前资产也可以拆成并发波次。

推荐第一波：

```text
                  ┌→ 场景环境约束
                  │
                  ├→ 异常影响约束
故事正式锁定 ──────┼→ 拍摄事件约束
                  │
                  ├→ 世界状态
                  │
                  └→ 资源选择
```

这些资产大部分只依赖：

```text
故事
20张分镜
人物
世界设定
```

可同时计算。

---

# 十一、生图前必须保留的串行链

以下必须保持顺序：

```text
世界状态
↓
时间连续性
↓
服装连续性
```

原因：

服装选择依赖：

- 时间
- 天气
- 温度
- 场景
- 活动强度

而时间连续性依赖最终世界状态。

因此不能无脑并发。

最终：

```text
场景环境约束
异常影响约束
拍摄事件约束
资源选择
时间连续性
服装连续性
↓
统一编译20张最终生图约束
```

---

# 十二、第三组并发：视觉校准

当前 1+3 视觉校准思想应继续保留。

必须：

```text
第1张普通状态人物基准图
↓
真实像素评审
↓
身份锚点暂时锁定
```

这一步禁止并发越过。

第一张通过以后：

```text
                  ┌→ 最差拍摄条件
身份基准通过 ──────┼→ 首次主要异常
                  └→ 高冲击场景
```

后三张并发生成。

三张全部通过后：

```text
身份锚点正式锁定
↓
视觉校准完成
```

---

# 十三、第四组并发：正式图片生产

原则：

> 只有真正依赖上一张图片像素的帧才需要等待。

叙事上的先后关系不能自动等价于图片生成依赖。

例如：

```text
第02张
第03张
第04张
```

如果都只依赖：

```text
人物锚点
场景约束
故事约束
```

则可以同时生成。

当前已有图片并发额度：

```text
最多同时 3 个图片任务
```

建议保持当前并发 3 作为稳定默认值。

未来根据：

- 图片通道稳定性
- 失败率
- 平均生成耗时
- 额度情况

再动态调整。

---

# 十四、第五组并发：滚动评审与返修

正式生产不应该变成：

```text
20张全部生成
↓
再开始评审
```

应该形成流水线：

```text
图片生成池
↓
已生成图片立即进入评审池
↓
失败图片立即进入返修池
↓
通过图片继续向后推进
```

即：

```text
生成第01～03张
同时：
评审已完成图片
同时：
返修已确认失败图片
同时：
继续生成后续图片
```

形成三条并行通道：

```text
生成
评审
返修
```

但同一帧仍必须保持：

```text
生成
↓
评审
↓
返修
↓
再评审
```

单帧内部顺序不可打乱。

---

# 十五、字幕阶段并发建议

字幕不能在真实图片生成前完全锁死。

原因：

- 人脸位置未知
- 关键动作位置未知
- 异常证据位置未知
- 左中安全区是否可用未知

因此建议：

## 故事阶段

只生成：

```text
字幕语言风格
叙述者口吻
知识边界
每张图字幕功能意图
```

## 图片通过后

每张已通过图片立即可以并发执行：

```text
字幕候选
+
安全区分析
```

最终统一执行：

```text
连续三张语言检查
朗读检查
删除字幕检查
知识边界检查
线索回收检查
```

# 十七、预计性能收益

当前基线：

```text
扣除桥接故障后

```

第一阶段只做：

```text
固定结构模板化
+
一次故事生产资产包
+
故事阶段并发
```

目标：

```text
生图前 15～25 分钟
```

预计节省：

```text
约 40%～60%
```

注意：

这只是目标区间，最终必须通过下一篇真实生产记录验证。

不能为了达到时间目标：

- 删除独立评审
- 跳过人物一致性检查

- 降低故事门禁
- 降低图片评审标准

# 十九、实施边界

本次优化不允许：

```text
新增第二套分集状态机
新增第二套调度器
新增第二套图片运行时
删除现有故事门禁
删除独立评审
伪造评审来源
把治理资产合成一个不可审计的大文件
为了并发破坏真实依赖
```

应优先复用当前已有：

```text
运行有向图
异步任务运行器
图片调度器
批量调度器
滚动评审
返修通道
执行胶囊
增量复用
哈希证据绑定
```

# 二十、验收指标

改造完成后，必须用新的真实 Episode 验收。

至少记录：

| 指标 | 目标 |
|---|---|
| 一句话到最终选题 | 可观测 |
| 一句话到故事资产包完成 | 可观测 |
| 故事级并发总耗时 | 可观测 |
| 一句话到故事正式锁定 | 可观测 |
| 一句话到第一张视觉校准图 | 15～25 分钟目标区间内优先验证 |
| 每个模型调用次数 | 相比当前明显下降 |
| 重复上下文读取次数 | 相比当前明显下降 |
| 故事门禁数量 | 不减少 |
| 独立评审 | 保留 |
| 人物身份连续性 | 不降低 |
| 图片真实像素评审 | 保留 |

另外必须记录：

```text
串行耗时
并发等待耗时
模型调用耗时
图片生成耗时
评审耗时
返修耗时
```

避免以后只能看到“总共用了多久”，却不知道真正慢在哪里。

# 二十一、最终结论

当前 Story OS 的性能优化方向不应是：

```text
删文件
删门禁
少评审
```

而应该是：

```text
固定结构模板化
↓
题材生产预设化
↓
同源内容一次生成
↓
治理文件继续独立保留
↓
无依赖任务并发
↓
真实依赖保持串行
↓
生成、评审、返修流水线化
```

最终目标：

```text
一句话输入
↓
15～25 分钟完成生图前全部准备
↓
进入真实视觉校准
↓
图片并发生产 + 滚动评审 + 定点返修
↓
稳定到发布准备完成
```

核心原则只有一句：

> 保留治理强度，减少重复思考；保留文件证据，减少模型调用；只并发真正无依赖的任务。
