# StoryOS 生产模式与执行路由收敛方案

> 状态：设计冻结，暂缓实施
> 日期：2026-09-28
> 实施时机：当前 StoryOS 主改造完成之后

## 1. 目标

把“生产模式”收敛成一个顶层配置入口，同时把图片、视觉审核、Critic、Workspace、全流程 Agent/模型都定义为可替换执行能力。

核心原则：

- StoryOS 决定流程。
- Production Mode 决定整条生产链的控制方式。
- Capability Router 决定任务级能力路由。
- Runtime Scheduler 保持唯一实际 dispatch owner。
- Executor / Provider / Agent 只负责执行，不成为 StoryOS 顶层架构本身。

本方案当前只落设计文档，不修改现有生产行为。

## 2. 生产模式命名

### 2.1 协同生产

内部枚举：`COLLABORATIVE`

当前实现含义：

```text
Story / PREIMAGE / Governance / Gate / Release -> WORK / Product Runtime
Workspace                                      -> WebCodex
Image Generation / Repair                     -> Codex
Vision Review                                  -> Codex
```

“协同生产”不是“WebCodex + Codex”的永久别名。WebCodex、Codex 都只是当前执行实现，未来更换 Workspace、图片模型或 Agent 后，模式名称仍然保持不变。

### 2.2 Codex 全托管

内部枚举：`CODEX_MANAGED`

含义：整条 StoryOS 生产链显式交给 CODEX Runtime。

必须满足：

- 只能显式选择。
- 不允许因为 WebCodex / WORK 不可用自动进入。
- 不允许因为本机存在 `codex.exe` 自动进入。
- 不允许因为图片执行器是 Codex 自动进入。

## 3. 生产模式单入口

当前改造完成后，目标是只暴露一个正常生产模式入口：

```yaml
production:
  mode: COLLABORATIVE
```

或：

```yaml
production:
  mode: CODEX_MANAGED
```

普通用户不再通过手工组合 `WORK / WEB / CODEX`、图片 Runtime、Vision Runtime 来构造生产模式。

环境变量层未来只保留一个顶层正常覆盖入口：

```text
STORY_OS_PRODUCTION_MODE=COLLABORATIVE
STORY_OS_PRODUCTION_MODE=CODEX_MANAGED
```

现有 `STORY_OS_RUNTIME` 保留一段兼容期，但降级为 legacy compatibility / low-level debug override，不再作为普通生产模式入口。

## 4. 图片执行器必须独立显式指定

图片生成不是生产模式本身，不能和 Codex 永久绑定。

未来配置目标：

```yaml
production:
  mode: COLLABORATIVE

execution:
  image:
    executor: CODEX
```

以后可以直接切成：

```yaml
execution:
  image:
    executor: OPENAI_IMAGE
```

或：

```yaml
execution:
  image:
    executor: CUSTOM_IMAGE_AGENT
```

而不改变 `production.mode`。

允许的未来图片执行器包括但不限于：

- Codex
- OpenAI Image API
- 其他图片模型 Provider
- 第三方图片 Agent
- 自研图片 Agent
- ComfyUI / Flux / SD 本地流水线
- MCP / Remote Worker

因此长期应把当前 `runtime.image_execution_runtime` 逐步迁移为语义更准确的：

```text
execution.image.executor
```

现有 `STORY_OS_IMAGE_RUNTIME` 在迁移期保留兼容，后续可迁移为 `STORY_OS_IMAGE_EXECUTOR`。

## 5. Vision / Critic / 全流程执行器同样可替换

长期目标不是只支持 Codex。

例如：

```yaml
execution:
  workspace:
    provider: WEBCODEX
  image:
    executor: CODEX
  vision_review:
    executor: CODEX
```

未来完全可以变成：

```yaml
execution:
  workspace:
    provider: CUSTOM_WORKSPACE
  image:
    executor: CUSTOM_IMAGE_AGENT
  vision_review:
    executor: MODEL_X_AGENT
```

如果未来接入第二个真正能完整执行 StoryOS 的全流程 Agent，再进一步抽象：

```yaml
production:
  mode: MANAGED

execution:
  orchestrator:
    executor: CUSTOM_AGENT
```

当前阶段不提前引入该第三种模式，等真实第二个全流程 Executor 存在后再抽象。

## 6. 禁止自动升级为 Codex 全托管

当前代码仍存在 WebCodex 不可用、Codex CLI 可用时自动把整体 effective runtime 切到 CODEX 的行为。

后续配置收敛时必须改成：

```text
COLLABORATIVE
    -> required Workspace / Host unavailable
    -> PAUSED / BLOCKED
    -> 等待恢复或人工显式切换
```

禁止：

```text
COLLABORATIVE
    -> WebCodex unavailable
    -> 自动 CODEX_MANAGED
```

`CODEX_MANAGED` 必须始终来自显式配置或显式本次运行参数。

## 7. 与 P4 Capability Router 的边界

`production.mode` 解决的是“整条生产链由哪种控制方式运行”。

Capability Router 解决的是“某一个具体 Task 选择哪个 provider / model / executor”。

二者必须保持独立。

标准链路：

```text
production.mode
    -> Production Mode Resolver
    -> Runtime DAG
    -> Capability Router / Executor Resolver
    -> effective_execution_target
    -> Runtime Scheduler
    -> Adapter / Executor
```

Scheduler 继续保持唯一实际 dispatch owner。

## 8. 推荐最终配置形态

当前协同生产的目标配置示例：

```yaml
production:
  mode: COLLABORATIVE

execution:
  workspace:
    provider: WEBCODEX
  image:
    executor: CODEX
  vision_review:
    executor: CODEX
```

Codex 全托管示例：

```yaml
production:
  mode: CODEX_MANAGED

execution:
  image:
    executor: CODEX
  vision_review:
    executor: CODEX
```

以后即使图片改用别的 Provider / Agent，也不需要改变顶层生产模式。

## 9. Web Console 最终展示建议

普通用户只看到：

```text
生产模式

● 协同生产
  StoryOS 按能力分配不同执行器

○ Codex 全托管
  整条生产链由 Codex Runtime 执行
  仅显式启用
```

高级设置单独展示：

```text
Workspace      WebCodex
Image          Codex
Vision Review  Codex
Semantic Route Capability Router
```

以后可以只把 `Image` 改成其他模型或 Agent，而生产模式仍显示“协同生产”。

## 10. 本轮明确不实施

在当前 StoryOS 主改造完成前，本方案只作为后续设计基线。

本轮不执行：

- 不新增 `production.mode`。
- 不删除现有 Runtime 字段。
- 不迁移现有环境变量。
- 不重构图片 Scheduler。
- 不重构 Vision Review。
- 不改 Web Console 模式选择。
- 不新增 Executor Registry。
- 不扩大 P4 Capability Router 范围。
- 不改变当前 production 行为。

当前最高优先级仍然是：

```text
effective_execution_target
    -> Runtime DAG / Scheduler
    -> actual executor
```

先把本次架构改造闭环。

## 11. 后续实施前置条件

满足以下条件后，再开启 Production Mode / Executor 配置收敛：

1. P4 Capability Router Implementation Gate 通过。
2. Scheduler 已验证消费 `effective_execution_target`。
3. P4 Production Canary 完成。
4. 当前 StoryOS 主改造完成。
5. Runtime Contract 与配置入口稳定。
6. 不再存在高优先级架构迁移 blocker。

## 12. 后续建议实施顺序

### Phase A：新增单一生产模式字段

新增 `production.mode`，先只做兼容映射，不改变运行行为。

### Phase B：关闭自动整体 Codex fallback

协同生产依赖不可用时改为 `PAUSED / BLOCKED`，不自动进入全托管。

### Phase C：建立 Production Mode Resolver

统一输出 configured/effective production mode。

### Phase D：图片执行器独立化

逐步从 `runtime.image_execution_runtime` 迁移到 `execution.image.executor`。

### Phase E：Vision / Critic / Model Executor 统一

等真实多个 Provider / Agent 存在后接入统一 Executor Resolver。

### Phase F：最后修改 Web Console

UI 分成“生产模式”和“高级执行器配置”两层，避免 UI 先于 Runtime Contract。

## 13. 验收标准

后续实施完成必须满足：

- 普通生产模式切换只修改 `production.mode` 一个字段。
- 只有显式 `CODEX_MANAGED` 才允许 Codex 接管全流程。
- 修改图片 Executor 不得改变 `production.mode`。
- 图片从 Codex 替换为其他 Provider / Agent 不需要修改 Runtime DAG 主流程。
- Workspace / Provider 故障不得自动改变生产模式。
- Effective Config 能记录 configured/effective mode、configured/effective executor、override source、actual dispatch target。
- 任何 Executor / Provider / Agent 都不能绕过 Runtime Scheduler 自己 dispatch。

## 14. 最终目标

```text
StoryOS
  -> production.mode
  -> Runtime DAG
  -> Capability Router / Executor Resolver
  -> Runtime Scheduler
  -> Executor / Provider / Agent
```

> **StoryOS 决定流程，Production Mode 决定控制方式，Capability Router 决定任务能力路由，Scheduler 决定实际 dispatch，Executor 负责执行。**

Codex、WebCodex、具体模型和未来 Agent 都只是可插拔执行能力，不再成为 StoryOS 顶层架构本身。

## 15. 当前决策

```text
先完成现有 StoryOS 主改造
-> P4 dispatch consumer
-> Implementation Gate
-> Production Canary
-> 当前架构收口
-> 再实施 Production Mode / Executor 配置收敛
```

当前生产行为保持不变。
