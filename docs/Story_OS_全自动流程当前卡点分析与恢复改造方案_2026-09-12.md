# 一、结论先说

当前全自动流程不是“随机断了”，而是同时遇到了两层阻塞：

1. **运行恢复层阻塞**：图片调度任务曾超过外层执行窗口，队列里留下了 `interrupted_unknown` / `running` 等非终态记录。`next_action` 为了避免重复生图、重复计费、错接产物，按设计进入 `RECOVER_INTERRUPTED_IMAGES` 并 `hard_stop=true`。
2. **内容治理层阻塞**：Frame 03 已经消耗了本帧唯一一次自动内容返修额度，但最终语义评审仍判定它存在真实内容问题，因此账本进入 `NEEDS_USER`。这一层不是技术故障，而是当前生产规范的硬门禁。

因此当前完整因果链是：

```text
20 张图片已经生成
↓
最终语义评审完成
↓
13 张通过并锁定
7 张需要修
↓
其中 6 张还有一次自动返修额度
其中 Frame 03 已经用完唯一一次返修额度
↓
6 张自动返修继续执行
↓
期间外层执行窗口中断
↓
部分 worker 没有在队列中写成明确终态
↓
next_action 发现 interrupted_unknown
↓
先进入 RECOVER_INTERRUPTED_IMAGES
↓
恢复完成后仍会遇到 Frame 03 = NEEDS_USER
```

所以：

> **眼前直接卡点是“中断任务恢复”；恢复之后的最终硬卡点是 Frame 03 已用完唯一内容返修额度。**

# 三、第一层卡点：运行恢复层为什么会停

## 3.1 现象

当前生产队列里存在：

- `running`
- `generated`
- `interrupted_unknown`
- 历史 `blocked / superseded`

等混合状态。

当前 6 张自动返修中，最新一次检查为：

```text
05 running
11 generated
12 running
13 generated
15 generated
20 running
```

同时更早的原始/历史任务还有若干：

```text
interrupted_unknown
```

`next_action.py` 中明确规定：

只要队列存在 `interrupted_unknown`，就返回：

```text
RECOVER_INTERRUPTED_IMAGES
hard_stop = true
blocking = true
```

原因文本：

```text
an interrupted worker has no terminal receipt;
inspect reconciliation evidence before retry
```

## 3.2 大白话

就是：

> Story OS 看到有些图片任务“好像跑过，但不知道最后到底成功还是失败”，所以不敢继续。

它不能直接重试，因为可能发生：

- 图片其实已经生成，只是外层进程没来得及登记；
- 重跑会重复调用图片模型；
- 重复扣候选预算；
- 生成两个不同版本，后续不知道该认哪个；
- provider 已成功，但 ledger/queue 没收到最终回执。

所以当前设计选择 **fail-closed**：

```text
不知道结果
↓
先停
↓
查真实 provider / runner / lifecycle / candidate 证据
↓
确认成功则恢复
确认失败才允许重试
```

这个原则是正确的。

# 四、为什么会产生 interrupted_unknown

主要不是图片模型失败，而是**外层执行窗口与内部长任务生命周期不一致**。

真实生产中，多次出现：

```text
DevSpace 单次调用窗口到期
↓
外层 Python / 调度命令被中断或失去父进程
↓
用户态 Codex / 图片 worker 可能仍继续运行
↓
provider 甚至已经成功生成图片
↓
但 queue / ledger 的最后一步提交没有执行
↓
Story OS 只能标记 interrupted_unknown
```

Frame 15 之前已经证明了这种情况：

- Story OS 认为调度中断；
- Runner 日志实际显示 `returncode=0`；
- `generated_artifacts=1`；
- 请求哈希完全匹配；
- 原始图片真实存在；
- 最终通过 crash-recovery 无重生恢复成功。

因此当前问题本质上是：

> **生产 worker 的真实生命周期长于调用它的宿主执行窗口，但“后端成功 → Story OS 提交账本”的最后一跳还不够抗父进程中断。**

# 五、第一层哪些是正确设计，哪些是框架缺口

## 正确的部分

以下行为必须保留：

- `interrupted_unknown` 不允许直接当失败；
- 不允许盲目重生；
- 必须验证 request hash；
- 必须验证 provider / Runner 成功记录；
- 必须验证真实图片存在；
- 必须验证 Frame Contract；
- 必须验证候选 SHA；
- 恢复后才能写 ledger。

这些都是防止重复计费和错误证据的正确门禁。

## 需要改进的部分

目前恢复仍偏“事后人工触发”。

全自动模式下更合理的是：

```text
发现 interrupted_unknown
↓
自动进入 reconciliation
↓
读取 lifecycle
↓
读取 Runner task record
↓
匹配 request_fingerprint
↓
检查 provider receipt
↓
检查 generated_artifact
↓
成功：自动恢复为 generated
失败：标记 tech_failed
仍无法判断：才 hard_stop
```

也就是说：

> **RECOVER_INTERRUPTED_IMAGES 本身应该成为自动恢复动作，而不应该一出现就等人来输入“继续”。**

只有证据真正不足时才需要人工。

# 八、为什么系统不能自动再修一次 Frame 03

如果系统为了“一键跑完”自动给 Frame 03 第二次内容返修，会直接破坏冻结的生产规则：

```text
max_content_repairs_per_frame = 1
```

这样会产生非常危险的副作用：

- 只要最终评审失败就无限重画；
- 候选预算失控；
- 模型可能越修越漂；
- Story Lock / Visual Lock 失去实际约束力；
- “一次内容返修”变成名义规则；
- 全自动系统为了完成率偷偷降低质量治理标准。

因此当前进入：

```text
NEEDS_USER
```

是**正确的治理行为**。

# 九、这里不是框架 Bug，而是产品决策点

Frame 03 的 `NEEDS_USER` 与之前发现的“最终审图必须先 approved、approved 又要求先审图”的死结不同。

之前那个是**代码闭环缺失**，应该修。

Frame 03 现在是：

```text
生产规则明确只允许一次自动返修
↓
自动返修已经使用
↓
最终评审又发现真实硬问题
↓
系统拒绝擅自消耗第二次内容返修
```

这是治理策略在正常工作。

因此不能简单把 `NEEDS_USER` 当作漏洞删除。

# 十、真正需要改造的是“全自动模式下的人机决策契约”

用户希望：

```text
一句话
↓
无人值守
↓
发布准备完成
```

但当前生产治理同时规定：

```text
每帧最多一次自动内容返修
```

两者在某些真实生产案例中必然冲突。

因此 Story OS 需要显式定义：

## 模式 A：严格全自动

规则：

```text
每帧 1 次自动返修
↓
仍失败
↓
Episode 自动停止
↓
NEEDS_USER
```

优点：

- 质量治理最严格；
- 不会无限烧预算；
- 不会自动越权。

缺点：

- 无法保证每个 Episode 都无人值守到发布。

## 模式 B：无人值守生产

可以增加一个明确、冻结的“异常返修策略”，例如：

```text
ordinary_content_repair = 1
exception_repair = 1
```

但第二次不能默认为普通自动重画，必须满足全部条件：

- 最终权威 critic 明确判 FAIL；
- 问题可修复；
- Story / Storyboard 不变；
- Frame Contract 不变；
- 只针对 critic issue_code 修；
- 记录为 `delegated_exception_repair`；
- 独立计入异常预算；
- 第二次再失败必须 hard stop；
- 禁止第三次自动内容返修。

这样才能既保留治理，又实现更高程度的无人值守。

# 十一、推荐方案

建议不要把现有 `max_content_repairs_per_frame=1` 直接改成 2。

推荐增加第二层独立语义：

```text
普通内容返修：1 次
最终权威评审异常返修：最多 1 次
```

状态语义建议：

```text
ORIGINAL_READY
↓
CONTENT_FAILED
↓
REPAIR_AUTHORIZED
↓
REPAIR_READY
↓
最终评审再次失败
↓
EXCEPTION_REPAIR_REQUIRED
↓
DELEGATED_EXCEPTION_REPAIR_AUTHORIZED
↓
第二次修复
↓
PASS
或
NEEDS_USER_FINAL
```

注意：

这不是新增第二套生命周期。

仍然使用：

- `production-ledger.json`
- 当前 Episode State
- 当前 Repair Queue
- 当前最终语义 critic

只是给现有 repair governance 增加一条受控异常路径。

# 十二、无人值守异常返修必须满足的硬条件

建议必须全部满足：

1. 当前 `execution_mode = full_auto`；
2. 初次内容返修已经消耗；

6. Story Lock SHA 不变；
7. Storyboard SHA 不变；
8. Frame Contract SHA 不变；
9. Character Contract 不变；
10. 不允许扩大剧情；
11. 不允许改变主角身份；
12. 不允许修改世界规则；
13. 第二次返修只允许一次；
14. 再失败立即 `NEEDS_USER_FINAL`；
15. 不能因为想继续生产而修改 critic 规则。

# 十六、为什么现在 next_action 不是直接显示 Frame 03 NEEDS_USER

因为当前更前面还有一层队列恢复阻塞：


```text

4. 对返修结果做最终复审

```

# 十七、当前还暴露出的恢复框架问题

## 问题 1：宿主窗口中断后恢复不够自动

现在：

```text
interrupted_unknown
↓
hard_stop
↓
需要外部再次推动
```

目标：

```text
interrupted_unknown
↓
auto_reconcile
↓
证据充分则自行恢复
↓
继续 pipeline
```

## 问题 2：Runner 成功与 Ledger 提交没有事务性绑定

目前可能发生：

```text
provider 成功
Runner 成功
图片存在
但 queue / ledger 尚未提交
```

建议增加：

```text
provider result journal
↓
immutable commit journal
↓
ledger apply
↓
queue terminal state
```

任何一步重启后都可以 replay。

## 问题 3：长 critic / 长 image worker 缺少 detached 生命周期收口

当前外层调用窗口可能比工作节点短。

应该让：

```text
Story OS Scheduler
↓
提交 task_id
↓
worker 独立执行
↓
Story OS 按 task_id 恢复 / poll / reconcile
```

而不是把“父 shell 还活着”当成 worker 生命周期的一部分。

# 十九、验收标准

## 恢复能力验收

模拟：

```text
图片 provider 成功
↓
在 ledger commit 前杀掉父进程
```

重新启动后必须自动：

```text
识别已有成功产物
↓
校验 request hash
↓
校验图片 SHA
↓
恢复 ledger
↓
不重复生图
↓
继续生产
```

## 异常返修验收

模拟某帧：

```text
第一次生成失败内容评审
↓
普通返修 1 次
↓
最终 semantic critic 又发现可局部修复问题
```

full_auto 下：

```text
自动进入 delegated_exception_repair
↓
只允许 1 次
↓
通过则继续
↓
再次失败则 NEEDS_USER_FINAL
```

## 安全验收

必须证明：

- 普通内容返修仍然最多 1 次；
- 异常返修单独最多 1 次；
- 不存在无限 retry；
- technical failure 不消耗内容返修；
- Story/Storyboard/Frame Contract SHA 漂移时异常返修禁止执行；
- critic 失败不能被系统自动改成 PASS；
- 用户未授权时不得伪造 direct user approval。

# 二十一、大白话总结

当前卡住不是因为 Story OS “不会继续”，而是两个问题撞在一起：

第一：

> **有几个后台图片任务跑到一半时外层执行窗口断了，系统不知道它们到底成功没成功，所以为了不重复花钱，先停下来查账。**

第二：

> **Frame 03 已经自动重画过一次，但最终审图又发现它的相机位置不合理。当前规则规定一张图只能自动重画一次，所以系统不敢偷偷再画第二次。**

前者属于：

```text
恢复自动化能力不足
```

应该修。

后者属于：

```text
现有治理规则主动阻止越权
```

不能简单删掉。

如果目标真的是：

```text
一句话 -> 无人值守 -> 发布准备完成
```

正确改法不是取消限制，而是增加一条严格受控的：

```text
最终权威评审异常返修（最多 1 次）
```

并同时让：

```text
interrupted_unknown -> 自动 reconciliation
```

这样既不会无限重画，也不会每次遇到可修复的小问题就要求用户输入“继续”。
