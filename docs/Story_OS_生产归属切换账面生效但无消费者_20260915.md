# Story OS 生产归属切换：账面生效，但生产侧无消费者

更新时间：2026-09-15

分支：story-platform-v3

基线：`c40b0a2`（2026-09-14）

---

## 一、结论

Phase9 的「生产归属切换」**已经执行并落盘**，台账上当前就是 `V3_RUNTIME`，这一部分是真实的。

但这次切换的动作范围，只是**把一个 JSON 字段从 `V2_RUNTIME` 改成 `V3_RUNTIME`**：

```
episodes/_system（生产真实执行体）对 primary_runtime 的引用数 = 0
```

即：**切换发生了，但生产链上没有任何一个消费者读这个字段。** 生产继续由 V2 引擎执行，不是因为它"拒绝切换"，而是因为它**根本不知道有这次切换**。

`reports/phase9_production_readiness_gate.md` 中「W-11 已解决」在它的判定口径下是成立的，但它查的是**字段值**，不是**谁在读这个字段**——这与该文档 2026-09-14 已自我推翻的 W-03 属于同一类口径问题。

```json
  "previous_runtime": "V2_RUNTIME",

  "updated_at": "2026-09-11T02:05:21.559030+00:00"

```

执行入口：`scripts/phase9_production_switch.py`（P9.34.3，阻塞项 #7）

```
python scripts/phase9_production_switch.py switch --apply
```

该执行器默认 dry-run，`--apply` 才落盘（`scripts/phase9_production_switch.py:96-104`），且只允许 `--to V3_RUNTIME`（`:76`），回退交给 Canary rollback。行为与文档一致，没有实现缺陷。

## 三、但生产侧没有任何消费者

### 证据 1：生产执行体零引用

```
grep -rn "runtime-primary|runtime_primary|V3_RUNTIME|V2_RUNTIME" story_os.py episodes/ runtimes/ config/
→ 唯一命中：config/monitoring/prometheus/prometheus.yml:27  runtime: V3_RUNTIME
```

`config/monitoring/prometheus/prometheus.yml:27` 是 Prometheus 抓取标签（给 Grafana 展示用），不是控制信号。

### 证据 2：生产侧对 platform 包零依赖

```
grep -rn "from platform\.|import platform\." story_os.py episodes/
→ 0 命中
```

全仓库引用 `platform.*` 的只有 `scripts/phase9_*.py` 七个演练/冒烟脚本。生产链从未 import 过 V3 平台层。

### 证据 3：读取方自产自销

`primary_runtime` 的全部读取方都在 `platform/gateway/` 内：

- `canary_production_finalizer.py:17,41,48`
- `phase8_final_release_package.py:32,45`
- `production_migration_audit_report.py:20,47,54`
- `production_migration_completion.py:13,29,38`

这些模块只被 `scripts/phase9_*.py` 调用——**写入方与读取方同属 V3 平台层，形成闭环，生产侧不参与。**

### 证据 4：注册表自己声明了这一点

`platform/gateway/runtime_primary_registry.py:22-24`：

```python
"""Stores current production runtime ownership.

This registry only represents runtime routing truth. It does not replace
episode state, release manifest, or migration evidence.
"""
```

「只代表路由真相」——但**没有任何路由在读它**。

## 四、切换路径上没有就绪门

`scripts/phase9_production_switch.py:65-70`：

```python
def plan_switch(current, target: str, reason: str):
    """纯函数：返回 (new_record, changed)。目标相同则 changed=False。"""
    registry = RuntimePrimaryRegistry(current.primary_runtime)
    new_record = registry.promote_to(target, reason=reason)
    changed = new_record.primary_runtime != current.primary_runtime
    return new_record, changed
```

`RuntimePrimaryRegistry.promote_to`（`runtime_primary_registry.py:37-52`）只比对新旧值，不做任何校验。

对照 `docs/architecture/Story_OS_V3_Phase2_P2.5_Workflow_Migration_Readiness报告_V1.0.md` 与 `platform/workflow/workflow_migration_readiness.py:21-25` 定的三个就绪判据：

```python
ready = (
    event_coverage >= 0.99
    and projection_accuracy >= 0.99
    and shadow_engine_match_rate >= 0.99
)
```

**这三个指标在切换路径上一次都没有被检查过。** 切换执行器与就绪判据之间不存在调用关系。

## 五、为什么门禁报告会写「W-11 已解决」

`reports/phase9_production_readiness_gate.md:5`：

> **W-11 已解决**：`phase9_production_switch.py status` 返回 `primary=V3_RUNTIME`、`reason=production_migration_finalized`。

判定方式是**读 `status` 的返回值**。这个判定在它自己的口径内是正确的——字段值确实是 `V3_RUNTIME`。

问题在于这个口径无法区分下面两件事：

| | 台账 | 生产行为 |
|---|---|---|
| 情况 A：切换生效 | `V3_RUNTIME` | 由 V3 执行 |
| 情况 B：切换未生效（当前） | `V3_RUNTIME` | 由 V2 执行 |

两者在 `status` 输出上**完全一致**。

同一份文档的 `:6` 已经记录了一次同类修正：W-03 早先写「计划任务存在且状态为 Ready」，经二次复核被推翻（`Get-ScheduledTask -TaskName 'StoryOSRuntime'` 全库 0 命中，`scripts/phase9_runtime_deploy.py status` 实测 rc=1 `NotFound`）。

**W-11 与 W-03 是同一类问题：判定读的是"某个声明/字段说了什么"，而不是"有没有东西真的在依赖它"。**

## 六、影响

1. **状态不一致风险（当前最实际的风险）**：台账是 `V3_RUNTIME`，事实是 V2 在跑。若后续有人给 `primary_runtime` 接上消费者（例如让 `episodes/_system` 在非 V3 时拒绝启动），**生产会在那一刻直接停摆**——因为 `platform/` 内不存在创作、门禁、Visual Lock、帧合约、生图调度任何一项生产管线。
2. **迁移进度失真**：Phase8 的「生产闭环最后一步」与 Phase9 阻塞项 #7 被记为闭环（`reports/phase8_production_migration_final_acceptance.md:83`），后续 Phase10 的排期依据建立在此之上（`docs/architecture/Story_OS_V3_Phase7_Implementation_Roadmap实施路线设计_V1.0.md:341`）。
3. **能力缺口被掩盖**：V3 平台层（147 个 py 文件、345 个测试）覆盖数据模型、Workflow 引擎、Agent/Skill/MCP 注册表、Memory、API、Console、Canary、学习闭环；**不覆盖** `VISUAL_CALIBRATED` / `visual_lock` / `frame_contract` / `PRODUCTION_PASSED` / `dag`（在 `platform/` 下逐个搜索，命中数均为 0）。79 份 V3 设计文档中，无一份提及 `episodes/_system` 的迁移路径。

---

## 七、修复方向

### 方案 A：修正判定口径（立即可做，零生产风险）

把 W-11 从「已解决」重开为「**切换已落盘，接管未完成**」，并在就绪门中增加一条必检项：

> 一个归属切换要判定为生效，必须同时满足（1）字段已切换；（2）存在至少一个**生产侧**（`episodes/`、`story_os.py`）的运行时代码路径读取该字段并据此改变行为。

仅满足（1）时，状态应记为「账面切换」，不得计入迁移闭环。

### 方案 B：把缺口变成机器可检（推荐先做）

新增消费者契约测试（放 `tests/system/`，与既有 `test_single_driver_contract.py` 同层）：

```
断言 primary_runtime 至少有一个生产侧读取方；
当前应 FAIL —— 让「无消费者」成为 CI 可见的事实，而不是文档里的描述。
```

这样缺口不会随文档归档而消失，且**不改变任何生产行为**。

### 方案 C：真正的接管（长周期，不在本轮范围）

按 `docs/architecture/Story_OS_V3_Phase7_Implementation_Roadmap实施路线设计_V1.0.md:53-58` 的既定原则：

```
禁止：直接替换 V2.7 Runtime / 直接修改 EP002 生产流程
采用：新增平台层、兼容旧 Runtime、逐步迁移
```

真接管 = 先把生产管线（创作 / 门禁链 / Visual Lock / 帧合约 / 生图调度）在 `platform/` 内建成，再让 `episodes/_system` 读取 `primary_runtime` 并在 `V3_RUNTIME` 时交出执行权。**在该管线建成之前执行此步，等同于删除生产能力。**

### 关于当前状态的处置

`primary_runtime=V3_RUNTIME` 与事实不符，且已埋下第六节第 1 条的风险。两个选择：

- 保持现状，但必须在就绪门中显式标注「账面切换、无消费者」，禁止被下游当作已完成；
- 或先 `switch` 回 `V2_RUNTIME` 使台账与事实一致，待方案 C 完成后重新切换。

**此项需要决策，本轮不单方面变更已落盘状态。**
