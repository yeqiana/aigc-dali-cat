# StoryOS 视觉生产提速、“单图最多生成 2 次”、统一 Model Policy 与 CODEX_MANAGED Cutover 落地方案

**日期：2026-09-30**<br>
**适用范围：StoryOS Production / COLLABORATIVE → CODEX_MANAGED / 图片生产链路 / Model Policy**<br>
**基准 Episode：《未交的答卷》00-04**

---

## 0. Executive Summary

《未交的答卷》真实 Production Pilot 已经证明 StoryOS 的 COLLABORATIVE 架构可用，但真实 Episode 的墙钟周期仍然过长。

本次复盘得到的核心结论：

- 《未交的答卷》从正式 `RUN_START` 到最终接受，墙钟约 **21 小时 37 分**；
- 其中约 **9 小时 51 分**属于明显的过夜停顿；
- 扣除该大段停顿后，真实生产窗口仍约 **11 小时 46 分**；
- Story / Storyboard / PREIMAGE 本身不是主要瓶颈；
- 主要耗时集中在：
  - Visual Lock 前置视觉反复；
  - 20 帧正式出图；
  - Frame Scout / Semantic / Visual Review；
  - Repair；
  - Repair 后重复评审；
  - Final Semantic 收口。

因此下一轮优化的重点不再是单纯增加图片并发，而是：

> **缩短“生成 → 评审 → Repair → 再评审”的视觉质量闭环。**

进一步下钻《未交的答卷》的 Image Worker / Batch Review / Scout 日志后确认：

- Production First Pass 约 3 小时 38 分中，真正 Generation Wave 仅约 **16.6 分钟（7.6%）**；
- 生成完成后等待 Review 约 **95.1 分钟**；
- Review 执行/恢复/落盘约 **84.6 分钟**；
- 因此当前图片链第一性能瓶颈是 **Review / Orchestration 串行闸门**，而不是 Image Provider。

同时新增一个全局生产硬约束：

> **每一个逻辑图片资产，最多只允许发生 2 次真实 Provider 生图尝试。**

这条规则必须覆盖所有生产路径，不能只通过修改普通帧、Visual Lock、technical retry 三处配置实现。

同时，本轮进一步确认：**模型调用入口尚未真正单一收敛**。当前仓库仍同时存在 `config/storyos.yaml`、Python `DEFAULT_MODEL` / `REASONING_EFFORT` 常量、Codex `config.toml`、P4 Capability Router、Runtime Contract / Workflow Contract 等多个模型来源。若直接把默认生产模式切到 `CODEX_MANAGED`，这些旁路会被放大成真实生产行为。

因此新增两项前置决策：

```text
1. 先完成 Unified Model Policy Consolidation；
2. 再在视觉链优化稳定后执行 CODEX_MANAGED Runtime Cutover。
```

本文统一使用以下生产角色模型基线：

```text
Orchestration / Supervisor
= gpt-6-luna / medium

LLM Prompt Authoring
= gpt-6-luna / high

Story Authoring
= gpt-6-luna / high

Semantic Critic
= gpt-6-luna / high
Final Semantic Critic
= gpt-6-luna / high

Fast Vision Review
= gpt-6-luna / low

Visual Lock / Final Vision Review
= gpt-6-luna / high

Image Generation Controller
= gpt-6-luna / high

Image Payload
= gpt-image-2.5-flare / quality=high
```

其中必须明确：

> **`gpt-6-luna` 是图片生成 Controller，不是像素 Payload 模型；真正像素生成仍由 `gpt-image-2.5-flare` + `quality=high` 承担。**

LLM 参与的 Production Prompt / Repair Prompt 统一走 `gpt-6-luna` + `reasoning_effort=high`；纯本地、确定性的 Prompt Package 拼装不应为了“统一模型”而新增 LLM 调用。

# 1. 本轮正式决策

## 1.1 单图全局硬上限

从本方案落地后：

```text
MAX_REAL_IMAGE_GENERATION_ATTEMPTS_PER_ASSET = 2
```

这里的“单图”是指一个**逻辑图片资产 / logical asset**，例如：

- Production Frame 01；
- Production Frame 02；
- Visual Lock baseline；
- Visual Lock admission frame；
- Character Pixel Master；
- Environment / World Image Asset；
- Cover；
- Repair 对应的原逻辑图片；
- 任何其他会真实调用图片 Provider 的 Production Asset。

不是指整个 Episode 只能生成 2 张图。

例如 20 帧 Episode：

```text
Frame 01 最多生成 2 次
Frame 02 最多生成 2 次
...
Frame 20 最多生成 2 次
```

理论极端上限为 40 次真实生成，但正常目标应远低于 40。

---

## 1.2 Canonical Logical Asset Identity

“最多生成 2 次”的计数对象必须先定义清楚，否则 Visual Lock、Production、Repair 可以通过换 scope 绕过额度。

对正式 Frame，统一使用：

```text
logical_asset_key = episode_id + frame_id
```

例如：

```text
00-04/frame-03
```

以下都只是同一个 Logical Asset 的 `attempt_reason / scope`：

```text
original
visual_lock
production
content_repair
technical_retry
authority_refresh
manual_continue
```

它们**不得**进入 Logical Asset Identity。

因此：

```text
Visual Lock Frame03 Attempt 1
Production Frame03 Repair Attempt 2
```

已经用完：

```text
00-04/frame-03 = 2/2
```

后续无论以什么 scope 请求，都必须拒绝第三次 Provider Dispatch。

非 Frame 图片资产使用稳定业务键，例如：

```text
00-04/character/P01/master
00-04/environment/E01/master
00-04/cover/main
```

禁止把 queue item id、candidate id、attempt id、stage 名称当成 Logical Asset Identity。

---

## 1.3 Attempt Reason 与 Asset Identity 分离

每次生成记录：

```text
logical_asset_key
attempt_index
attempt_reason
scope
provider_request_id
generation_key
```

其中：

```text
logical_asset_key
```

决定“这是不是同一张逻辑图片”；

而：

```text
attempt_reason / scope
```

只解释“为什么这次要生成”。

这样可以保证：

> **换 Stage、换 Router、换 Repair 类型、换 Authority Refresh 都不能刷新 2 次硬额度。**

---

# 2. 什么算“一次生图”

必须建立统一定义，否则不同 Runtime 会继续各算各的。

## 2.1 消耗一次额度

满足以下任一条件，即消耗一次真实生图额度：

- StoryOS 已将真实图片 Worker 提交到不可安全撤回的 `WORKER_DISPATCH_COMMITTED`；
- 子 Worker 已观察到 `image_generation` / Provider request；
- 已取得 Provider request / receipt；
- Worker 已提交后发生 timeout / crash / connection broken，无法证明子 Worker 没有调用 Provider；
- Provider 已返回图片，即使后续 Normalize、保存、审查失败；
- Original、Repair、Visual Lock Candidate、Authority Refresh 等任何 scope 发生新的真实 Generation Dispatch。

原则：

> **当前 Codex Subscription 路径无法精确控制子 Worker 内部 Provider 调用边界，因此从 `WORKER_DISPATCH_COMMITTED` 起 fail-closed 计费：宁可保守占一次，也不能把可能已经生过图的额度重新放出去。**

---

## 2.2 不消耗额度

以下行为不算生图次数：

- Prompt 构建；
- Prompt Review；
- Local Visual Triage；
- Frame Contract 生成；
- Queue 创建；
- Scheduler 排队；
- 尚未真正发到 Provider 的本地技术失败；
- 已存在图片的 Normalize / Resize / Crop；
- 对同一 Provider 结果的幂等恢复；
- Same Episode Resume 后复用已有 receipt；
- 数据库 / Ledger replay；
- Scout / Semantic / Vision Review；
- 字幕、视频、Release；
- 对已有图片进行纯读取分析。

# 3. 新的统一预算模型

当前 StoryOS 分别存在：

```text
普通 Content Repair 限制
Visual Lock Candidate Pool
Technical Retry
Raw Candidate Budget
Authority Refresh
```

这些限制彼此独立，因此即使每一项自身“有界”，叠加后仍可能让同一个逻辑图片超过 2 次真实生成。

本次必须改成：

```text
                ┌─ original
                ├─ content repair
Logical Asset ──┼─ visual lock candidate
                ├─ technical retry
                └─ authority refresh

                     ↓

         Unified Image Generation Budget

                     ↓

             HARD MAX = 2
```

所有路径共享同一个计数器。

---

## 3.1 唯一 Generation Attempt Authority

本次不能让：

```text
raw_candidate_budget
production_ledger
scheduler
web console projection
```

分别维护一份 `used / remaining` 并同时参与决策。

必须确定唯一子资源 Authority：

```text
Generation Attempt Ledger
```

职责仅限图片 Attempt：

```text
logical asset identity
attempt claim
attempt reservation
provider dispatch consumption
attempt terminal state
idempotency
remaining budget
```

其他系统：

```text
Production Ledger
raw-candidate-budget.json
Web Console
Performance Report
```

全部只是该 Authority 的 projection / evidence，不得反向决定剩余额度。

Episode State 仍然是 Episode Phase 的唯一 Authority；Generation Attempt Ledger 只是图片 Attempt 子资源 Authority，两者职责分离。

### Durable Store 固定为 MySQL

当前 StoryOS 正式存储拓扑已经是：

```text
runtime_store      = MySQL
episode_meta_store = MySQL
hot_state          = Redis
```

因此 Generation Attempt Ledger 不再保留“文件 / Redis / MySQL 三选一”的实现自由度。正式 Production 约定：

```text
MySQL = durable Attempt Authority
Redis = 可重建 hot projection / cache
JSON  = compatibility / debug projection
```

MySQL 至少必须提供唯一约束：

```text
UNIQUE(episode_id, logical_asset_key, attempt_index)
```

并持久化 Lease / Fencing / Terminal 状态。Redis 和 JSON 都不得反向决定 Attempt 剩余额度。

---

## 3.2 Atomic Attempt Lease

并发下不能只做：

```python
if used < 2:
    dispatch()
```

否则不仅可能两个 Worker 抢最后一个额度，还可能在 `used=0, hard_cap=2` 时让同一 Frame 的 Attempt 1 和 Attempt 2 **同时在途**。

正式约束增加：

```text
MAX_PROVIDER_ATTEMPTS_PER_LOGICAL_ASSET = 2
MAX_INFLIGHT_ATTEMPTS_PER_LOGICAL_ASSET = 1
```

即：第二次机会只能在第一次进入 Terminal，并经过 Review / Technical Decision 确认确实需要以后才可申请。

### Attempt 生命周期

当前 Codex Subscription 图片路径不是 StoryOS 直接 HTTP 调 Provider，而是：

```text
codex_subscription_image.py
→ invoke_codex()
→ codex_user_runner.run_codex()
→ 子 Codex Worker
→ image_generation
```

父 Runtime 无法保证精确知道子 Worker 在哪一毫秒真正调用了 `image_generation`。因此安全状态机改为：

```text
REQUESTED
   ↓
RESERVED
   ↓
WORKER_DISPATCH_COMMITTED
   ↓
IMAGE_GENERATION_OBSERVED   （有事件时记录；不是安全计费前提）
   ↓
SUCCEEDED
或
FAILED_AFTER_DISPATCH
```

规则：

```text
RESERVED 之前失败
→ 不占 Attempt

RESERVED 后、WORKER_DISPATCH_COMMITTED 前失败
→ release reservation
→ 不占 Attempt

进入 WORKER_DISPATCH_COMMITTED
→ Attempt 永久消耗
```

即使随后发生：

```text
timeout
worker crash
receipt missing
unknown outcome
```

也不得返还 Attempt。原则是：

> **无法证明子 Worker 没有机会调用真实 image_generation 时，宁可保守消耗一次，也不能把额度重新放出去导致第三次。**

### Single Inflight

例如：

```text
Frame03 used=0

Worker A → RESERVED attempt-1
Worker B → DENIED: ASSET_ATTEMPT_INFLIGHT
```

不能出现 Attempt 1 / Attempt 2 同时跑。

### Lease Fencing

每个 Lease 还必须带：

```text
lease_id
fencing_token
owner
reserved_at
expires_at
```

避免旧 Worker 在 Lease 被回收后“复活”：

```text
Lease A fencing=17
→ 超时回收
Lease B fencing=18

旧 Worker A 恢复
→ Gateway 发现 17 != 18
→ DENY
```

`reserve_next_attempt()`、Lease 回收、fencing token 增长必须依赖 MySQL 事务 / 唯一约束保证，不得只依赖进程内锁。

---

## 3.3 Stable Generation Key

Frame 的 `logical_asset_key` 本身已经包含 Episode 身份，例如：

```text
00-04/frame-07
```

因此真实 Attempt 的稳定键直接定义为：

```text
generation_key = logical_asset_key + "/attempt-" + attempt_index
```

例如：

```text
00-04/frame-07/attempt-1
00-04/frame-07/attempt-2
```

同一 `generation_key`：

```text
最多一个 WORKER_DISPATCH_COMMITTED
最多一个有效 Provider Dispatch 语义
```

Resume / Replay 发现已有：

```text
runner_request_id
receipt
raw image
candidate
terminal attempt evidence
```

必须绑定并恢复原 Attempt，不得创建新 `generation_key`。

---

## 3.4 ImageGenerationGateway 最后一层硬 Guard

不能只在 Next Action 或 Scheduler 做检查，因为历史代码可能仍存在：

```text
direct generate
repair CLI
Visual Lock direct path
authority refresh path
debug/manual production path
```

但 Gateway 也不能粗暴包住整个 `generate_for_frame()`，因为当前真实代码里它还包含两类**不应新增 Provider Attempt** 的合法路径：

```text
_recovered_codex_raw
STORY_OS_MANUAL_RAW_DIR
```

因此正式拆分语义应为：

```text
ImageArtifactPipeline
├─ provider_generate()      ← 必须有效 Attempt Lease + fencing token
├─ recover_existing_raw()   ← 绑定已有 Attempt，不新增 Attempt
├─ adopt_user_asset()       ← 不调用 Provider，不新增 Attempt
└─ normalize_candidate()    ← 不调用 Provider，不新增 Attempt
```

真正的最后一层 Guard 只保护：

```text
REAL_GENERATION_DISPATCH
```

Gateway 调用必须携带：

```text
logical_asset_key
attempt_index
lease_id
fencing_token
generation_key
attempt_reason
```

没有有效 Lease、fencing token 过期、同 Asset 已有 active Attempt，全部：

```text
REAL_GENERATION_DISPATCH_DENIED
```

最终防线：

```text
Next Action Guard
        ↓
Scheduler Guard
        ↓
Atomic Attempt Lease + Single Inflight
        ↓
ImageGenerationGateway Lease/Fencing Guard
        ↓
WORKER_DISPATCH_COMMITTED
        ↓
Codex User Runner / Provider Worker
```

Recovery、Replay、用户提供已有图片、`media/publish` 已确认资产，都走 Artifact Adoption / Recovery，不得伪装成一次新的 Provider Generation。

# 4. 统一硬规则

## 4.1 普通帧

当前普通帧已经是：

```text
首次生成 1 次
+
内容返修最多 1 次
=
最多 2 轮内容生成
```

因此：

```yaml
production:
  max_content_repairs_per_frame: 1
```

可以继续保持。

但它必须受新的全局硬预算控制。

例如：

### 正常情况

```text
Original = 1
Content Repair = 1
Total = 2
→ 禁止任何第三次生成
```

### 首次成功直接 PASS

```text
Original = 1
Total = 1
→ 完成，不使用第二次额度
```

# 5. Visual Lock 改造

当前仓库配置：

```yaml
visual_lock_baseline_pool:
  enabled: true
  max_additional_candidates: 2

visual_lock_admission_pool:
  enabled: true
  max_additional_candidates_per_frame: 2
```

这意味着：

```text
原始候选 1
+ 普通返修 1
+ additional candidate 最多 2
```

在部分路径上可能出现多于 2 个真实候选。

这是本轮必须修改的重点。

---

## 5.1 新规则

Visual Lock 的每个逻辑资产：

```text
最多只有 2 次真实生图机会
```

推荐配置改为：

```yaml
production:
  visual_lock_baseline_pool:
    enabled: true
    max_additional_candidates: 1

  visual_lock_admission_pool:
    enabled: true
    max_additional_candidates_per_frame: 1
```

但仅改成 `1` 仍然不够。

必须同时由统一预算判断：

```text
remaining_generation_budget = 2 - provider_attempts_used
```

如果前面已经使用过一次 Repair：

```text
Original = 1
Repair = 1
Remaining = 0
```

则：

```text
Visual Lock Additional Candidate = 禁止
```

不能再因为 Visual Lock 自己还有 Candidate Pool 就生成第三张。

---

# 6. Technical Retry 改造

当前配置：

```yaml
technical_retry:
  max_attempts_per_item: 3
  backoff_seconds: [15, 45]
```

当前设计允许：

> 同一个生成任务在技术失败时最多进行 3 次 backend attempt。

本轮改为：

```yaml
technical_retry:
  max_attempts_per_item: 2
  backoff_seconds: [15]
```

但同样需要服从统一预算。

---

## 6.1 技术失败也必须占用全局真实生图预算

新规则：

```text
只要真实图片 Worker 已进入 WORKER_DISPATCH_COMMITTED，
就把这次机会视为已消耗。
```

如果后续能观测到真实 `image_generation` 事件，则追加 `IMAGE_GENERATION_OBSERVED` 证据，但这不是是否计费的前提。

例如：

```text
Attempt 1:
Provider 请求发出
→ Timeout
→ 无法证明 Provider 没执行
→ used = 1

Attempt 2:
再次请求
→ 成功
→ used = 2

后续内容评审 FAIL
→ 不允许再 Repair
→ GENERATION_BUDGET_EXHAUSTED
```

这与当前“技术重试不占内容返修次数”的语义并不冲突。

它仍然可以：

```text
technical_retry_counts_as_content_repair = false
```

但是：

```text
Technical Retry 不占 Content Repair Counter
≠
Technical Retry 不占 Real Generation Budget
```

必须把这两个概念彻底分开。

---

# 7. Provider 前失败的处理

为避免把本地错误误算成一次生图：

### 不消耗额度

如果在以下阶段失败：

```text
Prompt Build
Contract Validation
Queue
Scheduler
Capability Router
Local IO
WORKER_DISPATCH_COMMITTED 之前
```

则不消耗真实生成预算。

### 消耗额度

如果已经无法证明请求没有送到 Provider：

```text
worker dispatch committed
connection broken
provider timeout
receipt uncertain
worker outcome unknown after committed worker dispatch
```

则 fail-closed：

```text
消耗 1 次
```

宁愿少一次，也不能因为状态不确定无限重试。

# 8. Budget Exhausted 后怎么办

当某个 Logical Asset：

```text
provider_attempts_used >= 2
```

图片执行层必须返回：

```json
{
  "action": "STOP_GENERATION",
  "reason_code": "GENERATION_BUDGET_EXHAUSTED"
}
```

注意：

> `GENERATION_BUDGET_EXHAUSTED` 是 execution / blocker reason code，不是新的 Episode State，也不是新的 Production Phase。

Scheduler / Router / Repair / Visual Lock / Final Semantic 都不得再创建新的图片生成任务。

Episode State 仍按 StoryOS 现有 Authority 规则，根据实际原因保持或进入现有状态，例如：

```text
ACTIVE
NEEDS_USER
CAPABILITY_WAIT
```

不得为本方案新增第二套 Phase State。

---

## 8.1 内容问题

如果两次图都已生成，但内容质量仍不满足自动 Gate：

```text
Generation = STOP
```

然后根据现有 Gate：

```text
已有候选中存在可接受结果
→ 选择 best existing candidate
→ 继续人工/正式 acceptance

已有候选均不可接受
→ NEEDS_USER
```

不得偷偷再生成第三张。

---

## 8.2 技术问题

如果两次 Provider Attempt 都失败：

```text
Generation = STOP
```

状态应按现有状态机进入：

```text
CAPABILITY_WAIT
或
NEEDS_USER
```

不得把第三次 technical retry 当成“技术问题，不算生图”。

---

# 9. Authority Refresh 不能绕过硬上限

StoryOS 当前还存在：

```text
authority_refresh
raw-candidate-budget override
user continuation
```

这些机制历史上用于处理 stale contract、candidate budget 等问题。

本轮要求：

> **任何 override 都不得把单个 Logical Asset 的真实 Provider Attempt 上限提高到 2 以上。**

即：

```text
Episode Budget Override
可以影响 Episode 总额度
但不能突破 per-asset hard cap = 2
```

```text
Authority Refresh
可以刷新 authority / contract
但如果需要重新调用 Provider：
仍然必须检查 remaining budget
```

如果已经：

```text
used = 2
```

# 10. Resume / Replay 规则

必须避免因为恢复流程重复计数。

Same Episode Resume 时：

### 不新增额度

```text
已有 request_id
已有 provider receipt
已有 raw image
已有 normalized candidate
```

则恢复原任务：

```text
REPLAY / REUSE
```

不得重新调用 Provider。

---

## 10.1 幂等约束

同一个：

```text
episode
asset_key
attempt_index
```

必须对应唯一 Provider Dispatch。

建议生成稳定键：

```text
image_generation_key =
episode_id
+ logical_asset_key
+ provider_attempt_index
```

例如：

```text
00-04/frame-07/attempt-1
00-04/frame-07/attempt-2
```

任何第三个：

```text
00-04/frame-07/attempt-3
```

都应在 Scheduler 前直接拒绝。

---

## 10.2 Episode Model Policy Freeze

Resume / Replay 除了保证 `generation_key` 幂等，还必须保证**同一 Episode 的模型策略不会因为全局配置变化而漂移**。

新 Episode 必须在 **Runtime Request Bind 完成后、第一次任何模型执行之前**冻结；不能等到 Production / CODEX_MANAGED 中后段才冻结：

```text
Runtime Request Bind
→ Global config/storyos.yaml#models
→ model_policy.resolve_all()
→ validate capabilities
→ Episode Bound Model Policy Snapshot
→ FIRST MODEL EXECUTION
```

冻结内容至少包括：

```text
model_policy_version
model_policy_sha256
resolved role -> model / reasoning_effort
image payload model / quality
policy source
fallback candidate chain
```

该 Snapshot 绑定到 Runtime Request / Execution Capsule 的 canonical projection，并覆盖整集：

```text
Concept
→ Story
→ Storyboard
→ PREIMAGE
→ Prompt
→ Image
→ Review
→ Repair
→ Release
```

不能出现“Story 用 V1、Production 才冻结 V2”的半集漂移。

规则：

```text
新 Episode：
读取最新 Global Model Policy
→ validate
→ freeze

已绑定 Episode：
继续使用 Episode Bound Policy
→ 全局 models.* 改动不能自动改变该 Episode

本版本不支持运行中自动 Model Policy Migration：
→ 已绑定 Episode 一律继续旧 Policy
→ 新 Episode 才使用新 Policy
→ 紧急人工迁移作为运维例外，不纳入本版本自动能力
```

禁止 Resume 后出现：

```text
Attempt 1 / Prompt 1 = Model A
全局配置变化
Attempt 2 / Prompt 2 = Model B
```

本版本默认禁止这种中途切换；如发生紧急人工迁移，必须显式记录运维 evidence，且不作为普通生产路径。

Codex 本机 `config.toml` 的 `model` / `model_reasoning_effort` 只能作为人工直接使用 CLI 的默认值，不是 StoryOS Production Authority。

## 10.3 Episode Model Policy Snapshot：复用现有 Persistence

不新增一套独立的 Model Policy 数据库子系统。直接复用 StoryOS 已有 `episode_meta_store=mysql` / payload persistence 模式，新增一个轻量 `model_policy_persistence.py` 即可。

```text
Global Authority
= config/storyos.yaml#models

Episode Bound Authority
= existing MySQL episode_meta_store 中的一份 immutable JSON payload

meta/runtime/model-policy-snapshot.json
= compatibility / debug projection

Execution Capsule
= consumer snapshot
```

最小 payload：

```text
schema_version
policy_version
policy_sha256
bound_at
profiles
role_aliases
fallback_candidates
```

不拆 role 为独立数据库列，不新增复杂 migration graph。MySQL-only 模式无法读取已绑定 Policy 时 fail-closed。

### Model Fallback × Provider Attempt 状态机

fallback 必须和真实 Provider Attempt Boundary 统一判断，不能只看“模型是否换了”。

```text
A. WORKER_DISPATCH_COMMITTED 之前
MODEL_UNAVAILABLE / PROVIDER_CAPACITY
→ Policy 可以推进到下一个 fallback candidate
→ 不消耗 Provider Attempt
→ 不需要新的 Attempt Lease

B. WORKER_DISPATCH_COMMITTED 之后
Model A failure / unknown outcome
→ 当前 Attempt 永久消耗
→ Policy 若允许 fallback 到 Model B
→ 必须重新 reserve 下一 Attempt Lease
→ Attempt 2 才允许再次 Dispatch

C. used = 2
→ 即使还有 fallback candidate
→ DENY
→ 不得生成 Attempt 3
```

默认可触发模型 fallback 的 failure class 只包括：

```text
MODEL_UNAVAILABLE
PROVIDER_CAPACITY
```

默认不得通过换模型自动规避：

```text
AUTH_401
PERMISSION_403
CONTENT_FAILURE
POLICY_REJECTION
```

`429 / 5xx / NETWORK_ERROR` 走 technical retry policy；若已经越过 `WORKER_DISPATCH_COMMITTED`，仍计入同一 2-Attempt Hard Cap。

任何 fallback Receipt 必须同时记录：

```text
attempt_index
dispatch_commit_state
failure_class
from_model
to_model
fallback_candidate_index
attempt_consumed
remaining_provider_attempts
```

禁止新生产代码继续出现：

```text
DEFAULT_MODEL = "gpt-..."
REASONING_EFFORT = "..."
从 ~/.codex/config.toml 读取业务 preferred_model

Workflow Contract 再维护第二套 default_image_model
```

迁移期允许旧字段作为**只读兼容别名 / projection**，但必须：

```text
legacy alias == models.* resolved value
```

发现漂移直接 fail-fast；新代码不得继续读取 legacy 模型字段。

最终状态：

```text
人工只改 config/storyos.yaml#models
```

## 12.6 CODEX_MANAGED Supervisor / Scoped Worker 边界

默认模式未来切换：

```yaml
production:
  mode: CODEX_MANAGED
```

但“全自动”不等于“一个 Codex Session 从头干到尾”。

正式结构必须保持**确定性 Runtime 编排唯一 Authority**：

```text
StoryOS Runtime DAG / Scheduler
        ↓
resolve next deterministic task / dependency / concurrency
        ↓
Model Policy
        ↓
P4 Provider / Runner resolution
        ↓
Scoped Codex Worker + Frozen Capsule
        ↓
Candidate / Decision
        ↓
StoryOS Verifier / Gate
        ↓
Authority Commit
```

`orchestration` Role 通过 Profile 解析后，只能承担 **advisory planning / diagnosis / bounded exception analysis**，不得成为第二套 Scheduler，也不得独立决定：

```text
Episode Stage
Next canonical DAG node
Gate PASS
Attempt Budget
Concurrency ownership
Provider dispatch authorization
Authority Commit
```

因此 CODEX_MANAGED 的含义是：

> **所有需要模型的业务节点由 Codex 自动执行；不是把 StoryOS 的 DAG / Scheduler / Gate Authority 交给一个长 Codex Session。**

Supervisor / advisory model 不应在同一长 Session 内直接包办 Story、20 条 Prompt、20 张图审核和 Release。

必须继续保持：

```text
StoryOS Runtime DAG / Scheduler = Orchestration Authority
Codex Scoped Worker            = Model Execution Worker
StoryOS                         = State / Contract / Gate Authority
```

任何 Episode Stage / Gate 推进仍只允许通过正式 Verifier + Authority Commit。

## 12.7 Model Policy Idempotency / Reuse Identity

Model Policy SHA 必须进入 Runtime 幂等身份，避免不同 Policy 的结果互相复用。

```text
step_input_hash = SHA256(runtime_request_sha + evidence_sha + model_policy_sha256 + resolved_role)

worker_fingerprint = SHA256(step + source_sha + model + effort + model_policy_sha256)
```

本版本不实现运行中自动 Policy Migration；这套 identity 主要保证历史 Episode Resume 和紧急人工迁移时不会错误复用旧结果。

# 17D. Generation Lane 与 Review Lane 必须解耦

当前真实运行效果近似：

```text
Batch 生成
↓
等待
↓
Batch Review
↓
等待
↓
下一 Batch
```

目标：

```text
Generation Pool（持续并发）
    │
    ├─ Frame 01 ─────────┐
    ├─ Frame 02 ──────┐  │
    ├─ Frame 03 ───┐  │  │
    ├─ Frame 04 ─┐ │  │  │
    └─ Frame 05  │ │  │  │
                 ↓ ↓  ↓  ↓
             Review Queue
                 ↓
           Review Worker Pool
                 ↓
            Repair Aggregator
                 ↓
           One Repair Wave
```

硬要求：

```text
Review 不阻塞下一张 Original Image 的生产
Review 不占 Image Worker Slot
Generation 按 max_inflight 持续 refill
```

---

## 17D.1 双 Lane 必须有 Review Backpressure

“Review 不阻塞 Generation”不是“永远无条件继续生成”。

Review Runtime 已经真实出现：

```text
429 Too Many Requests
websocket reconnect
```

因此必须有独立配置：

```yaml
review_runtime:
  max_inflight_reviews: 2
  queue_backpressure_threshold: 8
  max_oldest_review_age_seconds: 300
```

具体阈值由压测确定，不能写死在业务代码中。

行为：

```text
Review Queue 正常
→ Generation 持续 refill

Review Queue 过深
→ Generation 自适应降并发

Oldest Review Age 超阈值
→ 暂停新的 refill

Review 恢复
→ 自动恢复 Generation 并发
```

Review Worker 不得占 Image Worker Slot。

为避免队列在阈值附近反复 5→4→5 抖动，Backpressure 必须使用 hysteresis：

```text
high_watermark = 8   → throttle / pause refill
low_watermark  = 4   → 才允许恢复
```

具体数值由压测确定，但必须是“高水位触发、低水位恢复”的双阈值，不得只有单一 threshold。

---

## 17D.2 Review Backpressure + 复用现有 Circuit Breaker

本版本不新建第二套系统性缺陷熔断框架。仓库已有 `runtime_circuit_breaker.py` 和 Image Worker 接线，直接复用。

第一版只做两个必要动作：

```text
review_queue >= high_watermark
→ throttle / pause generation refill

review_queue <= low_watermark
→ resume refill
```

现有 Circuit Breaker 继续处理明显技术/重复失败；复杂 `systemic_issue_signature` 聚合留到真实 CODEX_MANAGED Pilot 证明有需要后再扩。

已在途 Provider Attempt 不强杀。

# 25. Final Semantic 前移，Repair 后只验证不再生成

```text
→ First-Pass Final Semantic
```

### used = 1

只允许生成一个：

```text

```

由 Repair Aggregator 汇总后进入唯一一次 Repair Wave。

### used = 2

```text

或
NEEDS_USER
```

### Repair Wave 完成以后

无论：

```text

还是 2
```

# 28. 新生产 SLA 与统一耗时定义

此前“First Pass”存在多种口径，必须统一为三个指标：

```text
Generation First Pass
= 第一张 Original Provider Dispatch
→ 所有 Original Candidate Ready

Production Review Closure
= 第一张 Original Provider Dispatch
→ 所有 First-Pass Review Terminal

Image Production Closure
= 第一张 Original Provider Dispatch
→ ONE Repair Wave Incremental Verify Terminal
```

20 帧常规 Episode 第一阶段 SLA：

| 指标 | 第一阶段 Gate | 成熟目标 |
|---|---:|---:|
| Generation First Pass | <= 30 min | 15–30 min |
| Production Review Closure | <= 60 min | 30–60 min |
| Image Production Closure | <= 120 min | 60–120 min |
| Visual Lock | <= 40 min | 20–40 min |
| Final Semantic First-Pass | <= 15 min | 5–10 min |
| Subtitle / Video / Release | <= 20 min | 10–20 min |

同时必须固定三套性能时钟，避免 Session Restart 后只看 `latest_session_active_seconds` 造成“假提速”：

```text
Episode Elapsed Wall
= 第一次正式 Production Start → Production Closure
= 包含用户等待在内的真实日历墙钟

Pipeline Controlled Wall
= ACTIVE
+ internal queue wait
+ review wait
+ backpressure
+ provider wait
= 不包含 USER_WAIT

External / User Wait
= USER_WAIT + 明确外部人工等待
```

正式性能 Gate 优先使用：

```text
Image Production Closure
Pipeline Controlled Wall
```

不得以 `latest_session_active_seconds` 作为跨 Resume / Restart 的最终验收口径。

Episode 整体第一阶段目标：

```text
Pipeline Controlled Wall <= 6h
阶段目标：<= 4h
Stretch SLA：1.5 ～ 3h
```

`1.5～3h` 保留为成熟目标，不作为第一次改造上线唯一 PASS 条件。

允许读取、审计、Resume。


```text

```

禁止任何新 Provider Dispatch。

## 32.1 Legacy Attempt Reconciliation

上线时对历史 Episode 建立只读 reconciliation：

```text

→ 回放生成 logical_asset_key
→ 计算 historical_provider_attempts_used
```

不删除、不重写历史。

如果历史记录无法明确区分 Worker 是否已经进入不可安全撤回的真实图片执行边界：

```text

```

将不确定的已发送任务按已消耗 Attempt 处理。

## 32.2 Episode Hard Ceiling 动态计算

Episode 总硬上限不得固定写成：

```text
35
40
```

而应从 canonical image asset plan 动态计算：

```text
episode_hard_generation_cap =
Σ logical_asset.provider_attempt_cap
```

例如：

```text

+ 1 Cover
= 21 Logical Assets
hard cap = 42
```

Visual Lock Frame 如果就是 Production Frame 本身，不重复计 Logical Asset。

同时可以保留成本预警：

```text
expected_budget
warning_threshold
hard_ceiling
```

例如：

```text
expected = 21
warning  = 26
hard     = 42
```

成本异常告警与合法 Second Attempt 分离。

# 36. 风险

最大的风险是：

> 严格限制成 2 次之后，低质量首图会更容易导致 NEEDS_USER。

因此不能只做“砍次数”。

必须同步提高：

```text
PREIMAGE
Frame Contract
Prompt
Reference Binding
Visual Lock Prompt Quality
First Pass Quality
```

核心目标不是：

```text
少生成但质量变差
```

而是：

```text
把判断和约束前移，让第一次就更接近可用，
第二次成为真正的最后修复机会。
```

模型与 Runtime 还有两类新增风险：

```text
1. Model Policy 版本变化导致同一 Episode 前后行为漂移；
2. CODEX_MANAGED 被误实现成“一个超长 Session 包办全链”，造成上下文污染、不可恢复和 Authority 模糊。
```

对应控制：

```text
Episode Bound Model Policy Freeze
Scoped Worker + Frozen Capsule
P4 Provider-only Routing
StoryOS Gate / State Authority 不变
```

# 37. 最终生产原则

从本方案实施完成后，StoryOS 图片 Production 应遵循：

```text
每个 Logical Image Asset：

第一次
= 正式首轮

第二次
= 唯一最后机会
  （可能是技术重试，也可能是内容 Repair，也可能是 Visual Candidate）

第三次
= 永远禁止
```

即：

> **不是“内容最多修一次，同时技术还能再试三次”。**

而是：

> **只要是真实 Provider 生图，不管为什么生成，单个逻辑图片资产总共最多两次。**

这条规则必须由：

```text
Generation Attempt Authority
+ Atomic Attempt Lease
+ Scheduler Guard
+ ImageGenerationGateway Hard Guard
```

共同保证，不能依赖各阶段自觉遵守。
