# StoryOS 本轮改造后暴露问题与运行慢归因（2026-09-29）

## 范围与结论

本记录针对 `04_未交的答卷` 的 `run_resident_bounded.py` 运行慢问题，结合本地只读性能剖析、Episode 运行证据和 WebCodex 本机日志。**目前可直接归因的本地瓶颈是 `next_action.derive` 的串行远程 MySQL 读取与重复 Frame Contract 编译**。WebCodex 日志另显示长轮询、较慢的 `run_process` 调用和持续的 receipt 持久化告警；现有日志没有把这些调用与本 Episode 的 request ID 一一绑定，不能将它们全部计入 Episode 耗时。

本次只读调查没有重跑生产、模型或图片任务，也没有修改 Episode 状态。下表中的 `host_wait` 是 StoryOS 观察到的等待时间，不等同于 WebCodex 宿主的模型实际执行时间。

## 大白话解释

现在的慢，像是每走一步都要重新翻一大摞远处仓库里的档案：StoryOS 只是想判断“下一步该做什么”，却会反复从远程数据库取合同、重新编译画面要求。光这一次判断就实测花了约 40–48 秒。WebCodex 近期几个“查看当前进度”的作业，也各花了约 47–95 秒；频繁查看会让人感觉系统一直在慢慢转。

正式生产还要等图片生成、图片审核和失败后的恢复。有些作业显示运行几分钟，确实是在做这些工作；有些时间只是等待宿主返回消息，不能算成模型一直在执行。另有一次审核恢复因图片候选与 Ledger 状态冲突而失败，白花了约 70 秒。**先该处理的是重复查数据库和重复计算，以及查清这次状态冲突；不能只把超时时间调大或把“等待”当作根因。**

## 本轮 P1 性能修复实测（同日续测）

针对上文 P1 的 `next_action.derive` 远程读取放大，本轮已落地**单次 operation/request 范围内**的读取去重；没有引入跨 resident cycle 的长期 Authority 缓存。

已实施：
- `next_action.derive` 统一包裹 Episode Contract operation scope，使嵌套 Frame Contract / Review 检查共享同一次合同读取缓存。
- MySQL 为唯一 Authority 时，明确的“合同不存在”结果也可在本次 operation 内缓存；任一 `persist()` 仍按 contract type 立即失效。
- Production Ledger Authority 在本次 operation 内只读取一次并返回隔离副本；`persist_authority()` 成功后立即失效。
- StoryOS YAML 已有 mtime 内容缓存；本轮新增的只是“本次 operation 只做一次完整 validate”，不跨 cycle 固化配置。

同一 `04_未交的答卷`、同一当前状态下的对比：
- 初始问题记录：单次 `derive` 约 39.5 秒；另一轮 cProfile 约 47.893 秒。
- 本轮额外保留的一次旧路径对照：67.848 秒，MySQL Episode Contract `get_latest=234`。
- 只加 derive umbrella scope 后：51.213 秒，`get_latest=186`。
- 加 authoritative negative-result operation cache 后：8.540 秒，`get_latest=5`。
- 再加 Production Ledger operation snapshot 后：5.377 秒，Ledger Authority MySQL `get=1`。
- 最终三次独立新路径采样：5.806 / 5.378 / 6.801 秒，中位数 **5.806 秒**；每次 `storyos_config.validate=1`、Episode Contract MySQL `get_latest=5`、Production Ledger Authority MySQL `get=1`。
- 以上新旧路径的核心派生结果一致；当前均为 `REVIEW_GENERATED_IMAGES`，batch=`BATCH_ee35e243c582`，`hard_stop=false`。

结论：
- P1 “`next_action.derive` 远程读取放大”已从几十秒级降到约 6 秒级，当前可视为**主要瓶颈已缓解**。
- 剩余约数秒主要仍来自 Frame Contract / Batch Review 的真实派生与少量远程 Authority 读取。本轮**不继续做跨 cycle Frame Contract 长缓存**，避免以陈旧 Authority 换速度。
- 下一阶段若继续优化，应以 operation-scoped Frame Contract/shared-derived memoization 为主，并继续要求：同状态派生结果 SHA/核心 action 不漂移、Authority 写入即时失效、跨 cycle 必须重新观察最新状态。

## 生产现场续测：写路径、Repair 与预算调度

在继续生产 `04_未交的答卷` 时，又暴露并处理了三类与“慢/重复执行风险”直接相关的问题：

- **Production Ledger typed projection 写放大**：完整 Authority BLOB 仍然每次原子写入 MySQL，但旧实现随后会把所有 frame 与所有 attempt 的 typed projection 全量 `upsert`。Frame16 单次 repair authorization 曾因此在远程 MySQL 中途触发 2013 断线。现已改为：事务内读取旧 authority，只对 payload 实际变化的 frame 重写 typed projection；首次写仍全量投影，完整 Authority 语义不变。专测验证首次 2 frame/1 attempt 全量写，后续仅 Frame02 状态变化时只写 1 frame/0 attempt。
- **Review → Repair 信息丢失**：Production Batch Vision Review 的 issue/reason 原先落在 `vision_batch_review`，而 `enqueue_marked_repairs()` 只读取旧的 `work_batch_review/scout/repair_assessment`，会导致 repair prompt 退化为泛化原因。现已把 `vision_batch_review` 纳入 repair finding 汇总，Frame16 的 `GHOST_CAMERA_ALL_PARTICIPANTS_VISIBLE`、`P01_WARDROBE_AND_ROLE_DRIFT` 等具体问题可进入返修指令。
- **superseded original 被误判为“未生产”**：repair 入队会把原 original queue row 标成 `superseded`。旧 `_represented_original_frames()` 直接排除所有 superseded row，导致已经真实生成过的帧重新触发 `PREPARE_PRODUCTION_BATCH`。现改为：superseded original 只要保留真实 `output_path`，仍算 production representation；无输出的 superseded row 仍不计入。
- **Episode 总预算守卫位置过晚**：旧 image scheduler 先把 queued repair admission 为 running，再由 worker 内 `raw_candidate_budget.claim()` 才发现 Episode budget 已耗尽，造成 04/05/06/14 已 dispatch 后才被 `RAW_CANDIDATE_BUDGET_EXHAUSTED` 挡住。现已在 scheduler admission 前读取 `raw_candidate_budget.summary().available`；为 0 时不再把新 repair 标成 running，也不启动 worker。

本次真实 Episode 现场结果：

- 图片候选预算上限：35；当前 `committed=35`、`inflight_reserved=0`、`available=0`。
- 成功生成的 Production Review repair：Frame07、09、10、11、13、16，均已进入 `REPAIR_READY`。
- 因总预算耗尽而未生成 repair：Frame04、05、06、14；当前 formal `next_action=USER_DECISION_REQUIRED`，`decision_kind=CANDIDATE_BUDGET_EXHAUSTED`，若继续这四帧，Episode budget 最低需从 35 显式授权到 39。
- Frame03/15/18 继续保留用户此前接受当前版本的决定，本轮未重新生成。
- 当前没有 duplicate attempt id；本轮 image metrics 记录 42 次 image attempts、35 次成功候选、7 次技术失败/阻断。

需要注意：typed projection 增量写已经消除了“每次重写 20 帧历史”的 SQL 放大，但真实 `enqueue_marked_repairs()` 一次处理多帧时仍观察到远程 MySQL 长尾，因此写路径性能不能只靠 projection diff 宣称已经完全解决。后续若继续优化，应把多帧 repair authorization 的 authority read/write 合并为更粗的单事务批处理，或至少减少同一 operation 中反复读取完整 authority；不能用提高数据库超时掩盖写路径放大。

## 目前不能下的结论

- 不能说 WebCodex 的 55 秒 `observe_jobs` 调用就是模型执行了 55 秒；它可能是在等状态变化。
- 不能把 WebCodex 全局日志中的 `run_process` 长尾直接算到 `04_未交的答卷`，因为这次统计没有完成 request/job ID 关联。
- 不能把 `host_wait` 全部归咎于 WebCodex、模型或数据库中的任一方；它是端到端等待量。
- 不能仅凭持续的持久化告警断言该 Episode 的执行 receipt 缺失。

## 建议的最小处理顺序

1. 先给 `next_action.derive` 的每段读取和 MySQL 查询数做 request-scoped 计时，在不改变派生结果的前提下消除重复加载。
2. 对 Review 技术失败串起 attempt identity、WebCodex job ID、receipt 和恢复决策，排查重复 dispatch 与空等。
3. 再把 StoryOS host request 与 WebCodex `run_process`/`observe_jobs` 日志关联，拆分真实执行、轮询和持久化时间。
4. 处理 receipt 持久化降级时，以 completion 可见性、receipt 完整性和告警归零为验收，不能只降日志级别。

本文件是问题记录和归因依据，**不是性能优化已完成或生产门禁通过的证明**。
