# StoryOS 调度器计划增加 Generation Authority 硬阻断（2026-10-09）

## 生产问题与事实

正式《五十亩山地之后》 `image_scheduler.py plan` 曾返回 `ready=[]`、`blocked=[]`，同时 `next_action.py show` 明确要求 `VERIFY_TECHNICAL_GENERATION_EVIDENCE`，Frame 06、24 的共享 MySQL Generation Attempt 1 均为 `OUTCOME_UNKNOWN`。

二者此前含义不同：`plan.ready` 和 `plan.blocked` **只计算状态为 `queued` 的分镜任务及其依赖**，不会列出已有 `tech_failed` 的历史 Attempt。这样空数组看起来像“所有工作已经完成”，却不表示 Stage 可以推进或图片可再生。

## 本轮方案（独立于正式生产的只读投影）

在 `image_scheduler.py` 中新增 `unresolved_generation_evidence_for_plan(ep,q)` 和 `plan_snapshot(ep,q)`，由原 `plan` 命令调用：

- 保留 `ready` 和 `blocked` **旧字段及依赖语义不变**；
- 新增 `authority_blocked`，仅遍历当前 Queue 中 `tech_failed` 的图帧，通过**同一现有** `_technical_retry_budget` 和正式共享 Attempt Authority 验证是否有权重新调度；
- 若现存 Attempt 为 `OUTCOME_UNKNOWN`、`RESERVED`、`DISPATCH_COMMITTED` 等且缺少合法重试依据，将帧号、原技术失败码、Authority 拒绝理由与 `VERIFY_TECHNICAL_GENERATION_EVIDENCE` 显示为 **`retry_permitted=false`**；
- 新增 `requires_evidence_verification`，只表示这类 Frame 权限核销尚未完成；不代表对整个 Episode 进行不可恢复的 Stage 终止决策；
- 已有 `FAILED_AFTER_DISPATCH` 且预算合法的 Frame 不应被误标为历史 UNKNOWN；
- `plan` 不调用 `retry_tech`、`save_queue`、Provider、Model 或 Stage 写入，不覆盖历史 Attempt，更不触发自动派发。

对于现有正式 Episode，预计输出新增：

```json
{
  "ready": [],
  "blocked": [],
  "authority_blocked": [
    {"frame": 6, "technical_failure_code": "IMAGE_TOOL_NO_ARTIFACT", "reason": "previous_generation_attempt_unverified", "action": "VERIFY_TECHNICAL_GENERATION_EVIDENCE", "retry_permitted": false},
    {"frame": 24, "technical_failure_code": "ASPECT_RATIO_MISMATCH", "reason": "previous_generation_attempt_unverified", "action": "VERIFY_TECHNICAL_GENERATION_EVIDENCE", "retry_permitted": false}
  ],
  "requires_evidence_verification": true
}
```

实际拒绝理由以当前 MySQL Authority 为准，不能把这个示例当真实执行回执。

## 验收与部署门禁

新增 `tests/system/test_image_scheduler_authority_plan.py` 共 **10 个待执行测试案例**，覆盖：单条/多条 UNKNOWN 帧、排序、已核销失败不误报、非 tech_failed 不误报、旧字段兼容、无可派发帧时仍可见历史硬阻断、空队列不会凭空出现新阻断、MySQL Authority 不可用时失败关闭、共享预算已耗尽时仍显示不可重试，以及和 `next_action` 的判断一致性。

**本提交的 10 个测试尚未在 Windows StoryOS 工作区运行 pytest，也未运行正式数据库的 `plan` 复测。** 原因是 WebCodex 连接层在本轮反复返回内部错误；GitHub 远程也没有与新 HEAD 关联的可见 CI 运行。只能算**代码已进入独立候选分支，不算生产通过**。不应直接合并安全集成分支，更不能部署到正在运行的 Production Scheduler。

恢复后必须执行：

```powershell
python -m pytest -q tests/system/test_image_scheduler_authority_plan.py tests/system/test_generation_unknown_technical_retry_guard.py tests/system/test_image_scheduler_review_exit_v4.py
python scripts/storyos_production_env.py episodes/_system/image_scheduler.py plan "episodes/00_独立篇/05_五十亩山地之后"
python scripts/storyos_production_env.py episodes/_system/next_action.py show "episodes/00_独立篇/05_五十亩山地之后"
```

要求 `ready=[]`、原有 `blocked=[]` 的语义保持不变，且 `authority_blocked` 正确报告 Frame 06/24；严禁因为新增展示字段而改变 `OUTCOME_UNKNOWN`、扣除/退还 Attempt、打开 OpenCodex 或引入视频。待本地回归、真实只读比对和 Git 冲突检查全部通过，再从本 PR 合并回 `storyos-main-integration-20261009`。
