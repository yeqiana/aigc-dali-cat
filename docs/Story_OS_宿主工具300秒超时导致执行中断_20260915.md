## 三、根因

### 3.1 300 秒墙 vs 3600 秒步预算 —— 12 倍错配

| 层 | 上限 | 出处 |
|---|---|---|
| 宿主 bash 工具 | **300 s** | `~/.devspace/devspace-server.log` 两次实测 |
| 引擎单步预算 `codex_scoped_step` | **3600 s** | `config/storyos.yaml` → `runtime_timeout_policy` |

证据原文：

```json
{"ts":"2026-09-15T02:34:39.471Z","tool":"bash","workspaceId":"ws_5f0a488dcb",
 "commandLength":129,"success":false,"durationMs":300478,
 "error":"Command timed out after 300 seconds"}
```

该调用开始于 `02:29:39Z`，与 `dag run` 的 python 进程创建时刻**分秒吻合**。

### 3.2 孤儿 codex 的产出**没人取**（不是"卡住了"）

codex 被托管给常驻服务 `codex_user_runner.py serve`，`dag run` 死掉时它**不跟着死**：

| 尝试 | codex 起 | codex 止 | 实际跑了 | 产出 |
|---|---|---|---|---|
| #1 | 10:29:41 | 10:46:53 | **1033 s（17.2 min）** | `task-results/a1c696cd….json` **2,438,430 字节** |
| #2 | 10:49:27 | 10:58:37 | **549 s（9.2 min）** | `task-results/1209c5cf….json` **1,203,458 字节** |

两次 codex 都在正常跑（#1 被杀时仍未跑完），产出**完整落盘**。

问题出在消费端：`codex_user_runner.py` **没有 attach / resume**。新一次 `dag run` 用
`uuid4()` 生成新 `request_id`（`:541`），**永远不会回头读旧结果文件**。
所以——**产出没丢，是没人取**。

补充两点（都经核实）：

- serve 是 `ThreadingHTTPServer`（`:1197`），**并发**处理请求。孤儿**不会挡住**新的 driver，
  它纯粹是白烧额度。
- codex 的 stdout 落点是 `meta/scoped-workers/<step>.jsonl`（`scoped_codex_worker.py:207`
  的 `stdout=h`），`h` 由 `dag run` 进程持有。该进程一死，这个文件就再没有写入者——
  所以它是 0 字节。**这不是"卡在管道上"，是写入者已经不在了。**

### 3.3 三层叠加的结果

```
前台 dag run ──300s──> 被杀
      │
      ├─ codex 继续跑完（17 min）──> 产出落 task-results/<uuid>.json
      │                                    │
      │                                    └─ 新一次 dag run 用新 uuid，永不回头读
      │
      └─ 剧集侧：creative_story.jsonl 0 字节，state 仍是 IDEA_LOCKED
```

## 六、修复方案

### 第 1 层：让 driver 活过 300 秒 —— 已落地

`.storyos_cache/dag_detach.py`：以 `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP`
（允许时加 `CREATE_BREAKAWAY_FROM_JOB`）分离启动 `dag run`，stdout/stderr 落**真实文件**
而非管道，3 秒返回；之后一律用 `dag_detach.py --status` 只读轮询。

- ✅ 零引擎改动，已用探针验证「调用方被杀后子进程仍存活」
- ✅ **2026-09-15 11:14:54 实跑验证**：分离启动的 driver（pid 17784）活过了 300 秒，
  进入 CREATIVE_STORY 并拉起 codex 任务进程 33192 —— 这条链第一次真正跑起来
- ❌ 它是**旁路脚本**，且 `.storyos_cache/` 在 `.gitignore` 内 —— 不属于产品

### 第 2 层：把"能分离"做进引擎

给 `story_os.py dag run` 加 `--detach`，让**文档入口自己**具备分离能力，不再依赖旁路脚本。
改 `story_os.py` + `runtime_dag.py`，需补测试。

### 第 3 层：让"被杀"不再等于"白烧" —— 真正的根因修复

接缝已经存在，改动很小：

| 事实 | 位置 |
|---|---|
| `request_id` 本来就是 `run_codex` 的参数 | `codex_user_runner.py:1376` |
| `build_task(..., request_id=...)` 也收 | `:618` |
| `read_task_result(rid)` 现成的读函数，缺失返回 `{}` | `:320` |
| `task_result_path` 只校验 hex/dash | `:313` |
| 结果文件由 serve 端按 `request_id` 落盘 | `:1016-1028` |

做法：**把 in-flight 的 `request_id` 记进 checkpoint**，resume 时先查结果再决定跑不跑。

```
rid  = checkpoint 里记的 in-flight rid（没有就新生成）
prev = read_task_result(rid)
若 prev.returncode == 0 且 output_base64 在
    → 写进 meta/scoped-workers/<step>.jsonl，rc=0 返回      （采纳，不再跑 codex）
否则 → run_codex(..., request_id=rid)
```

效果：**300 秒的墙不再致命**。driver 被砍 → codex 跑完 → 下一次 `dag run` 直接采纳，
**codex 成本为零**。

- 只采纳 `rc == 0`；`rc != 0` 一律重跑（fail-safe）
- 边界：孤儿还在跑时又提交同一个 rid，会并发跑两份 codex → 所以**清孤儿必须先于重跑**

### 备选（不推荐现在做）

`STORY_OS_RUNTIME=CODEX` + `story_os.py runner`：能让文档指定的常驻驱动跨过 scoped 步骤。
但它是**合约级**改动（翻转 `product_runtime_host_required` 等），且 runner 是 daemon
不代表安全——宿主若在前台启动它，一样被 300 秒砍。**它不替代第 1/2 层。**

### 操作红线（写给后续执行者）

1. **不要前台跑 `story_os.py dag run`** —— 必被 300 秒砍
2. **不要用 `taskkill /IM codex.exe`** —— 机器上常驻一个 Codex 桌面端后端进程
   （进程名就是 `codex.exe`），按名杀会连它一起杀掉。只能按 PID：
   `MSYS_NO_PATHCONV=1 taskkill /PID <pid> /T /F`

   2.1 **同名不同物，必须按镜像路径分。** 实测三个都叫 `codex.exe`：

   | 路径 | 是什么 |
   |---|---|
   | `%LOCALAPPDATA%\OpenAI\Codex\bin\...` + `app-server` | **桌面端后端**，常驻，不是本次任务 |
   | `D:\soft\nvm\...\node_modules\@openai\codex\...\bin\` | **本次 scoped 步骤**，从 nvm 的 node 装的 |
   | 同上，但父进程是另一个 codex.exe | 任务进程自己派出去跑单条命令的**子进程**，不是第二个任务 |

   **别用 PID 基线当唯一判据**：桌面端一重启 PID 就变。2026-09-15 11:22:18 实测，
   新的 app-server（9380）冒出来、旧基线（20700）作废，于是它被报成了「本次任务进程」
   —— 照着红线去杀，杀的是桌面端后端。`dag_detach.py --status` 现已按镜像路径过滤，
   `CODEX_TASK` 报出来的才是真的任务进程。

   2.2 **注意进程树：报出来的 driver pid 未必是干活的那个。** 走
   `story_os.py dag run` 时它只是转发器，真正跑 DAG 的 `runtime_dag.py` 是它的
   **孙进程**（见 8.4）。2026-09-15 那轮的 pid 17784 就是转发器。启动器现已改为直接
   分离 `runtime_dag.py`，所以 `--status` 报的 pid 就是真正干活的那个；但若有人绕过
   启动器手跑老命令，这个坑会回来——**清孤儿前先确认进程树，别只看 pid**。

   2.3 **`--status` 现在多报一行 `EXIT rc=<n>`**（启动器套了一层 `--wrap` 收退出码，
   否则分离进程没人 `wait()`，退出码永远丢掉）。它能直接分开三种情况：
   `rc=0` 正常结束 / `rc=20` 引擎主动停下等宿主动作 / 被 TerminateProcess 强杀。
   `EXIT 未记录` 则说明 driver 还在跑、或 wrap 层被一起杀了（例如 `taskkill /T`）。
3. 该 shell 是 Git Bash（MSYS），`tasklist /FI`、`taskkill /PID` 里的 `/FI` `/PID`
   会被当成路径改写并报「无效参数/选项」，**必须加 `MSYS_NO_PATHCONV=1`**
4. 判断卡死的依据是 **`--status` 里 `CODEX_TASK` 的 cpu 秒数长时间不涨**，不是别的：

   | 看起来像信号 | 实际上 |
   |---|---|
   | `CHECKPOINT` 不动 | **正常**。一个步骤整个跑完才写新的一行，中间几十分钟就是不动 |
   | `SCOPED_WORKER_LOG` 是 0 字节 | **正常，而且全程都是 0**。见 4.1 |
   | `CODEX_TASK` 的 `cpu=` 在涨 | **这才是活信号**。codex 多在等 API，涨得慢，但在涨就是在干活 |

   4.1 **scoped 步骤的日志不是流式的。** `codex_user_runner.run_codex` 的 bridge 分支是
   `result = execute_codex(task)` 等整个任务跑完，再 `_write_output(...)` 一次性写进
   `<step>.jsonl`。所以 CREATIVE_STORY 的 ~16 分钟、PREIMAGE_COMPILE 的 ~69 分钟里，
   那个文件**一个字节都不会有**。把它当卡死判据会在健康运行上误报并中止。

## 八、2026-09-15 11:14 实跑：分离启动成功，但死在引擎的一个步骤名 bug

### 8.1 这一轮跑出了什么

分离启动**第一次真正奏效**——driver 活过了 300 秒，把此前连续失败两次的
CREATIVE_STORY 跑完了：

| 时刻 | 事件 |
|---|---|
| 11:14:54 | 分离启动，pid 17784 |
| 11:40:00 | codex 跑完 1504.7 s，**rc=0** |
| 11:40:01 | **CREATIVE_STORY PASS** → `episode-state` 进 `STORYBOARD_LOCKED` |
| 11:41:28 | `preimage-candidates/character-finalize.json` |
| 11:41:59 | `provisional-release.jsonl`（118 s，rc=0） |
| 11:42:05 | `preimage_character_finalize.jsonl`（124.4 s，rc=0） |
| ~11:42:05 | **driver 进程消失** |

产物是真的：`02_..._StoryLock_DRAFT_V1.0.md`（5915 B，3 条硬约束全部兑现）
与 `03_..._20张正式分镜_DRAFT_V1.0.md`（14036 B）。**这次失败与 300 秒墙无关**，
第 1 层是有效的。

### 8.2 根因：`"PREIMAGE_"+task_type` 拼不出注册过的步骤名

`episodes/_system/runtime_dag.py:400-403`：

```python
                def _worker(task):
                    execution_capsule.compile_capsule(ep,"PREIMAGE_"+task["task_type"],write=True)
                    value, _log=scoped_codex_worker.run_step(ep,"PREIMAGE_"+task["task_type"],codex_raw=codex,timeout=timeout)
                    return value
```

而 `TASK_TYPES`（`preimage_task_contract.py:23-25`）里的名字**带 `_PREPARE` 后缀**，
两张注册表里的却**不带**：

| `TASK_TYPES` 拼出来的步骤名 | `stage_read_sets`<br>（`config/storyos-index.json`） | `STEP_DIRECTIVES`<br>（`scoped_codex_worker.py:129-134`） | 实调 `compile_capsule` |
|---|---|---|---|
| `PREIMAGE_CHARACTER_FINALIZE` | ✅ | ✅ | OK |
| `PREIMAGE_ENVIRONMENT_PREPARE` | ❌ | ❌ | **ValueError** |
| `PREIMAGE_WORLD_PREPARE` | ❌ | ❌ | **ValueError** |
| `PREIMAGE_VISUAL_NARRATIVE_PREPARE` | ❌ | ❌ | **ValueError** |

4 个任务**全部提交**（`_state_base` 的 `tasks` 是空模板，那 4 行 RUNNING 是
四次真实的 `update_task_state` 调用），其中 3 个在 `_worker` **第一行**就抛出
`ValueError: unsupported step`。

### 8.3 异常如何穿透，以及为什么拖到 11:42:05

```
_worker 第 1 行抛 ValueError
   └─ preimage_protocol.py:70-78  call() 是 try/finally，**没有 except**
        └─ :83  future.result() 在主线程重抛        ← 此刻约 11:40:01
             └─ execute_local 无捕获
                  └─ runtime_dag.execute() 的步骤循环无 try/except（:395-404 裸露）
                       └─ 穿出 main() → 进程注定死亡
```

主线程 11:40:01 就死了，但 **`ThreadPoolExecutor` 退出时要 join 非 daemon 的
worker 线程**，而 character-finalize 的 worker 还在等它的 codex。进程被迫陪跑到
11:42:05 那个 worker 结束。这一条解释了全部观察：

- 4 个任务卡在 `status: RUNNING`、`updated_at` 停在 11:40:01（完成态的
  `update_task_state` 再也不会执行——主线程已死，`as_completed` 不再 yield）
- `request_id` 恒为 `null`（本机 codex 路径的三处调用都不传 request_id，是设计现状）
- 没有 PREIMAGE_COMPILE 的 checkpoint / node evidence（`execute()` 没走到收尾）
- `preimage_character_finalize.jsonl` 与 ledger 却落在 11:42:05（worker 线程的
  `run_step` finally 里写的）

**这条路走不到 `HOST_ACTION_REQUIRED`（rc=20）**：`runtime_dag.py:372` 的条件是
`active_runtime in {"WORK","WEB"} and not codex`，带了 `--codex` 时 `not codex` 为假。

### 8.4 为什么日志是 0 字节 —— 一个独立的、通用的坑

**`story_os.py dag run` 不是真正跑 DAG 的进程。** `story_os.py:65-66`：

```python
def forward(script, args):
    return subprocess.call([sys.executable, str(SYSTEM_DIR / script), *args], cwd=ROOT)
```

`dag` 子命令只是 `forward("runtime_dag.py", extra)`，所以进程树是

```
detach 出来的 pid 17784（story_os.py，转发器）
   └─ runtime_dag.py（**孙进程，真正干活的**）
        └─ codex_user_runner / codex
```

实测（`.storyos_cache/_nest_probe.py`，其中 D4 用**不含任何仓库代码**的纯 Python
复现）：**`DETACHED_PROCESS` 之下，第二层子进程的 stdout/stderr 进不了日志文件。**

| 分离启动的命令 | 日志 |
|---|---|
| `runtime_dag.py show <ep>`（直接，第一层） | **8123 字符** ✅ |
| `story_os.py dag show <ep>`（转发，孙进程） | **0 字符** ❌ |
| `python -c "print(...)"`（第一层） | 15 字符 ✅ |
| `python -c "subprocess.call([python,'-c','print(...)'])"`（孙进程） | 孙进程输出丢失 ❌ |

**机制未查明，但行为稳定可复现**（三种独立构造均一致）。后果有两条，都很致命：

1. driver 的 traceback 一直存在，只是没有任何接收者——死因无从查起；
2. `--status` 跟的 pid 是**转发器**，真正干活的孙进程不在视野里，
   红线 2 的「按 PID 清孤儿」会漏掉真正该清的那个。

**已改**：启动器改为直接分离 `runtime_dag.py`（第 1 层，D1 已验证输出正常落地），
不再经 `story_os.py` 的转发。

### 8.5 不要再重跑

这个 bug 是**确定性**的：PREIMAGE_COMPILE 每次都会提交同样 3 个名字，每次都会
在几毫秒内抛 `ValueError`。重跑不会推进，只会把状态再洗一遍。
**必须先修名字映射。**

修法方向（择一，未落地）：在 `preimage_task_contract.py` 加
`task_type → 已注册步骤名` 的显式映射供 `runtime_dag._worker` 使用，并加一条
**启动期断言**——`TASK_TYPES` 里每个名字都必须同时在 `stage_read_sets` 与
`STEP_DIRECTIVES` 里注册，缺一个就当场报错，把「25 分钟后才炸」变成「开跑就炸」。

## 附：本文中修正过的误判

留档，避免同样的错再犯：

1. **"孤儿 codex 卡在无人读的管道上、不会产出也不会自己结束"** —— **错**。
   该判断来自"CPU 近零 = 挂死"的误读。实测反证：runner-log 记下了两次任务的
   `elapsed_seconds` / `returncode` / `output_bytes`，`task-results/` 里躺着完整产出。
   codex 一直在正常跑。

2. **"工具时间 10 分钟"** —— **不完整**。那只是两次 `dag run`。agent 全程 27.8 分钟，
   其余时间在做诊断和轮询，且诊断是正确的。

3. **"判断卡死看 `SCOPED_WORKER_LOG` 字节数涨不涨"** —— **错，而且危险**。该文件在步骤
   跑完前一直是 0 字节（见 4.1），所以这个判据会在每一个**健康**的 scoped 步骤上误报，
   让执行者主动中止一次正常推进。**现改为看 `CODEX_TASK` 的 cpu 秒数**（见红线 4）。
   同一个错误还写进了两个地方并已一并改正：v3 提示词第 6 条、以及 `--status` 的读数口径。

4. **"`OpenProcess` 返回 `ERROR_ACCESS_DENIED(5)` 说明进程还在"** —— **错，而且这个比
   误报 DEAD 更危险**。曾据此把 `alive()` 写成「err=5 → 活着」，理由看起来无懈可击：
   driver 在 Session 0、我在 Session 1，拿不到句柄是正常的。实测反证：

   | 判据 | driver 17784 **活着时** | driver 17784 **死后** |
   |---|---|---|
   | `OpenProcess(SYNCHRONIZE)` | err=5 | **err=5**（一模一样） |
   | 从未分配过的 pid 999999 | — | err=87 |

   也就是说 err=5 对「Session 0 的 pid」**无论死活都返回**，只有从未存在过的 pid 才是 87。
   按 err=5 报活着，会把一个**已经死掉的 driver 永远报成 ALIVE**：监视器再也不会喊
   `DRIVER_GONE`，而红线 4 里「DRIVER DEAD 才清孤儿」的条件永远不会成立。
   2026-09-15 11:42 的 driver 死亡因此被漏报约 12 分钟。
   **现改为以 Toolhelp32 快照为主判据**——它跨会话可见（实测能看到 Session 0 的
   `services.exe` / `winlogon.exe` / 93 个 `svchost.exe`），进程若活着必然在表里。

5. **"traceback 打到了 stderr，而日志只抓了 stdout，所以看不到"** —— **推理错，结论对**。
   `dag_detach.detach()` 写的是 `stdout=h, stderr=subprocess.STDOUT`，**stderr 是合并进
   同一个日志文件**的，而 Python 的 stderr 又是行缓冲。实测：分离启动一个必然抛异常的
   子进程，日志拿到 103 字节、含 `Traceback` 与 `ValueError`。所以「日志 0 字节」**不能**
   用 stderr 解释。真正的理由是 8.4 那条：真正抛异常的进程是**孙进程**，它的输出
   在 `DETACHED_PROCESS` 下整个丢失。**教训：结论对不代表理由对，理由会被用来做决策。**
   同一个错误推理还导致另一个误判——「主线程 11:40:01 抛异常」与「日志 0 字节」
   被当成互相矛盾，实际上两者都成立。
