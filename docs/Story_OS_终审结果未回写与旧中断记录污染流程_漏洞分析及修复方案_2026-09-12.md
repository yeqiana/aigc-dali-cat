# 一、问题结论

本次真实全自动生产暴露出一个新的生产闭环漏洞：

> **第二轮最终语义审图已经完成，并且已经明确得到“17 张通过、3 张失败”的真实结果，但该结果没有及时正式回写到 Production Ledger；与此同时，历史 `interrupted_unknown` 队列记录仍被 `next_action` 当作当前最高优先级阻塞项，导致系统没有进入正确的“仅返修失败帧”阶段。**

这不是图片生成失败，也不是最终评审没有执行。

真实情况是：

```text
20 张正式图片已经存在
↓
第一轮最终审图完成
↓
7 张问题帧完成返修
↓
第二轮最终审图完成
↓
真实结果：17 张通过 / 3 张失败
↓
【这里没有及时完成正式收口】
↓
Production Ledger 仍停留在旧通过数
↓
历史 interrupted_unknown 仍存在
↓
next_action 错误优先选择“恢复中断图片”
↓
流程没有自动进入“只处理 03 / 05 / 20”
```

因此本问题本质是：

**“最终评审结果持久化”和“历史队列状态清理”之间缺少原子化收口。**


原因是生产队列中仍保留历史：

这些记录中，有相当一部分对应任务后来已经：

- 已恢复候选；

- 或已经被最终语义评审重新判定。

# 五、为什么这是框架漏洞

正常情况下，系统的权威顺序应该是：

```text
最新成功生成结果
>
最新 Production Ledger 状态
>
最新最终语义评审结果
>
旧的运行尝试记录
>
历史技术失败记录
```

但当前实际行为更接近：

```text
只要 queue 里存在 interrupted_unknown
↓
优先阻塞
```

即使：

- 同帧已有更新候选；
- 同帧已经完成返修；
- Runner 已证明后端成功；
- 第二轮最终审图已经完成；

旧 `interrupted_unknown` 仍可能继续阻塞全流程。

这会造成：

> **历史运行噪音拥有了高于最新权威生产事实的优先级。**

这是错误的。

# 六、与前面已修问题的关系

本次问题和此前暴露的几个问题是同一类“生产状态收口”问题的延续。

此前已经出现过：

1. 后端图片实际成功，但调度器超时，没有及时写回账本；
2. 同帧旧 `tech_failed` 污染 `next_action`；
3. 同帧存在多个历史 `interrupted_unknown` 时，恢复器按“同帧唯一记录”选择错误任务；
4. 最终语义评审要求 `approved_asset`，但 `approved_asset` 又等待最终审图通过，形成互相等待；
5. DevSpace 单次执行窗口结束后，后台 Codex / Runner 实际可能已经成功，但宿主流程不知道。

本次进一步暴露：

> **即使最终评审本身已经完成，如果“评审收口”和“旧队列清理”不是一个完整事务，系统依旧可能停在错误的历史状态上。**

# 七、根因拆解

## 根因 1：最终评审结果与账本不是原子提交

当前存在：

```text
critic 写出 candidate JSON
```

和：

```text
Production Ledger 更新
```

两个阶段。

如果宿主进程在两者之间中断，就会出现：

```text
评审结果已经存在
但账本仍是旧状态
```

这正是当前现象。

---

## 根因 2：next_action 只看“有没有 interrupted_unknown”，没有判断其是否已经过时

当前逻辑过于保守：

```text
存在 interrupted_unknown
→ RECOVER_INTERRUPTED_IMAGES
→ hard stop
```

缺少以下判断：

```text
这个 interrupted_unknown 是否已经有更新成功候选？
这个任务是否已被 supersede？
同帧 Ledger 是否已经进入更晚状态？
Runner 是否已经证明成功？
最终语义评审是否已经绑定了一个更新 SHA？
```

---

## 根因 3：Queue、Ledger、Lifecycle、Runner、Critic 五套证据之间缺统一版本关系

当前至少存在：

- production queue
- production ledger
- image worker lifecycle
- user runner log
- semantic critic candidate/review

它们都在描述同一个 Frame 的不同阶段。

但系统缺一个统一判断：

> **哪个记录代表这个 Frame 的“最新有效事实”。**

因此历史记录会反复“复活”。

---

## 根因 4：收口恢复逻辑已经有能力，但没有自动串进全自动主循环

当前仓库实际上已经逐步具备：

- Runner 成功产物恢复；
- request-id + stdin SHA 精确匹配；
- provider receipt 恢复；
- candidate SHA 恢复；
- 最终语义评审 candidate 恢复；
- `apply-candidate`；
- supersede 语义。

但这些能力目前仍更像独立工具。

全自动主循环没有做到：

```text
发现宿主中断
↓
自动 reconciliation
↓
找到最新真实证据
↓
恢复并收口
↓
重新计算 next_action
↓
继续生产
```

所以仍需要人工推动。

---

# 八、正确的目标行为

第二轮最终评审结束后，系统应该自动执行：

```text
最终语义 critic 完成
↓
验证 candidate JSON 完整
↓
验证 Story / Storyboard / Frame Contract / 图片 SHA 未漂移
↓
按帧写回最终结果
↓
PASS 帧 → Production Ledger PASSED / approved / lock
↓
FAIL 帧 → REPAIR / NEEDS_USER
↓
把同帧更旧 running / interrupted_unknown / tech_failed 标记 superseded
↓
重新计算 next_action
```

对于当前 Episode，应得到：

```text
17 张正式通过
03 / 05 / 20 失败
↓
只处理 03 / 05 / 20
```

而不是：

```text
RECOVER_INTERRUPTED_IMAGES
```

# 九、建议修复方案

## P0-1：增加“最终评审原子收口”

建议在现有：

`episodes/_system/frame_semantic_review.py`

中实现统一的：

```text
finalize/apply transaction
```

职责：

1. 校验第二轮输入快照；
2. 校验所有图片 SHA；
3. 校验 candidate JSON；
4. 一次性按帧更新 Ledger；
5. 自动 promote / lock 通过帧；
6. 自动进入返修状态的失败帧；
7. 最后才删除/归档 `.candidate.json`；
8. 写一份 immutable transaction receipt。

如果事务中间失败：

- 下次根据 receipt 幂等继续；
- 不能重新调用 critic；
- 不能重复 promote；
- 不能重复占用返修次数。

---

## P0-2：给 Queue 增加自动 supersede 规则

当满足任一条件时，旧运行项不再阻塞：

### 条件 A

同 Frame 已存在时间更晚、SHA 不同的成功 candidate。

### 条件 B

同 Frame 已存在 approved_asset / LOCKED。

### 条件 C

同 Frame 最新 semantic review 已绑定更新 candidate SHA。

### 条件 D

旧任务 lifecycle 已成功，但 queue 未收口。

### 条件 E

Runner 已通过 request-id + stdin SHA 证明后端成功。

这些旧项应标记为：

```text
superseded
```

或：

```text
recovered
```

而不是继续保留：

```text
interrupted_unknown
```

---

## P0-3：next_action 必须只看“有效阻塞项”

当前不应简单判断：

```text
counts.interrupted_unknown > 0
```

而应该判断：

```text
存在 unresolved_interrupted_unknown
```

定义：

只有在以下情况同时满足时才是真阻塞：

- 没有更新候选；
- 没有成功 Runner 证据；
- 没有成功生命周期证据；
- 没有 approved_asset；
- 没有更新最终审图结果；
- 无法确认是否调用过 provider。

只有这样的记录才允许：

```text
hard_stop = true
```

---

## P0-4：主循环自动执行 reconciliation

全自动生产主循环每一轮开始前：

```text
reconcile queue
↓
reconcile lifecycle
↓
reconcile runner receipts
↓
reconcile semantic review pending transaction
↓
重新计算 next_action
```

不应该要求人工看到：

```text
RECOVER_INTERRUPTED_IMAGES
```

以后再手动运行恢复命令。

# 十、不要采用的错误修法

## 不要直接删除 interrupted_unknown

因为有些任务可能已经调用图片模型，但尚未留下成功 receipt。

直接删可能导致：

- 重复计费；
- 重复候选；
- 预算错误；
- 审计链断裂。

---

## 不要无条件把 interrupted_unknown 当技术失败重跑

因为本次 05 / 12 / 20 已经证明：

> 后端实际成功，真实图片已经存在，只是外层 worker 来不及收口。

---

## 不要让旧 queue 状态覆盖最终 critic 结果

最终语义评审是内容权威。

历史 worker 状态只负责证明执行事实，不能推翻更新的内容评审状态。

---

## 不要为了继续流程直接把 03 / 05 / 20 标成 PASS

这三张第二轮终审仍然真实失败。

流程收口漏洞修复和内容质量问题必须分开处理。

---

# 十一、验收标准

## 自动恢复验收

构造：

```text
后端图片成功
↓
宿主在 Ledger commit 前退出
```

要求 Story OS 再启动后自动：

1. 发现 Runner 成功；
2. 精确绑定 request-id + stdin SHA；
3. 恢复原图；
4. 不重新调用 provider；
5. 写回 candidate；
6. 旧 queue item 不再阻塞。

---

## 最终评审收口验收

构造：

```text
critic 已写 candidate JSON
↓
宿主在 apply 前退出
```

要求重新启动后：

1. 不重新审 20 张；
2. 校验 pending snapshot；
3. 校验 candidate SHA；
4. 幂等 apply；
5. PASS 帧批准并锁定；
6. FAIL 帧进入正确返修状态；
7. 自动更新 next_action。

---


并且：


不能再因为与这些 Frame 无关的历史 `interrupted_unknown` 返回：

# 十二、优先级

优先级：**P0**

原因：

该问题会直接破坏“一句话全自动生产”目标。

即使：

- 图片生成成功；
- 返修成功；
- 最终语义审图成功；

系统仍可能因为历史运行噪音无法自己继续。

因此这是生产 Runtime 的闭环问题，而不是单个 Episode 的特殊情况。

---

# 十三、最终目标

修复后，全自动流程应满足：

```text
任何阶段宿主超时/退出
↓
Story OS 自动读取已有真实证据
↓
能恢复就恢复
↓
能确认成功就绝不重做
↓
过时失败记录自动 supersede
↓
最新权威结果自动回写
↓
next_action 永远基于最新有效事实
↓
继续生产
```

最终原则：

> **历史执行记录用于审计，最新有效事实用于决策。**

> **旧状态不能阻塞已经被更新成功事实覆盖的生产流程。**
