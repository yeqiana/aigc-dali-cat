# StoryOS Frame Contract 编译与校验性能优化方案

状态：A/B 已实施；真实 Episode 性能基准待在隔离环境验收
日期：2026-09-23
目标 checkout：`D:\workspace\YeQianWorkSpace\yeqian\storyOS`

## 1. 问题与证据边界

`frame_contract.verify_all(ep)` 先对每帧调用 `verify_frame()`，再为核对 index 对每帧调用一次 `compile_frame()`。20 帧时，至少执行 40 次完整编译。`compile_frame()` 每次都会经多种 Episode 级合同的 `load()` 读取同一批权威文档；`episode_contract_persistence.load_latest()` 每次调用都会请求远程 MySQL。

之前在 `aigc-dali-cat` checkout 的隔离副本上，开启 Episode 状态缓存后测得 `compile_frame` 约 4.47 秒/帧、46.5 次 MySQL 查询/帧，`verify_all` 约 191.4 秒、1883 次查询。两帧的 95 次查询中，92 次归因于 `episode_contract_persistence.load_latest()`。当时 `verify_all` 返回 21 项错误，其中 20 项为 Frame Contract 缓存文件缺失。这些数字说明优化方向，但不作为本 checkout 的改前基线。

目前目标 checkout 没有 `episode_state_cache.py`、`mysql_connection_pool.py` 或 `redis_connection_cache.py`；当前生产进程也可能持续写入 `误入桃花源`。本方案的测量和功能验收应使用隔离 Episode；不得修改正在生产的 Episode 或把不同 checkout 的数字作直接前后对照。

## 2. 目标与范围

目标：在不改变公共接口、合同 SHA 算法、MySQL 权威模式和数据库结构的前提下，减少一次 `verify_all()` / `compile_all()` 中重复编译及重复读取 Episode 级合同。

范围内：

1. `verify_all()` 每帧只编译一次；同一份结果用于逐帧缓存校验和 index 校验。
2. 一次批量编译或校验操作内复用 Episode 级合同读取结果；独立 `compile_frame()` 只复用该次调用中重复读取的结果。
3. 对缓存并发、写后失效、异常回退和跨进程写入建立明确边界。
4. 评估按 Episode 批量取得最新合同、异步预取和受控并发，按实测收益决定是否纳入实现。
5. 增加针对性测试，并在隔离 Episode 上记录同条件耗时与底层 SQL 次数。

范围外：长期进程缓存、修改 MySQL/Redis 权威模式、DDL、对其他 persistence 模块的全面改造，以及生产 Episode 的强制重跑。

## 3. 实施方案

### 3.1 单次编译结果复用

保持 `verify_frame(ep, frame)` 的公共接口。抽出内部校验函数，输入已编译的 `current` 和读出的 `cached`，输出与现有 `verify_frame()` 相同的错误。`verify_all()` 在一次循环中为每帧编译一次，并保存该帧的 `current`、`cached` 和用于 index 的期望行；完成逐帧校验后用这些已取得的结果核对 index。

`cached` 必须继续通过当前 MySQL 权威读取路径获取；缺失、SHA 漂移、projection-only 例外及 index 失效检查不得跳过。保留现有错误顺序：环境合同错误优先，之后逐帧错误，最后 index 错误。不存在 index 时无需再次编译。核对 `verify_all()` 的异常捕获语义，避免重构后把原有异常改为未捕获异常。

预期编译次数：对 20 帧从至少 40 次降到 20 次。节省的 SQL 次数由实测确定；Frame Contract 权威读取仍至少每帧一次。

### 3.2 Episode 级合同的操作范围缓存

在 `episode_contract_persistence.load_latest()` 的内部读取路径增加**显式操作上下文**，由 `verify_all()` 和 `compile_all()` 在入口建立、出口销毁。`compile_frame()` 独立调用时创建仅覆盖该调用的上下文；如果上层已有上下文则复用，不重新建作用域。不要仅用永久全局字典或无边界的 `lru_cache`。

缓存键包含已解析 Episode 路径、存储模式、完整 MySQL 连接参数的哈希、规范化的 `contract_type`；涉及文件回退时还必须包含规范化后的 `legacy_path`，或只缓存已验证的 MySQL 正结果。缓存值记录结果及来源。读取和返回都使用深拷贝，避免调用方修改共享字典。第一版只缓存成功且通过文档 SHA 校验的 MySQL 正结果；`dual` 模式无论因异常、缺行还是外部文档校验失败而走文件回退，都不缓存回退结果；`mysql` 模式异常照旧抛出。负结果与 JSON/file 模式缓存待独立证明语义和收益后再启用。

`persist()` 和 `save()` 成功完成权威写入后，清除本操作上下文中对应 Episode/合同类型的条目。若 `save()` 包含 MySQL 与兼容文件两段写入，须明确以现有成功语义为准，避免部分写入后继续返回旧缓存。缓存不改变返回值形状，也不向公共 DTO 增加字段。

批量编译可由线程池并行。上下文须显式传递给工作线程，或通过仅在批量入口有效的共享对象提供，不能依赖主线程的 `threading.local()` 自动传播。使用锁保护条目；同一 key 并发首次读取应只发出一次请求，其他线程等待该读取的结果。不得在持有全局锁时等待远程 MySQL，以免不同合同互相阻塞。

### 3.3 读取一致性与失效

缓存仅在一次 API 调用内有效，函数退出即丢弃；下一次 `verify_all()` 或 `compile_frame()` 从权威库重新读取。本进程通过 `persist()` / `save()` 写入时即时失效相应 key。

跨进程写入无法由本进程自动通知。对长时间批量操作，开始和结束读取权威版本或源 SHA，若发生变化则报告结果过期并要求重试。此检查应使用已有权威字段或快照机制；实施前先确认各 Episode 合同能否提供统一、可信的版本指纹。若无法做到，不应把“单次操作内跨进程写入可自动检测”写成已实现能力，而应把并发写入列为操作前提并在报告中明示。

本轮缓存保留 `mysql` 模式 fail-closed 和 `dual` 模式异常回退的现有行为。任何错误结果不能因为缓存命中而被标记为 PASS。

### 3.4 批量读取与分级缓存

减少单次操作内重复查询之后，再评估把**同一 Episode 所需的合同类型**一次批量读取。当前 `MySqlEpisodeContractRepository.get_latest()` 按 `EPISODE_ID + CONTRACT_TYPE` 每次查一条；可增加受请求类型白名单约束的 `get_latest_many(episode_id, contract_types)`，用一次参数化查询取得各类型的最高版本，再复用现有 `_decode()`。现有 Episode 合同 `list_versions(episode_id, contract_type)` 已按这两个字段过滤，但会返回该类型的全部历史版本，不能直接充当一次请求多个类型的最新版本查询；无过滤的 `list_versions()` 属于 Frame Contract 仓储。

若 `verify_all()` 需读取 20 帧已持久化的 Frame Contract，也可单独评估 `get_latest_frames(episode_id, frame_numbers)`；它按 Episode 和有限帧号读取最新版本，并沿用逐帧的外部文档 SHA 验证及错误报告。批量读取不得把 MySQL 缺失解释成文件 PASS；`mysql` 模式仍只能读权威库。SQL 方案须核对现有索引和实际查询计划，若批量 SQL 反而扫描大量历史版本，则保留逐 key 查询。

建议分级但有界：第一级为单个 `compile_frame()` 内的临时结果；第二级为 `verify_all()` / `compile_all()` 范围内共享的 Episode 合同快照；第三级为已有的 Frame Contract 派生文件和 MySQL 权威文档，不增设常驻进程的无期限内存缓存。跨进程写入后，新一次操作必须重读 MySQL；进程内写入则失效当前操作的相关条目。批量查询取得的数据也要经过同样的深拷贝与失效规则。

批量查询是否纳入本次补丁，以阶段 B 后剩余 SQL 的数量和耗时为门槛。如果重复读取已被消除、仅剩少量不同合同类型的查询，则新增 SQL 与索引复杂度可能得不偿失。

### 3.5 异步预取与受控并发

当前仓储使用同步 PyMySQL，`compile_all()` 已有线程池，`runtime.preimage_parallel_enabled` 在当前配置中为 `true`。无需为这一处改为 `asyncio` 或引入异步驱动。可在编帧前以现有执行器并行预取**彼此独立**的 Episode 级合同，再让所有帧消费同一操作快照；预取必须在实际编帧前完成并传播异常，不能让失败预取静默变成空合同。

批量校验可以在解决共享缓存和权威快照边界后再评估按帧并发。并发上限要结合实际 MySQL 连接预算、当前生产进程数量及远端库延迟确定，不能直接套用图片的 5 worker 上限。优先限制同时在途的 DB 操作数，并证明错误顺序、单写 Ledger、合同 SHA 和 index 结果不变。`verify_all()` 若改并发，收集结果时仍按帧号排序，以维持现有对外错误顺序。

这里的“异步”是让独立 I/O 重叠执行，不会消除查询本身。只有在批量读取及操作缓存后仍有足够多彼此独立的等待时才值得引入；若远端库已接近 20 条总连接预算，增加并发可能使整体更慢。当前 checkout 未见有界 MySQL 连接池，因此 D 阶段必须以连接池合入或其他可执行的进程内 DB 并发上限为前置条件，不能仅在文档中写额度。

## 5. 方案评审

### 评审结论

**有条件通过，先实施 A → B，再用剩余查询和耗时决定 C → D。** A 的行为边界清楚、收益直接。B 能针对剩余 46.5 次/帧查询中的主要来源；C 的批量读取可进一步减少不同合同类型之间的往返；D 只缩短仍然独立的等待。每一步都需要单独计数和测时。跨进程一致性只能以已有权威版本复核提供保证，不能凭单进程缓存自动保证。

### 评审发现与处理

| 等级 | 发现 | 处理 |
|---|---|---|
| 必须 | 原设想“给 `load_latest()` 加单步缓存”没有说明由谁持有步骤范围；逐个 `compile_frame()` 自建上下文无法跨帧复用 | 明确由 `verify_all()` / `compile_all()` 建立顶层上下文，独立 `compile_frame()` 仅建立本调用上下文 |
| 必须 | 并行 `compile_all()` 使用线程池，主线程局部缓存不能自动传到工作线程 | 显式传递共享上下文，并对同 key 首次加载做单次请求协调 |
| 必须 | MySQL 异常后的 `dual` 文件回退若缓存会掩盖网络恢复 | 标记异常回退且不缓存；下次调用重新尝试权威库 |
| 必须 | 目标 checkout 没有前次状态缓存和连接池，前次 4.47 秒/帧不适合作本次直接基线 | 在目标 checkout 的隔离 Episode 重新采样，并分阶段报告收益 |
| 注意 | `verify_all()` 复用编译结果时可能改变错误顺序或 index 缺失行为 | 以现有错误列表作等价性断言；保留 public API 和异常处理 |
| 注意 | 单次操作内发生外部写入时可能混合新旧合同 | 优先复用已有快照/权威版本复核；无可信指纹时不宣称自动检测，避免并发写场景的 PASS 承诺 |
| 注意 | File/JSON 模式的外部写入也可能被操作缓存挡住 | 本进程写后失效；外部写入在下一次操作重新读取；长操作以同一版本边界处理 |
| 必须 | Episode 合同 `list_versions()` 虽有 Episode/类型过滤，但返回全部历史版本，不能高效地取多个类型的最新版本 | 增加受 Episode ID 和合同类型白名单约束的查询；验证最高版本选择与现有 `get_latest()` 一致 |
| 必须 | 图片 5 worker 与 MySQL 连接预算不是同一并发额度 | DB 预取和校验单独限流，记录峰值连接数及排队时间；不因“可异步”直接提高并发 |
| 注意 | 多级缓存若延伸至常驻进程会放大跨进程旧值风险 | 仅保留调用内与批量操作内两级内存缓存；持久派生文件维持现有 SHA 校验 |

### 二次评审裁定（2026-09-23）

1. **A 可单独实施。** `verify_all()` 当前确实先经 `verify_frame()` 编译每帧，再为 index 编译每帧。复用结果时须保留环境错误提前返回、缺失缓存的逐帧错误、index 缺失/帧数错误及外层异常转错误文本的顺序。
2. **B 修改后实施。** 原缓存 key 漏掉 `legacy_path`，且 `dual` 回退不止发生在 MySQL 异常时。第一版只缓存校验通过的 MySQL 正结果，不缓存缺行、坏引用、JSON/file 结果及任何文件回退。并行 `compile_all()` 的上下文传播和同 key 单次加载须写出具体实现，再做并发验证。
3. **C 需要数据门槛。** 先量 B 后剩余的不同合同类型查询。若实施批量查询，SQL 必须保持 `get_latest()` 的每类型最高 `VERSION_NO` 语义，并用现有复合索引的 `EXPLAIN` 验证；不得一次取回全部历史版本再筛选。
4. **D 暂缓。** 当前 checkout 未具备可验证的进程连接额度。只有在池或等效限流落地、A/B/C 后仍有明显独立 I/O 等待、且真实墙钟收益超过排队开销时再实施。
5. **跨进程边界。** 当前方案只保证新操作重新读权威。若要让长操作在外部写入时拒绝旧结果，必须先设计可信的完整版本指纹及其读取时点；没有该机制时不得声称长操作结果具备跨进程一致性。

### 实施记录（2026-09-23）

- A 已实施：`verify_all()` 每帧只调用一次 `compile_frame()`，同一编译结果供帧级校验与 index 校验使用。
- B 已实施：`compile_frame()`、`compile_all()`、`verify_all()` 复用单次操作范围的线程安全正结果缓存；`compile_all()` 显式将同一缓存上下文传入 worker。缓存键包含 Episode 路径、模式、MySQL 参数哈希、合同类型与 legacy 路径；MySQL 写成功后失效。文件回退和缺失结果不缓存，结果读写深拷贝。
- 自动化回归：定向 pytest 19 项通过；相关文件 `py_compile` 通过。
- 尚未验收：隔离 Episode 的真实 `compile_frame` 耗时/查询数、`verify_all` 耗时/查询数，以及生产环境运行噪声记录。C 批量查询与 D 并发预取没有实施。

## Executive Summary

【目标】消除 Frame Contract 校验的重复编译与 Episode 合同重复查询。
【改动文件】本文件；实施阶段拟改 `frame_contract.py`、`episode_contract_persistence.py` 和定向测试。
【风险】跨进程写入、并发连接峰值和异常回退需严守一致性边界。
【必须验收】同一隔离 Episode 的编译次数、SQL 次数、耗时、错误等价性、写后失效与连接峰值。
【结论】A/B 已实施且定向回归通过；真实性能基准待验收，C/D 按剩余查询与连接额度再决定。
